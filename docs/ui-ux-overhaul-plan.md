# Tandem: UI/UX overhaul — plan

Started October 2, 2026. Requested directly: scope and phase a UI/UX improvement initiative, grounded first in established design principles, then in a real audit of what Tandem currently is and how it's actually being used/perceived — with an explicit, deliberately extreme target bar: **easy to learn and use for someone who has never used any app before.**

This is a planning document, not yet authorization to implement. Review the phases below and adjust before Phase 0 starts.

**Phase 0, item 1 (the mobile title-truncation bug) — fixed and verified, Oct 2, 2026.** Root cause confirmed by measuring real rendered widths in the browser (not guessed): `.day-timeline-block-time` was `flex: none` + nowrap, so an unusually wide time string (a cross-midnight range like "10:00 PM–12:00 AM+1" plus the zone badge) could claim up to 154px of a ~235px-wide mobile block with no ceiling, and the icon+who-badge inside `.day-timeline-block-main` consumed another ~71px before the title got anything — leaving the title literally 1.5px wide, rendering as an invisible sliver. Two more tasks turned out to be squeezed the same way, just less visibly (short titles still fit in the scraps). Fixed with three small, scoped CSS/JSX changes in `src/App.css`/`src/components/DayTimeline.jsx`: a `min-width: 100px` floor on `.day-timeline-block-main`, a `max-width: 45%` ceiling on `.day-timeline-block-time`, and `flex-wrap: wrap` on `.day-timeline-block-time-row` so the zone badge drops to its own line as a fallback only when the cap is actually hit (scoped to just the badge via a new `.day-timeline-block-time-label` nowrap class, so the time range itself never breaks mid-phrase). Verified via real browser measurement before/after (title width 1.5px → 50px) and visual screenshots at both the broken mobile width and desktop (desktop is pixel-identical to before — the fix only engages under genuine pressure). `npm run lint`/`npm run build` both exit 0.

## Part 1 — The rubric: established UI/UX principles

Rather than inventing taste-based opinions, every finding and recommendation below is checked against a small set of well-established, named principles. Listed here once so the rest of the document can just cite them by name.

- **Nielsen's 10 Usability Heuristics** (Jakob Nielsen, Nielsen Norman Group) — the industry-standard checklist: visibility of system status; match between the system and the real world; user control and freedom (undo, clear exits); consistency and standards; error prevention; recognition rather than recall; flexibility and efficiency of use; aesthetic and minimalist design; help users recognize, diagnose, and recover from errors; help and documentation.
- **Don Norman, *The Design of Everyday Things*** — affordances (what an element looks like it can do), signifiers (explicit cues that something is interactive), feedback (the system confirms an action happened), mapping (controls relate spatially/logically to their effect), constraints (the design itself prevents the wrong action).
- **Steve Krug, *Don't Make Me Think*** — a screen should be self-evident. If a user has to stop and figure out what something does, or has to be told how to use it before they can, that's a design debt, not a documentation gap.
- **Dieter Rams' principles of good design** — in particular "as little design as possible," "makes a product understandable," and "is honest" (doesn't promise what it can't do).
- **Fitts's Law** — the time to hit a target is a function of its size and distance; primary/frequent actions should be large and close at hand (this is why FAB placement and touch-target size matter, not just taste).
- **Hick's Law** — more choices presented at once increases decision time; a form with everything visible at once is slower to use than one that reveals complexity progressively.
- **Jakob's Law** — users spend most of their time in *other* apps, so they bring expectations from those apps with them; a novel interaction pattern has to earn its novelty, or it should default to the familiar one.
- **Progressive disclosure** — show the common case by default; put the advanced/rare case one deliberate tap away, not visible by default.
- **Recognition over recall** — never require a user to remember a syntax, a hidden gesture, or a rule that isn't visible on screen at the moment they need it.
- **Luke Wroblewski's mobile-first/touch guidance** — ~44×44px minimum touch targets, primary actions within thumb reach on a phone, forms that work with a stationary thumb, not a precise mouse pointer.

## Part 2 — Translating "never used an app before" into testable rules

The stated goal is deliberately more extreme than "intuitive for a typical smartphone user" — it means designing for someone with **no transferable mental model at all**: no assumption they know what a FAB is, what a swipe gesture does, what an icon-only button means, or that a long-press reveals anything. That's a specific, checkable bar, not a vibe. Concretely, it means:

1. **No control is icon-only with no label, the first time it's encountered**, unless the icon is truly universal (a plain ✕ to close, a checkmark to confirm). Everything else gets a visible text label, or at minimum needs to survive a "would my grandmother know what this does" test.
2. **No gesture is the *only* way to do something.** A swipe must always have a visible, tappable equivalent nearby (Tandem already mostly does this — e.g. the `‹ Today ›` arrows exist alongside the day-swipe gesture — this is a real existing strength, not a gap).
3. **No hidden syntax.** If a feature requires typing a specific format to work (a paste syntax, a markdown-like convention), that's a recall burden a true beginner can't meet. It can exist as a power-user shortcut, but there must be a non-syntax path to the same result.
4. **Every destructive action is reversible, or at minimum confirmed in plain language** — not a bare "Are you sure?" but a sentence describing what will actually happen.
5. **The system always says what just happened.** A state change (saved, sent, archived, an error) must be visible and worded in plain language, never silent and never a raw technical error.
6. **The primary next action is always the most visually obvious thing on screen.** A beginner should never have to hunt for "what do I do now."
7. **Forms show the minimum needed to get started, with everything else revealed only when asked for.** A long form with every optional field open by default fails Hick's Law hardest for exactly the person this bar is written for.
8. **Plain language throughout** — no internal jargon (role names, technical nouns like "assignee," "recurrence," "RLS"-adjacent concepts) in anything a non-admin, non-technical member actually reads.

## Part 3 — Current state: what Tandem actually is today, and real evidence of how it's used

This section is grounded in two things: (a) a live audit of the running app (screenshots taken Oct 2, 2026, both desktop and mobile viewports), and (b) real, already-documented incidents from this project's own history (`CLAUDE.md`), which is unusually rich in genuine "a real person got confused/stuck/misclicked" accounts — this project has a strong habit of writing down what actually went wrong, which is exactly the raw material this kind of audit needs.

### 3.1 — Existing strengths (worth preserving, not just preserved by accident)

- **Swipe gestures always have a tappable fallback** (day/week swipe plus the `‹ Today ›` arrows; Board's Pins/Projects/Inbox swipe plus the tab row itself). This already satisfies rule #2 above.
- **Error handling has already been through one real cleanup pass**: raw `alert()` calls were deliberately replaced with inline errors app-wide; push-notification and member-fetch failures are now surfaced instead of silently discarded. This is Nielsen's "help users recognize, diagnose, and recover from errors" already partly in place.
- **Destructive-leaning actions mostly go through soft-disable (archive) before hard delete** — tasks, cork notes, rental properties, work sites all follow this pattern consistently. Real user-control-and-freedom hygiene, applied consistently rather than ad hoc.
- **The team already writes down real confusion as it happens.** `HowToGuide.jsx`'s FAQ tab is explicitly "real questions Ada has asked, written from her side" — i.e., the actual primary non-technical user's own confusions are already catalogued. This is unusually good raw material most projects don't have; the gap (see 3.3) is that it's opt-in and buried, not that it doesn't exist.
- **The New Task form already applies progressive disclosure to its riskiest complexity** — Date/Time/End time/Timezone/Duration collapse behind one tappable summary line instead of five always-open fields (CLAUDE.md's "Part C" work). This is the right instinct; it just hasn't been applied as consistently to the rest of the form (see 3.2).

### 3.2 — Real, current gaps (found live, Oct 2, 2026)

**A genuine mobile layout bug, not a style nitpick.** At a 375px mobile viewport, a task's title can render essentially invisible — "Schedule the construction-loan meeting" collapsed to a sliver of a single letter inside its Day-timeline row, while a sibling row ("Care.com inquiries look for Property Manager") truncates mid-word with no ellipsis styling cue that it's cut off. This directly violates "the system always shows what's there" — a beginner has no way to know a title is even missing, let alone recover it. **This is a Phase 0 bug fix, not a redesign question.**

**The New Task form shows a lot at once by default.** Title, Who, Priority, All-day, the date/time summary, Repeats (plus a 7-button weekday picker that's *always rendered*, not revealed only when "Selected weekdays" is actually chosen), an attachment dropdown, a notes textarea, and two more actions ("+ Add subtask," "+ Add multiple") — all visible on first open. For the stated "never used an app before" bar, this is Hick's Law working against the user: a first task should probably ask for a title and nothing else, with everything past that revealed on request. Worth noting this form already *proved* the team knows how to do progressive disclosure correctly (the date/time summary collapse) — this is applying that same instinct more completely, not inventing a new pattern.

**Task clarifications (the comment thread) are being used as something the UI doesn't actually support.** A real, live example on this task board: a single task accumulated a comment thread of plain-text step-by-step troubleshooting instructions — "at VoIP.ms -> login -> tickets -> click the only ticket -> reopen ticket -> scroll a little downward -> attach your files for verification" — followed by three consecutive, still-unanswered "Waiting for a reply…" messages. This is a real signal, not a hypothetical: the freeform "ask a question or leave a comment" channel is being stretched to do the job of a structured, checkable step list (which the app already has — `ChecklistEditor`/`ChecklistView` — but nothing in the comment flow nudges a user toward it). This is Don Norman's mapping problem: the tool being reached for doesn't match the actual task being done, because the better-fitting tool (a checklist) isn't visible or suggested at the moment it's needed.

**Icon-only, label-less controls are still common**, and this project has already paid for that gap once directly: the always-visible, disabled "Send" button sitting immediately next to a task's Edit/Delete/Duplicate row caused a real reported bug — a user meant to tap the done checkbox, misclicked the ever-present Send button instead. (It's since been fixed to only render once there's content to send — a good, real precedent for rule #1/#6 above, but the broader pattern — icon-only action rows without labels — is still common across the app and worth a systematic pass, not just this one instance.)

**Several past incidents are really "the system didn't say what just happened," Nielsen's #1 heuristic, violated repeatedly before being caught:** a real notification bug told a user "Ada completed a task" regardless of who actually completed it (visibility-of-status violated at the notification layer); the Overdue/Completed-today pills could silently freeze on yesterday's data across a day rollover until a manual reload; a swipe gesture initially fired backwards from the expected direction and had to be corrected after it "read as wrong in practice." None of these are design taste issues — they're the same underlying class of bug (the system's visible state didn't match its real state), worth treating as one systemic risk area, not three unrelated bugs.

**Bulk Add's power-user paste syntax is a real recall burden**, by design — `## Heading` for a milestone, `!high`/`!med`/`!low` markers, zone abbreviations like `PHT`/`CT` appended to a line, indentation to attach a subtask. This is appropriate *as a shortcut* for someone who already knows the app, but it has no beginner-friendly alternative path for the same outcome (adding several tasks, with a priority, in one go) today — it's paste-syntax or nothing.

**Admin-facing screens lean on internal vocabulary** ("Task access," "View & update," "Create & assign tasks," per-feature deny-list checkboxes) that's accurate but not plain-language — acceptable for Aaron as the technical administrator, worth a lighter pass but lower priority than the primary daily-use screens every member touches.

### 3.3 — How Tandem is actually perceived (not guessed — documented)

The project's own history already contains a strong signal of what real confusion looks like for its actual non-technical primary user (Ada):

- The `HowToGuide.jsx` FAQ tab exists specifically because of real, repeated questions from her — but it's reached through Settings → a gear icon → a modal → a tab switch, i.e., exactly the kind of "go find the manual" flow Krug's whole thesis argues against. A true beginner won't think to look there at the moment they're actually stuck.
- A login failure was caused by a mobile keyboard auto-capitalizing a plain lowercase username — a pure "the system should accept what a real person actually types" failure, since fixed, but telling: small friction points compound into real failed-to-sign-in moments for someone with no mental model to fall back on.
- The task-nudge picker was built once to skip the "who" step automatically when there was only one possible recipient, then deliberately reverted back to always prompting, because the automatic version "read as too automatic in practice" — i.e., real use revealed that *less* friction was actually the wrong call there. Worth remembering as a counter-example: the goal isn't "remove every step," it's "remove every step that doesn't carry real information the user needs to confirm."

## Part 4 — Phased roadmap

Ordered so that foundational correctness ships first (cheap, prevents active harm, builds trust fast), then the core daily-use loop gets simplified, then consistency/accessibility get hardened app-wide, then polish. Each phase should be small enough to ship, verify in a real browser (screenshots, not just reading the diff), and check off before starting the next — same verification discipline already established on this project (see `PROJECT_JOURNEY.md`'s "Established conventions").

### Phase 0 — Fix what's actively broken (foundation, not redesign)
- Fix the Day-timeline mobile title-overflow/truncation bug found during this audit (title rendering invisible at narrow widths).
- Sweep for similar truncation/clipping issues at mobile width across the other dense screens (Rentals toolbar, Month view chips, Inbox items) — confirm or rule out the same class of bug elsewhere before assuming it's isolated.
- No scope creep here — bug fixes only, verified with real mobile-viewport screenshots before/after.
