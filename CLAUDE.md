## What this app is

A shared task board that started as exactly two named people — Ada and Aaron — and has since been generalized to support any number of members, for a healthcare VA joining the household who needs the task board without Ada's Rentals/Vault/Staff data. There's still no signup flow (a hand-maintained `members` allowlist, invited via Supabase Auth plus a manual insert — see Members, permissions, and task access below), but the schema and frontend no longer assume exactly two people: `tasks.assignee_ids` is a real array of member ids, `members.permissions` gates whole features per member, and `task_access` gates one member's visibility into another member's tasks, per ordered pair. Some behavior is still deliberately asymmetric — Ada never submits an EOD report, Rentals is specifically her business, Aaron is the app's administrator — but that asymmetry is now expressed as per-member data (`permissions`, `is_admin`, `task_access` grants), not a hardcoded name check. The admin UI for managing another member's permissions/task-access doesn't exist yet (see that section) — today those are still set by hand in the Supabase SQL editor.

## Architecture

**Stack:** React 19 + Vite, no router (despite `react-router-dom` being a listed dependency — it's unused; `App.jsx` conditionally renders `Login`, `TaskBoard`, `StaffClockView`, or a blocked screen based on session state and `useAccountRole()` — see Property manager / staff time tracking below). Backend is Supabase (Postgres + Auth + Realtime + Storage + Edge Functions) on the free tier, accessed directly from the client via `src/lib/supabaseClient.js` — there is no separate API server, except for the Edge Functions described below.

**Icons:** `lucide-react` (outline-style SVG icons, `currentColor`-based so they inherit whatever text color the surrounding element already sets) is the icon system app-wide — nav, header actions, task-row badges, settings, staff clock in/out, everything. `src/components/icons.jsx` (a handful of hand-inlined SVGs matching the same visual recipe — 24×24 viewBox, `stroke="currentColor"`, `strokeWidth 2`, round caps/joins) was TaskRow.jsx/TaskClarifications.jsx's icon source before this and is now fully unused — left in place rather than deleted, matching this codebase's own don't-delete-until-verified convention for migration leftovers. Emoji still appear throughout this doc and in a few genuinely textual spots in the app itself (`HowToGuide.jsx`'s prose, push-notification message bodies built as plain strings for `manual-notify`) — those aren't rendered icon elements and were deliberately left alone; an emoji mentioned elsewhere in this file is describing a concept, not literal current markup.

**Auth:** Password sign-in (`supabase.auth.signInWithPassword`) is the only sign-in method in `Login.jsx` — a magic-link (`signInWithOtp`) fallback used to sit behind a toggle here, but it's gone: it needed a real, working inbox to deliver the link to, which stopped being true once Ada and Aaron's actual Supabase Auth emails were changed to `ada@tandem.local`/`aaron@tandem.local` (see Login below), so the fallback could no longer reach either account. Password sign-in has no redirect step either way, so it was already the one that reliably worked everywhere — magic link breaks entirely inside an iOS "Add to Home Screen" install (isolated storage, no address bar to land the redirect in). Invite-only either way — public signup is disabled at the Supabase project level, not in this code. `src/lib/AuthContext.jsx` wraps the app and exposes `session`/`loading`/`signOut`.

**Login:** every real account — Ada, Aaron, and any `staff` account (see Property manager / staff time tracking below) — signs in with a short username (`"aaron"`, not an email) rather than a real address. Supabase's password auth is still built on email as the identifier underneath (there's no native "sign in by username" call), so `toLoginEmail()` in `Login.jsx` just appends a fixed `@tandem.local` placeholder domain client-side before the real `signInWithPassword` call; typing a full address with an `@` in it still works unchanged, so an account that still has a real email keeps working too. This only works because Ada and Aaron's actual Supabase Auth emails were changed to match (`ada@tandem.local`/`aaron@tandem.local`) — the placeholder domain isn't a real, receivable mailbox, which is exactly why magic link (above) had to go. `toLoginEmail()` explicitly lowercases the input (not just trims it) — the username field is `type="text"`, not `type="email"` (a bare username has to be accepted, not just a full address), so it doesn't get a mobile keyboard's usual no-autocapitalize handling for `type="email"` inputs for free; caught after a real login attempt of plain `"aaron"` landed on the `'blocked'` screen instead of `TaskBoard`, most likely from a keyboard auto-capitalizing the first letter into `Aaron@tandem.local` — a different, unrecognized row as far as auth is concerned. `autoCapitalize="none"`/`autoCorrect="off"`/`spellCheck="false"` on the input ask the keyboard not to do this in the first place, but the lowercasing in `toLoginEmail()` is the actual guarantee, independent of keyboard/OS/autofill behavior upstream.

**Members, permissions, and task access:** `supabase/schema.sql` has a `members` table (id references `auth.users`) that acts as the allowlist: `display_name`, `working_since`, `default_timezone`, `color` (per-member badge color, replacing a hardcoded 2-person color map), `permissions` (jsonb, see below), `is_admin` (boolean — Aaron, today; controls who can grant/revoke other members' access, separate from what a member can personally see). RLS on `members`/`tasks`/most other tables checks membership via `is_member()` (`security definer`, needed so checking "is caller a member" against `members` doesn't recursively re-trigger RLS on that same table). Member rows can now be created in-app (see Admin UI below) or, same as before, by hand via Supabase Auth + a manual `insert into members (...)` per README.

**Feature permissions** (`members.permissions`, a deny-list jsonb blob, `{}` by default): an absent key or explicit `true` means allowed, only an explicit `false` denies it. Deny-list rather than allow-list specifically so an existing member needs zero data to keep full access — Ada and Aaron's rows never had to be populated to keep working exactly as before. Keys in use: `'rentals'`, `'vault'`, `'staff'`, `'reports'` (EOD/EOW/EOM submission — Ada's row has `{"reports": false}`, since she's the boss and never submits one). `has_permission(feature text)` (`security definer stable`, same shape as `is_member()`) is checked *alongside* `is_member()`, never instead of it, on every RLS policy for `rental_properties`/`rental_bookings`/`rental_expenses`/`rental_savings_goal`, `vault_meta`/`vault_entries`, and `staff`/`time_entries`/`work_sites`/`time_entry_requests`'s member-facing policies. `TaskBoard.jsx`'s `hasPermission(feature)` mirrors this client-side to hide the corresponding nav item/quick action, not just block the write.

**Task access** (`task_access`, one row per *ordered pair* — what `viewer_id` may see/do regarding `target_id`'s own tasks) replaces the old `tasks.who` enum's implicit "both members see everything" with something that can actually restrict one member's view into another's. `tasks.who` (a fixed `yours`/`assistant`/`both` enum tied by name to exactly Ada/Aaron, defined once in the now-retired `src/lib/whoLabels.js`) is gone — replaced by `tasks.assignee_ids uuid[]`, a real array of `members.id`, any subset of however many members exist. A row in `task_access` has a `level` (`null` = Hidden, `'view'`, or `'update'`) plus three independent booleans — `can_create`, `can_delete`, `can_reassign` — each requiring `level` to be non-null first (a check constraint; you can't grant an action on a Hidden row). **Absence of a row means Hidden** — the opposite of `permissions`' deny-list default, since this mechanism exists specifically to *restrict* access, not preserve it.

Five `security definer stable` functions resolve a task's real accessibility from its `assignee_ids` at query time (nothing is stored per-task):
- `can_view_task(assignees)` / `can_update_task(assignees)` — the **"any assignee"** rule: `auth.uid()` being literally one of the assignees always grants baseline access; otherwise, the caller needs the matching `task_access` grant (`view`+ for visibility, `update` specifically for editing) for **at least one** of the task's assignees.
- `can_delete_task(assignees)` / `can_reassign_task(assignees)` / `can_create_task_for(assignees)` — the stricter **"every other assignee"** rule: the caller needs the specific grant for *every* assignee other than themself. Being a co-assignee never auto-grants these — a task assigned solely to the caller has no "other assignee" to check, so it's always fully deletable/reassignable/creatable by them regardless.

The four `tasks` RLS policies (`select`/`insert`/`update`/`delete`) are built from these. Reassignment specifically (changing `assignee_ids` on an existing task) can't be expressed in the `update` policy's `using`/`with check` clauses — those never see the row's old and new state at once — so a separate `before update of assignee_ids` trigger (`enforce_task_reassignment_access()`) checks `can_reassign_task` against the old assignees and `can_create_task_for` against the new ones; a plain field edit (checklist, notes) never touches this trigger at all. `grant_admin_access_to_new_member()` (`after insert on members`) auto-grants every existing `is_admin` member `view & update` on a brand-new member's tasks the moment their row is created — no manual step before an admin can oversee a new hire's work — but never the reverse; what the new member can see of an admin stays Hidden until explicitly granted. Ada and Aaron are backfilled to full mutual `update`+create+delete+reassign access, so nothing changed for them when this shipped. **Was documented but never actually deployed**: found Oct 1, 2026, while debugging why Aaron couldn't see RC Lina's tasks after she was onboarded as a real member — neither the function nor its trigger existed in production at all, so no admin ever auto-gained access to a new member's tasks despite this being described here since the N-member generalization shipped. Fixed via a dedicated incremental migration re-applying both (see schema.sql's end) plus a one-time backfill of Aaron's specific missing grant toward RC; worth checking this trigger is actually present (`select tgname from pg_trigger where tgname = 'members_grant_admin_access_to_new_member'`) before assuming the next Add Member will auto-grant correctly.

`delete_recurring_task()` (`security definer`, bypasses RLS by construction) explicitly re-checks `can_delete_task()` before doing anything — this was a real privilege-escalation hole until fixed, since a `security definer` function doesn't inherit the table's RLS policy just because one exists.

**Frontend:** `src/lib/whoLabels.js` now exports `memberColor(members, id)`/`memberLabel(members, id)`/`assigneeBadge(members, assigneeIds)` (one name+color for a single assignee, names joined with " + " in a shared neutral color for multiple) reading the live `members` array instead of a hardcoded map. `AssigneePicker.jsx` is a multi-select toggle-pill component over `members`, replacing every old who-`<select>`/click-to-cycle badge (`TaskForm.jsx`, `BulkAddTasksForm.jsx`, `PriorityItemsEditor.jsx`). The who-filter dropdowns (`TaskBoard.jsx`, `BulkAddTasksForm.jsx`'s Edit tab, `TaskExportForm.jsx`) are populated from live `members` (All + one option per member) rather than a fixed Ada/Aaron/All list, matched via `assignee_ids.includes(memberId)`.

**Overlap detection** (`getOverlappingTaskIds` in `tasks.js`, `DayTimeline.jsx`'s matching stack-conflict check): two tasks conflict when their `assignee_ids` arrays share at least one real member (`assigneeIdsOverlap`), replacing the old `whoSharesPerson`. **EOD report scoping** (`getCompletedInPeriod`/`getCompletedSince`): a task counts toward member X's report when `assignee_ids.includes(X.id)` (`taskBelongsTo`), replacing `whoMatchesFilter`.

**Admin UI:** `ManageMemberAccessView.jsx` (reached from `SettingsMenu.jsx`'s "Manage member access" row, only rendered when `me.is_admin`) lists every other member with an "Edit access" button opening `MemberAccessForm.jsx` — one form per member covering feature permissions (the four `PERMISSION_FEATURES` checkboxes, deny-list, same semantics as `has_permission()`), their `task_access` grant toward every *other* member (a Hidden/View only/View & update radio plus Create/Delete/Reassign checkboxes, disabled and force-cleared while Hidden — mirrors `task_access_actions_require_access`'s own check constraint rather than letting the form produce a combination the database would reject), and their `report_access` grant toward every other member (a plain checkbox per teammate — see End-of-day reports below for why this one has no levels the way task access does). All three writes go through admin-only RPCs (`setMemberPermissions`/`upsertTaskAccess`/`setReportAccess` in `src/lib/memberAccess.js`) — explicit Save, no per-toggle auto-write, matching this app's other draft-then-save forms rather than `cork_notes.archived`-style immediate toggles.

A "+ Add member" button on that same roster opens `AddMemberForm.jsx` — username, a generated password (`generateStrongPassword()` from `vault.js`, same "share this directly, there's no email to send it to" copy `StaffProfileForm.jsx`'s create mode already established), display name, a badge-color swatch picker (`MEMBER_COLOR_PALETTE` in `memberAccess.js`, defaulting to the first color no existing member already has), and the same feature-permission checkboxes, pre-checked to a sensible starting template (Rentals/Vault/Staff off). It does **not** also set the new member's `task_access` grants in the same screen — on success it hands the new member's row straight to `MemberAccessForm.jsx` (still open, now targeting them) so their task visibility toward Ada/Aaron gets set immediately, reusing that already-built form instead of a second, separate "review and create" UI. `create-member-account` (the Edge Function `createMemberAccount()` in `memberAccess.js` invokes) mirrors `create-staff-account`'s exact shape (see Property manager below) — `auth.admin.createUser()` needs the service-role key, so this can't be a plain client insert — but checks `is_admin` specifically rather than just membership, since creating a full member is more sensitive than creating a property-manager account; it rolls back the just-created `auth.users` row if the `members` insert fails, same orphan-prevention `create-staff-account` already established.

Each roster row also has a "Login" button opening `MemberCredentialsForm.jsx` — an admin resetting another member's username and/or password, mirroring `StaffCredentialsForm.jsx` exactly (write-only fields, no way to read back the current username since it's only in `auth.users`) via a new `update-member-credentials` Edge Function (`updateMemberCredentials()` in `memberAccess.js`). Same `is_admin`-specific gate as `create-member-account`, and confirms the target id is actually a `members` row before calling `auth.admin.updateUserById()` — without that, an admin could point it at a staff account's id and hijack that login instead (`update-staff-credentials` is the right path for staff).

**My Profile** (`MyProfileForm.jsx`, opened from a "My profile" row in `SettingsMenu.jsx` — every signed-in member, not admin-gated) closes the self-service gap: display name, badge color (same swatch picker `AddMemberForm.jsx` uses), and an optional password change (`changeOwnPassword()` in `members.js`, same `auth.updateUser()` call `StaffChangePasswordForm.jsx` already established — no current-password re-entry, GoTrue trusts the active session). `updateMemberProfile()` writes `display_name`/`color` with a plain client `.update()`, no RPC needed — those two columns were never behind `guard_member_privilege_columns()`'s trigger, which only blocks `permissions`/`is_admin`. Default timezone is deliberately **not** duplicated into this form — it already has its own row directly in `SettingsMenu.jsx`.

**Not yet built:** admin promotion/demotion (`is_admin` stays SQL-editor-only, deliberately — see the guard-trigger comment above), forced password-change on first login (no such concept exists anywhere in this app, not even for staff), and a "copy access from…" shortcut when adding a member. See `/Users/aaron/.claude/plans/multi-member-permissions.md` for the fuller design doc covering these follow-on phases.

Notifications: `_shared/notify.ts`'s `fetchAllMembers()` (replacing the old `resolveMemberIds()`, which mapped 'Ada'/'Aaron' `display_name` to id by name) and `memberHasPermission()` read every real member generically. `notify-task-events`' assignment ping notifies every id in the new task's `assignee_ids` except the creator; its completion ping attributes to one name when there's exactly one other assignee, or falls back to generic "A shared task was completed" wording for 2+ assignees (unchanged logic, just generalized from a `=== 'both'` check to `assignee_ids.length > 1`). `notify-reminders`' due-soon/stale-overdue loops iterate `task.assignee_ids` directly.

**Completion pings go to admins only, not every non-assignee** — the original rule ("everyone not assigned gets told") worked fine for two people, but once a third, non-admin member joined it meant two teammates getting pinged about each other's routine completions neither one needed to know about (`others = allMembers.filter(m => m.is_admin && !assigneeIds.includes(m.id))` in `notify-task-events`; `fetchAllMembers()` now selects `is_admin` for exactly this). Admin oversight stays automatic — the person managing the team should still see work get done without asking — but peer-to-peer completion chatter doesn't, by design. The one-name/generic-wording split is otherwise unchanged.

**The deliberate opt-in for the rare case someone specific *should* know**: right after a task gets checked off, `TaskRow.jsx` shows a brief, dismissible "Notify someone this is done?" prompt (an `AssigneePicker` + Send/Dismiss, auto-dismissing after `COMPLETION_NOTIFY_TIMEOUT_MS` — 8s, same window Projects' own undo-on-remove banner uses — if left untouched) rather than reopening every time you look at the task, and unchecking the box cancels it outright. Its options are deliberately narrow, not "every other member": `members_who_can_view_task(task_id)` (schema.sql, `security definer`) returns everyone with legitimate visibility into the task (an assignee, or anyone with a `task_access` view/update grant toward one), and `loadCompletionNotify()` further filters that down to exclude the viewer themselves, the task's own assignee(s) (they already know), and any admin (already covered by the automatic ping above) — so the picker can never suggest notifying someone into a dead end (a push that opens to a task they can't actually see), and never duplicates the admin ping. The task's own `created_by` is pre-selected by default when they made the cut — the person who delegated the work is the one most likely waiting to hear it's done, a real signal already sitting on the row, not a new field. Sending goes through `manual-notify`'s new `task_completed` kind ("{name} finished a task"), scoped to exactly the ids picked — unlike `clarification_asked`/`clarification_answered`'s `resolveNotifyIds()`, an empty or missing list here never falls back to broadcasting everyone, since this kind is only ever called with a deliberate, explicit selection to begin with.

**Edge Functions are deployed independently of the frontend (see Commands above) — committing the N-member rewrite of a function's source is not the same as it actually running in production.** Found for real on Oct 1, 2026: `notify-task-events` and `notify-reminders` had both been committed with the correct `assignee_ids`/`fetchAllMembers()` logic since the Sept 30 generalization, but neither was ever actually redeployed — production was still running the original hardcoded two-person version (`task.who`, `resolveMemberIds()`/`resolveTaskWho()`). Since `tasks.who` no longer exists as a column, the deployed code's `task.who === 'assistant'` check always evaluated false against the real (undefined) field, which made every single task completion — regardless of who actually did it or who it was assigned to — hardcode to "Ada completed a task" sent to "assistant" (Aaron). Caught because Aaron completed his own task and got notified that Ada had. Fixed by redeploying both with no code changes needed (the repo was already correct) — `supabase functions download <name>` (compared against the repo copy, then restored via `git checkout --`) is the fast way to check a given function for this exact kind of drift; nothing else in the deployed set (`manual-notify`, `create-staff-account`, `update-staff-credentials`, `create-member-account`, `update-member-credentials`) was stale when checked the same way. Worth re-checking after any future schema change that removes/renames a column a deployed function still reads — a function silently reading a dropped column doesn't error, it just always takes one branch.

`generate_month_occurrences` (schema.sql) copies `template.assignee_ids` straight through onto every generated occurrence — no resolution needed, since assignee_ids is already the real id array, not a name-based enum to re-derive.

**Status is simpler than the schema suggests:** `tasks.status` is still a 3-value enum (`to_do` / `in_progress` / `done`) in Postgres, but the UI only exposes a done/not-done checkbox (`TaskRow.jsx`) — `in_progress` is vestigial and not reachable from the current UI.

**Checklist:** subtasks are a `jsonb` array column (`tasks.checklist`, shape `[{ id, text, done, blocked, blockedReason }]`) rather than a child table. `blocked`/`blockedReason` mark an item as not accomplishable (e.g. a requirement that turned out to be impossible), with an optional reason; blocked and done are mutually exclusive (setting one clears the other) in both `ChecklistEditor.jsx` (create/edit form, purely local state) and `ChecklistView.jsx` (task detail, writes straight to Supabase on every change). The reason `<input>` in `ChecklistView.jsx` keeps local draft state and only persists `onBlur`, not per-keystroke — wiring it directly to the per-change Supabase write made fast typing feel laggy/dropped, since every keystroke was round-tripping over the network before the input reflected it.

**Task icons:** `tasks.icon`, nullable `text`, storing a Lucide icon *name* (e.g. `'Dumbbell'`) — inspired by a competing app (Structured) after comparing its timeline against Tandem's own; scoped down deliberately (see `/Users/aaron/.claude/plans/cuddly-dancing-bird.md` for the full comparison and what got cut: no per-icon color customization, no ML-trained "smart" suggestion, no categorized icon browser). `src/lib/taskIcons.js`'s `guessTaskIcon()` matches the task's title against a curated keyword map (`.includes()`, first match wins, ~40 entries) live at render time — the guess is never persisted, so the map can keep improving later without a backfill touching existing rows. `resolveTaskIcon()` is `task.icon` (an explicit manual pick, which always wins) → the live guess → `null`. `TaskIcon.jsx` is the one shared component both `TaskRow.jsx`'s collapsed row and `DayTimeline.jsx`'s block render through — it renders the resolved icon in `currentColor` (not tinted by priority; a second independent color axis would just compete with the left-border priority color for attention), or falls back to the existing `PriorityDot` when nothing resolves, so an unmatched, unpicked task looks exactly like it always has. That fallback is also why `TaskRow.jsx`'s row gained its own priority-colored left border (mirroring `DayTimeline.jsx`'s block, which already had one) — before this, the now-replaced `PriorityDot` was the *only* priority signal on a collapsed row, so swapping it for an icon would have silently dropped priority entirely for any task with a resolved icon. `TaskIconPicker.jsx` (opened by tapping the icon in `TaskForm.jsx`, next to the Title field) is a flat, searchable grid — not Structured's categorized browser, since this app curates dozens of icons, not hundreds.

**All Day tasks:** `due_date IS NULL`. Created via an explicit "All day" checkbox in `TaskForm.jsx`, not just by leaving the date field blank — the form tracks a separate `allDay` boolean, because a blank date *string* and "deliberately no date" needed to be distinguishable to fix a real bug where editing an existing All Day task and saving without touching the date field would silently give it today's date.

**Task duration:** `duration_minutes` (nullable) + `due_date` = start; the end time is always derived (`due_date + duration_minutes`), never stored separately, so it can't drift out of sync. Shown as a range, e.g. "5:30–6:10 PM (40 min)". `getOverlappingTaskIds()` in `tasks.js` flags two timed tasks that intersect *and* share at least one assignee (`assigneeIdsOverlap` — see Members, permissions, and task access above) — two different people's tasks landing at the same time is never flagged, since that isn't a real conflict. Only needs *one* side of a pair to have a real `duration_minutes`, not both — a point task (no duration of its own) still counts as landing "inside" another task's real span, and gets flagged, exactly like a duration-having pair would; two point tasks against *each other* are still never flagged, since landing on the literal same millisecond isn't a meaningful conflict worth warning about. A point task's own end is treated as equal to its start (a zero-width instant) for the interval-overlap check, rather than needing a separate branch for the point-vs-duration case.

**Recurrence:** every non-`none` value of `task_recurrence` (`daily`/`weekly`/`selected_weekdays`/`biweekly`/`every_3_weeks`/`monthly`/`every_2_months`/`quarterly`/`every_6_months`/`annually`) is materialized ahead of time as real rows, all through the same template/materialize model — this used to be true only for `selected_weekdays`, with every other type instead spawning exactly one next occurrence on completion (`spawn_next_recurrence()`, since retired/dropped) and nothing before that, so a still-open recurring task's future occurrences simply didn't exist anywhere yet, including on the calendar. That inconsistency (pick "Selected weekdays" and see it on the calendar immediately; pick "Daily" and see nothing until you complete the current one) was the actual bug behind a real report — an overdue task turned "Daily" recurring didn't show up on the calendar, because nothing had been generated for it yet. Unifying every type onto one model fixed it: pick any Repeats option, and its upcoming occurrences show up right away.

- The first task saved with any non-`none` recurrence becomes a **template**: `recurrence_series_id` is set to its own `id` (`prepare_recurrence_series()`, a `before insert or update` trigger), and every generated occurrence for that schedule points `recurrence_series_id` back at the template. A partial unique index on `(recurrence_series_id, due_date)` is the actual dedup key, not application logic.
- `generate_month_occurrences(template_id, target_month)` inserts one row per occurrence landing in that calendar month, each copying the template's title/priority/icon/checklist/`assignee_ids`/etc. straight through — no per-occurrence resolution needed, since `assignee_ids` is already a real id array (see Members, permissions, and task access above for what this replaced). Wall-clock time is computed in the template's own `due_timezone`. Two different matching strategies live in one function, branching on `template.recurrence`: `selected_weekdays` (backed by `recurrence_days`, a `smallint[]` of Postgres weekday numbers — Sunday=0..Saturday=6, picked via `WEEKDAY_OPTIONS` toggle buttons in `TaskForm.jsx`, next to the Repeats dropdown) matches by day-of-week from the template's own date to the end of the month, since "the next Monday/Wednesday/Friday" isn't a fixed offset from `due_date`; every other type instead has a genuinely fixed step (a day count for `daily`/`weekly`/`biweekly`/`every_3_weeks`, a calendar-month count for `monthly`/`every_2_months`/`quarterly`/`every_6_months`/`annually`).

**Three rules the generator must keep (fixed Oct 2026 — `supabase/fix-recurrence-generation.sql`, verified against a real Postgres, not just read):** (1) *nothing is generated before the template's own date* — selected weekdays used to back-fill every matching day of the month, so a Mon/Wed/Fri task made on the 28th got eleven overdue copies; (2) *every type is computed in the task's own local wall-clock time* — occurrences are `local_start + k steps` on a plain `timestamp`, then converted with `at time zone due_timezone`, because stepping a `timestamptz` by `interval '7 days'` adds exact hours in the database's UTC session, so a 3:00 PM Central task slid to 2:00 PM after the clocks went back; (3) *each occurrence is computed from the ORIGINAL date, never from the previous occurrence* — the old `generate_series(due_date, …, step)` compounded, so a monthly task on the 31st went Jan 31 → Feb 28 → Mar 28 forever; it is now Jan 31 → Feb 28 → Mar 31 → Apr 30. A fourth guard keeps **one copy per local calendar day** per series, so a copy that is slightly off (finished early at an old, shifted hour) is not doubled by regeneration. The template's own date must itself be one of the chosen weekdays for a weekday schedule: `TaskForm.jsx` moves the start date to the first selected day on or after it (and says so in plain words under the day circles), and re-checks at save.

- **Copies are also created ahead of time by a scheduled job.** `ensure_upcoming_recurrences()` (no auth check, revoked from `anon`/`authenticated`, run hourly by `pg_cron` as `ensure-upcoming-recurrences`) generates this month and next for every template, so the copies — and the "due soon" reminders that read them — exist even if nobody has opened the app yet this month. Before this, a task due early on the 1st had no row until someone loaded the app. `TaskBoard.jsx` also asks for every month the visible Day/Week days touch (a week can straddle two months), not just the selected date's.
- `ensure_month_recurrences(target_month)` — `TaskBoard.jsx` calls it (`ensureMonthRecurrences()` in `tasks.js`, via `supabase.rpc`) whenever the viewed month changes, running every template through `generate_month_occurrences` for that month, so scrolling forward (in Month view, or just paging Day/Week into a later month) materializes it on demand rather than requiring every future month to exist upfront. `security definer`, re-checking `is_member()`-equivalent membership inline since it's invoked directly from the client.
- `sync_current_month_recurrences()` (`after insert or update of recurrence, recurrence_days, due_date, due_timezone`) keeps a schedule's occurrences honest when the *template* itself is edited, and — separately from whatever month the editor happens to be browsing — always regenerates the real current calendar month right away by calling `generate_month_occurrences(new.id, current_date)`. If the template's type/weekdays/time/zone change (or it stops recurring at all), every not-yet-done generated occurrence is deleted first and the current month regenerated fresh — guarded by an `app.recurrence_sync` session flag so that bulk delete doesn't itself re-trigger the deleted-occurrence tombstoning below. This is also what makes editing an overdue task's Repeats field from "Never" to "Daily" show up on the calendar immediately, without waiting for the next month-view visit — the same `after insert or update` trigger that handles a template's ongoing edits already covers the "just became a template" transition too, since `prepare_recurrence_series()` (a `before` trigger on the same statement) has already set `recurrence_series_id` by the time this one runs.
- `task_recurrence_exclusions` (`recurrence_series_id`, `due_date`) tombstones an occurrence the user deliberately deleted, via a `before delete on tasks` trigger (`remember_deleted_recurrence_occurrence()`) — without it, the next month-view visit would see the missing date as "not yet generated" and silently recreate exactly what was just deleted. Guarded by `pg_trigger_depth() = 1` (skip cascade-deletes, e.g. deleting the whole template) and the same `app.recurrence_sync` flag (skip the sync function's own bulk deletes above).
- Deleting any recurring task (`recurrence !== 'none'` in `TaskRow.jsx`, not just `selected_weekdays`) prompts for scope (the "Delete recurring task?" dialog: "Just this one" vs. "This and future") rather than silently picking one, since either reading is plausible and gets it right half the time by guessing. Both routes go through `delete_recurring_task(target_task_id, delete_future)` (`tasks.js`'s `deleteRecurringTask()`) rather than a plain `.delete()`: deleting a non-template occurrence is a plain row delete either way (the template survives regardless — nothing to promote); deleting the template itself is where it gets real — "this and future" deletes the template (cascading its later occurrences) after stripping `recurrence`/`recurrence_series_id` off everything *earlier* so that history doesn't vanish with it; "just this one" instead promotes the next-soonest occurrence to be the new template (re-pointing every sibling row and every existing exclusion at it) before deleting the original, so the series keeps running under a new template id rather than being severed.

Existing deployments need three incremental migrations `schema.sql` alone doesn't retroactively apply (the third, `supabase/fix-recurrence-generation.sql`, is described at the end of this paragraph): `supabase/show-current-month-recurrences.sql` (every function/trigger/table described here, plus an explicit `drop trigger`/`drop function` retiring the old `spawn_next_recurrence()` model and a one-time backfill materializing the current month for every already-existing recurring task) and, unrelated to recurrence but following the same "run once by hand" convention, `supabase/add-rental-turnover-tasks.sql` (see Rentals below). Both are standalone files rather than appended blocks inside `schema.sql` itself, unlike this repo's older incremental-migration convention (e.g. `cork_notes.archived`, `in_negotiation`) — large enough pieces of SQL that inlining them into the middle of the base schema file would have made that file harder to read start to end. `show-current-month-recurrences.sql` is idempotent and safe to re-run even for a project that already applied an earlier, `selected_weekdays`-only version of it. The third, `supabase/fix-recurrence-generation.sql` (idempotent), replaces `generate_month_occurrences` with the corrected version above, repairs future not-done copies the old math left an hour off or on the wrong day of the month (deleting only those, under the same `app.recurrence_sync` guard so they are not remembered as user deletions, then regenerating this and next month), installs `ensure_upcoming_recurrences()` plus its hourly `pg_cron` schedule, and adds `update_recurring_series_future()`. It also contains a **read-only** review query for old back-filled weekday copies before a template's start date, with the delete left commented out for a human to run after looking at the list.

**Editing a repeating task asks "only this task, or this and future?"** The generator copies the template's fields onto each copy when it makes it, so editing the title, priority, icon, assignees, length, source, notes or checklist used to change one copy and leave every future one on the old value. `TaskRow.jsx` now compares those fields on save and, if any changed on a task that belongs to a series, shows the same three-button dialog the delete flow uses (Cancel / Only this task / This and future tasks). "This and future" saves the task normally, then calls `update_recurring_series_future(id, patch)` (`security invoker`, so row-level security still decides which copies you may change): it updates the template (so copies made later inherit) and every open copy on or after this one, never finished ones or earlier ones. Schedule fields (date, time, zone, Repeats) are deliberately outside it — the template-edit trigger owns those — and "Only this task" on the template itself still changes what later-generated copies inherit, since the template *is* the series definition. Until the SQL has been run the function does not exist and the dialog's second choice reports that plainly (`updateRecurringSeriesFuture` in `tasks.js` maps PostgREST's missing-function error). **An All day task with no date cannot repeat** (the generator needs a date to repeat from and skips it), so `TaskForm.jsx` disables Repeats with a one-line reason in that state and saves such a task as non-repeating.

**Recurring-task indicator:** a recurring task (`task.recurrence !== 'none'`) is marked wherever it's shown, in whatever form fits that view's own space. `TaskRow.jsx`'s collapsed row gets the full version — a `Repeat2` icon plus the recurrence label text ("Weekly", "Daily", etc.) in a bordered pill, `title="Repeats {label}"`. `DayTimeline.jsx`'s block reuses the icon alone (no label text — it's fine as a tooltip there instead, `title="Recurring task"`) in the same secondary meta row already shared with the checklist/notes/question icons, since that row is the block's tightest real estate. `MonthView.jsx`'s chip gets the smallest version still: the bare icon at 10px between the title and time, `flex-none` so it can't eat into the title's own `flex: 1` truncation — there was no room here for a tooltip-bearing wrapper the way the other two have, so this one's just `aria-label`'d instead.

**Daily-planner grouping:** inline in `TaskBoard.jsx`, using `getOverdueTasks()` and `getTasksForDay()` (both in `src/lib/tasks.js`) plus a simple `!due_date` filter for the All-Day bucket — rendered as, respectively, a plain list (`AllDayRow.jsx`), a Structured-app-style vertical timeline (`TimelineRow.jsx`) reused by both the Overdue pill's modal (see Completed today/Overdue below) and Week mode's per-day sections, and (Day mode only) `DayTimeline.jsx` — a genuinely time-scaled version, tasks positioned by real start time and sized by real duration on a shared pixel-per-minute axis, with close-together tasks stacking full-width one after another rather than splitting into side-by-side columns (see `DayTimeline.jsx`'s scale/clustering note and Timeline connective tissue below). A task's position in these lists is always its own `due_date`, whether it's done or not — a done task never moves to wherever it actually got finished. This wasn't the original design: a completed task used to be bucketed and positioned by `completed_at` instead, since a household split across timezones means Ada (Central) assigning something at 3pm her time can land on what's already "yesterday" on Aaron's (Philippines, UTC+8) calendar, and a completed task pinned to that original, now-past due day made it look like nothing got done today even though it did. But relocating a task away from the day it was actually scheduled for read as its own kind of wrong — the day it was set for stopped getting credit for it. `getCompletedToday()` (`tasks.js`) now covers the original problem instead, without moving anything — see Completed today below.

**Completed today / Overdue:** two small tappable pills sitting together in the Today tab (`isToday && (completedToday.length > 0 || overdue.length > 0)` in `TaskBoard.jsx`, right below `DateStrip`) reading "N overdue"/"N completed today" — deliberately symmetric, both in layout and behavior, once Overdue stopped being an always-expanded inline section (see below) and became a second pill matching Completed today's existing shape, rather than two different UI patterns answering two similarly-shaped "what needs my attention right now" questions. `getCompletedToday()` filters to tasks with `completed_at` on the viewer's own local calendar day today, regardless of which day they were originally due, and is who-scoped the same way as the rest of the tab (built from `whoFiltered`, not the raw `tasks` array); `overdue` (`getOverdueTasks()`) is scoped identically. Tapping either pill opens a `Modal`/`ModalCard` listing that pill's tasks through the same `TimelineRow`/`TaskRow` pairing Week mode's per-day sections already use — each row still shows its own due date/time in the leading column (`time` is always `due_date`), with a completed task's real completion moment appearing separately via the nested `TaskRow`'s own "Completed HH:MM" tag (`dueLabel`) — so a row can honestly show both "this was due yesterday at 3pm" and "completed this morning" without conflating the two. `completedToday` falls back to `completed_at` for `time` when `due_date` is null — a genuinely dateless task (All Day's own "Date (optional)" left blank) can still be checked off, and unlike `getTasksForDay`/`groupTasksByDay` (which both require a `due_date` to bucket by), `getCompletedToday` doesn't, so this is the one place that case can actually surface. Each row expands in place (`TaskRow`'s own open state) rather than opening a further peek — same reasoning Week already relies on, since these rows aren't height-constrained the way `DayTimeline`'s blocks are.

Overdue used to render as its own always-expanded inline section directly in the Today list (a plain `TimelineRow` list, same shape as a Week-mode day-section) — replaced by the pill above once the list of genuinely stale overdue tasks grew long enough to push the actual "Today" section below the fold on ordinary days, which defeated the point of a *daily* planner. The pill is now the single entry point for browsing overdue tasks; there's no second inline copy of the same list living on the page underneath it.

The Overdue modal's own header also carries a "Move all to today" button (`handleMoveOverdueToToday()` in `TaskBoard.jsx`) — clearing the whole backlog in one tap rather than dragging each stale task forward by hand one at a time. Per task, only the date moves: `splitDueDateInZone()`/`zonedTimeToUtcIso()` (`timezone.js`) pull the task's own time-of-day out of its current `due_date` and rebuild it against today's date, both read in that task's own `due_timezone` (falling back to `DEFAULT_TIMEZONE`, same as everywhere else an unset one is treated) — so a Philippines-time task and a Central-time task each land on their own actual "today" rather than being forced onto one shared date, and a task's scheduled time of day survives the move untouched. Plain `updateTask()` calls, same as any other single-field edit elsewhere in the app — no special-cased bulk RPC, since this is really just N independent per-task writes fired together. That per-task zone-math loop now lives in its own `moveTasksToToday(taskList)` helper, shared with the bulk-select flow below rather than duplicated.

**Bulk-select in the Overdue modal:** requested directly once a long overdue list made touching each task one at a time real friction. "Select" (replacing "Move all to today" while active, rather than sitting beside it — a full-list action and a start-picking-some action read as competing entry points into the same list otherwise, and Select's own "Select all" plus any bulk action already covers the whole-list case) turns on a checkbox per row and a bottom toolbar with three actions, each showing the current selection count: **Mark complete** (a bulk version of `TaskRow.jsx`'s own `handleStatusToggle` — plain `status: 'done'` updates, then `reload()` afterward for the same reason a single toggle already does, since completing a recurring task can spawn/reveal its next occurrence; added specifically because most of a long overdue list tends to be recurring tasks that were actually done but never ticked off), **Move to today** (`moveTasksToToday()` scoped to just the selection instead of the whole list), and **Archive** (see below). `selectedOverdueIds` (a `Set`) resets whenever Select mode toggles off or the modal closes, since a stale id from a closed session would be meaningless against the live, Realtime-updated `overdue` list next time it opens.

**Archiving a task:** `tasks.archived` (boolean, default `false`) — a reversible "not doing this, but keep the record" state, distinct from marking a task done (dishonest for something that was never actually completed) and from deleting it (loses the record), same "soft-disable, not delete" reasoning `cork_notes.archived`/`rental_properties.active`/`work_sites.active` already establish elsewhere in this schema. `getOverdueTasks()`/`getTasksForDay()`/`groupTasksByDay()` (`tasks.js`) all now exclude archived tasks, so an archived task disappears from every planner view — Today, Week, Month, Overdue — not just the modal it was archived from. Not gated behind a `confirm()` the way a delete is, since it's reversible — see "Archive a task to the board" under Cork Board below for the restore path this later gained (a linked pin, with its own Restore to Today action). Since `schema.sql` is applied once to a fresh project rather than tracked as incremental migrations, adding this column to an *existing* live database needs the same manual one-time `alter table tasks add column archived boolean not null default false;` every other additive schema change in this app needs.

`DayTimeline.jsx`'s block position and its "Completed HH:MM" label are deliberately decoupled the same way: `start` (drives the block's pixel position and clustering) is always `new Date(task.due_date)`, while `blockTimeLabel`'s done-branch reads `task.completed_at` straight off the task rather than from `start` — a completed task's block still sits exactly where it was scheduled on the day it was due, while the label states honestly when it was actually finished, even on a day far from where the block itself renders. `blockDateLabel` no longer branches on done status either, now that `start` is always due_date-based — it always formats in the task's own `due_timezone`, matching every other zone-aware label on the block.

**`DayTimeline.jsx`'s scale** (`PX_PER_MINUTE`, 2.5 — 150px/hour) isn't just a legibility preference: a block's minimum render height (`MIN_BLOCK_HEIGHT`, a fixed 58px, tall enough to fit a wrapped title plus the date/time/zone column without clipping) has to feed back into the *clustering* logic too — `groupIntoClusters` clusters on each task's `clusterEnd` (floored to at least `MIN_BLOCK_HEIGHT`), not its real end, since using the raw end let two tasks with genuinely non-overlapping times still render with visually colliding boxes once each got clamped up to the minimum. At too small a scale, that fixed-pixel floor becomes a large real-minute span — at the original 1.2px/min (72px/hour) it was ~48 minutes — so two perfectly separate point-in-time tasks as little as 20-30 minutes apart (or even a task with a real, short stated duration, like a 30-minute one) fell inside that same inflated window and stacked as if they conflicted, with the block's own rendered height exceeding the duration printed on it. Raising the scale to 2.5px/min shrinks the floor's real-minute footprint to ~23 minutes, under `POINT_TASK_MINUTES` (30, the synthetic span a point task without a real duration renders as) — so a point task's own 30-minute span becomes the binding constraint instead of the legibility floor, and two tasks a real 30+ minutes apart stop spuriously colliding.

Two blocks stacked directly against each other within a cluster (`layoutClusters` in `DayTimeline.jsx`) get `STACK_GAP` (8px) of real vertical space between them, unless an `OVERLAP_LABEL_HEIGHT` label is already sitting between that specific pair (that label already provides its own separation — stacking `STACK_GAP` on top of it made the gap disproportionately larger than between any other pair). Without it, a genuinely back-to-back pair (one task ending exactly when the next starts — a common case, not just close-but-not-quite) rendered with both blocks' 1px borders flush against each other, reading as one merged card rather than two. Purely a `stackTop` accumulation change in `layoutClusters`, not a clustering-logic change — it doesn't affect which tasks land in the same cluster (`groupIntoClusters`/`clusterEnd` are untouched), only how much pixel space is reserved between already-clustered blocks, so every other position (`day-timeline-time-dot`, hour ticks, the task-time-label column) that derives from each item's own `top` picks it up automatically.

**Timeline connective tissue** (`DayTimeline.jsx`, Part B of `/Users/aaron/.claude/plans/cuddly-dancing-bird.md` — Structured's own timeline doesn't split overlapping tasks into narrower side-by-side columns either; it keeps them full-width and labels the overlap in plain text): `groupIntoClusters` (the renamed, clustering-only half of the old `assignColumns`) still decides which tasks are "close enough" to need stacking, exactly as before, but every member of a cluster now renders full-width, one after another — `layoutClusters` replaces the old single shared `timeToPx(date)` mapping entirely, walking cluster by cluster and accumulating pixel position directly instead. That replacement is load-bearing, not a style choice: once a cluster's rendered height can differ from its own real elapsed time (stacking N members takes N block-heights, not the real time between the first start and the last end), no single real timestamp reliably maps to one shared pixel position across a cluster boundary any more — a task starting shortly after a big stack would land *inside* that stack's own rendered range under the old linear-window math. `layoutClusters` sidesteps this by never asking "what real time does this pixel correspond to" across a cluster boundary; each cluster's members stack directly against each other (the second's `top` is the first's rendered bottom edge), and the gap *before* the next cluster is computed from real chronological end-to-start (not the `MIN_BLOCK_HEIGHT`-floored `clusterEnd` — using the floored version here would reintroduce the exact "legibility floor treated as real busy time" distortion the `PX_PER_MINUTE` fix above already went after, just between clusters instead of within one).

A stacked pair only gets the explicit "Tasks are overlapping" label between them when both are flagged in `overlappingIds` (the existing real, duration-based conflict detector — see `getOverlappingTaskIds` in `tasks.js`) — two tasks merely close enough to need stacking, but not an actual same-person time conflict (e.g. a point task 25 minutes after another, or two different people's tasks that happen to overlap — `overlappingIds` only ever flags same-`who` pairs), stack with no label between them, same as a genuine back-to-back pair. The label reserves real vertical space (`OVERLAP_LABEL_HEIGHT`, a fixed 22px, computed inside `layoutClusters` itself) rather than floating on top of anything, so it can't overlap either block's own content.

The left time gutter has two independent kinds of labels: normal hour ticks and one explicit start-time label per positioned task. Task labels cannot be inferred from hour ticks—multi-item clusters deliberately suppress ticks because stacked pixels no longer map linearly to real time, which previously made the left time disappear precisely when tasks overlapped or followed a collapsed gap. Hour labels within 8px of a task label are hidden to prevent duplicate text, but every task label always renders. Every positive empty interval between chronological clusters also gets a dashed, centered duration marker: gaps over 90 minutes collapse to a fixed 30px marker, while shorter gaps retain their proportional height with a 22px minimum so even a five-minute label remains legible. Zero/negative intervals are overlaps or back-to-back work, not gaps, and therefore get no gap label.

A dashed connecting rail (`.day-timeline-rail`, anchored near the track's left edge) renders through the dead space between two clusters — both a real, proportional gap and a collapsed one (the latter already got the equivalent `.day-timeline-gap-line` treatment before this, so no separate rail segment there) — reinforcing "this is one continuous day" for a short empty stretch that previously rendered as unmarked blank space. A zero-gap stacked pair gets no separate rail line at all — their block borders are already touching, which reads as connected without needing anything drawn between them; Structured's own version merges its (much larger, circular-avatar) icons into one continuous solid capsule for this case, which doesn't map cleanly onto Tandem's small inline icon, so this was a deliberate scope-down rather than a literal copy.

Hour-tick generation (`pushHourTicks`, inside `layoutClusters`) only runs for a *single*-item cluster or a real gap — never inside a multi-item stack, since a stack has no one real "this pixel = this clock time" correspondence any more. A boundary hour can be reachable from both a preceding gap's tick loop and the following single-item cluster's own tick loop (both inclusive of that exact instant); `layoutClusters` dedupes by real time (`seenHourTimes`, a `Set` of tick timestamps) rather than by pixel position, since two colliding ticks land on the identical pixel too and a positional check wouldn't catch it — caught via a real duplicate-React-key console error during this feature's own verification pass, not by inspection.

**View modes:** the Today tab has a Day/Week/Month toggle (`viewMode` state in `TaskBoard.jsx`, `.period-tabs` reused from Rentals/Priorities) — a "Multi-Day" mode was tried and dropped as redundant with Day+Week. `.period-tabs`/`.period-tab` render as one shared pill capsule (`--pill-bg` background, `999px` radius, `3px` padding) rather than each segment carrying its own border/fill — an inactive segment is just muted text sitting inside the group, and the active one gets a soft accent-tinted background (`color-mix(in srgb, var(--accent) 18%, transparent)`) rather than a solid fill, so it reads as a quiet highlight instead of a bold button. This is a shared class, not Today-specific — the same restyle applies everywhere `.period-tabs` is reused (EOD Reports' period filter, Bulk Add's Add/Edit toggle, the How-to guide's Guide/FAQ tabs), by design, same as every other place this class gets reused for a segmented-tab-row look. Day/Week share one rendering path — `daysToShow` (an array of Date, `getWeekDays(selectedDate)` for Week, `[selectedDate]` for Day, both in `tasks.js`) is mapped into `daySections`, each just `getTasksForDay()` called per day rather than any new bucketing logic; Day mode isn't special-cased in the loop, only its heading is: Day mode keeps the original "only show a heading if Overdue is also present" rule (to not add a redundant lone heading), while Week always labels each section ("Today"/"Tomorrow"/short weekday+date via `daySectionLabel()`) since multiple sections need telling apart. On mobile, Day mode's `.task-list` also responds to a horizontal swipe — left advances `selectedDate` to the next day, right goes back to the day before (`shiftDay()`, a one-day version of the header's own `shiftWeek()`; the initial version had this backwards, going by literal finger-motion direction rather than the usual swipe-left-to-advance carousel/calendar convention, and was corrected after the flip read as wrong in practice). Gated to `!isDesktop && viewMode === 'day'` in the touch handlers themselves rather than conditionally attaching different handlers, since the same `.task-list` element is shared with Week mode. Only reads `touchstart`/`touchend` coordinates (no running `touchmove` tracking, no `preventDefault()`) and requires the gesture to be clearly more horizontal than vertical past a minimum distance, so it can't misfire during an ordinary vertical scroll through a long task list — coexists with `PullToRefresh`'s own vertical-only gesture on the same ancestor without either needing to know about the other. `.task-list` also carries a `min-height: 50vh` — without it, an empty/near-empty day's actual rendered height was just its "Nothing here." text line, so the swipe gesture (attached to `.task-list` itself) only worked in that small sliver; the rest of the visible screen belonged to a parent element with no handler of its own.

Month mode gets the same swipe treatment, same threshold/gating, stepping a new `shiftMonth()` instead (resets to day 1 of the target month rather than shifting the day-of-month as-is, so a naive overflow — e.g. Jan 31 + 1 month — can't skip a month entirely; same fix `RentalsView.jsx`'s own `shiftMonth()` already uses). Implemented as its own small copy of the gesture rather than a shared hook with Day mode's — each is only a handful of lines with a different mode gate and step function. Rentals' own month calendar (mobile only; desktop already has ‹ › arrows and no touch to hook) gets the identical gesture wired to its own existing `shiftMonth()`, wrapped around `RentalCalendar` in `RentalsView.jsx`'s mobile render specifically — mobile/desktop are already two fully separate JSX trees there, so there's no single shared element a runtime `isDesktop` check would need to guard, unlike Today's Day/Month modes sharing one nav header.

**Realtime:** `TaskBoard.jsx` subscribes to four Postgres-changes channels — `tasks-changes`, `members-changes` (the latter exists specifically so the working-status summary pill and each member's own color/permissions update live — see Working status and Members, permissions, and task access above), `member-nudges-changes`, and `task-access-changes` — each just refetches its whole table on any change, no granular diffing. `task-access-changes` reuses `tasks-changes`' own debounced `scheduleTaskReload` rather than a plain `reload()` — a `task_access` grant changes exactly what `reload()` itself would return (which tasks RLS lets the viewer see), not a second, separate kind of data. A table must be explicitly added to the `supabase_realtime` publication (`alter publication supabase_realtime add table <name>`) before Realtime emits anything for it — this is not automatic on table creation and has been missed before, more than once: `members` was caught early on (a live `members-changes` subscription existed in the frontend, but the table was never added to the publication, so a working-status toggle silently never pushed live to anyone else), and `task_access` was caught the same way on Oct 1, 2026 — the channel subscription existed in code with no matching publication membership, so a freshly-granted admin's already-open session had no way to find out their access had changed short of an unrelated reload. Confirm the actual publication membership directly (`select tablename from pg_publication_tables where pubname = 'supabase_realtime';`) rather than assuming a table someone meant to add is actually there — this file's own instructions to add one are easy to skip and leave no error, just Realtime quietly doing nothing.

`EodReportsList.jsx` is self-contained like `RentalsView.jsx`/`CorkBoardView.jsx` (own fetch, no props from `TaskBoard.jsx`) and, as of the `report_access` work, subscribes to its own two channels the same way — `eod-reports-changes` (a teammate submitting or editing a report) and `report-access-changes` (an admin changing who can read whose reports, which changes exactly what the first channel's own refetch would return). **`eod_reports` and `report_access` both need the same `alter publication supabase_realtime add table eod_reports, report_access;` step** — neither was on the publication before this, since reports had no Realtime channel at all until now.

**Forms:** `TaskForm.jsx` is shared between creating a task (`NewTaskForm.jsx`) and editing one (rendered inline in place of the row inside `TaskRow.jsx`). Due date/time are edited as separate `due_date` + `due_time` fields (plus an end-time/duration pair) and combined into one ISO timestamp on submit (`zonedTimeToUtcIso` in `src/lib/timezone.js`) — the database only ever sees a single `due_date` timestamptz plus `duration_minutes`.

For a non-All-Day task, those Date/Time/End time/Time zone/Duration fields don't sit open by default any more (Part C of `/Users/aaron/.claude/plans/cuddly-dancing-bird.md`) — `dueSummaryLabel()` condenses them into one tappable summary button (e.g. "Wed Sep 2 · 3:30–4:30 AM (1 hr) · PHT", or just date/time/zone with no range when there's no duration set), matching Structured's collapsed-by-default layout. Tapping it opens the exact same five fields, unchanged, inside a `Modal`/`ModalCard` instead of always-open — the fields themselves (including `ScrollSelect`'s own nested modal for End time) aren't a new mechanism, just relocated behind a second tap; `Modal.jsx`'s portal-to-`document.body` design is exactly what makes nesting one modal inside another safe here. Deliberately scoped down from Structured's own version: no `⋯` overflow menu (its Change Day/Set Timezone/Inbox actions don't map onto Tandem's field set — All Day is already its own checkbox, sitting outside this summary entirely and untouched by this change) and no custom combined start–end scroll wheel (`ScrollSelect.jsx` stays its existing flat list — a further visual upgrade there was flagged as a separate, more speculative follow-up, not part of what shipped here).

`detectDefaultTimezone()` (`src/lib/timezone.js`) seeds a lazily-created task/priority/cork-note's zone when nobody touches the Time/Timezone fields — it now prefers the signed-in member's own explicit choice (`members.default_timezone`, set via `SettingsMenu.jsx`) over device detection, falling back to the device's own IANA zone (or `DEFAULT_TIMEZONE`) when unset. That preference is cached in a plain module-level variable (`setPreferredTimezone`, kept in sync by `TaskBoard.jsx` whenever `me` changes) rather than threaded through props, since `detectDefaultTimezone()` is called from several places (`TaskForm.jsx`'s `emptyTaskForm`, `CorkBoardView.jsx`, `PrioritiesForm.jsx`) that would otherwise all need `me`/`members` piped in just for this — the same reasoning `useTheme.js` already uses `localStorage` for, except this preference has to be mutually visible (the other person needs to see it too when bulk-adding *your* schedule for you, see `BulkAddTasksForm.jsx`'s `zoneForWho`), so it lives on `members` in Supabase rather than a per-device value.

**Modal:** `Modal.jsx` renders via a React portal straight onto `document.body`, not in place. This matters because a modal opened from *inside* another modal (e.g. the `ScrollSelect` time picker used inside the edit-task form) would otherwise sit nested deep in the outer modal's own DOM subtree — a `transform` on any ancestor (the mobile slide-up animation, for one) creates a new stacking context that traps `position:fixed` descendants regardless of z-index, so the inner modal could render behind sibling content instead of on top. The portal sidesteps this class of bug entirely rather than fighting it with z-index.

**iOS fixed-position reflow:** `App.jsx` listens for `visibilitychange` and forces a synchronous reflow (toggling `document.body.style.display` off and back on) whenever the tab becomes visible again. Fixes a WKWebView bug, not an app bug: a `position: fixed` element (the bottom `MobileNav` capsule, most visibly) can visually detach from the viewport — rendering as if it scrolled away with the page instead of staying pinned — after the installed PWA sits backgrounded for a long stretch (phone locked overnight) and nothing has forced WebKit to recomposite the fixed layer by the time it's reopened. Nothing else in the app triggers a reflow on wake on its own, so this listener is the one place that guards against it, app-wide, not just for the nav.

**"Today" going stale across a day rollover:** `TaskBoard.jsx`'s `displayToday` used to be a `new Date()` snapshot recomputed only when `displayTimezone` changed — fine at page load, but nothing ever told React to re-derive it once the real calendar day actually rolled over during a long-lived session (the same backgrounded-overnight scenario as the reflow bug above, or just a tab left open past midnight without ever backgrounding). `isToday` (`selectedDate` vs. `displayToday`) would then silently go false for what the viewer still saw as "today," taking the Overdue/Completed-today pills with it until a manual reload. A `now` state now re-ticks `displayToday` on `visibilitychange` (the same wake signal the reflow fix already listens for) and on a 60s interval as a fallback for a tab that stays foregrounded straight through midnight. A second effect keeps `selectedDate` tracking along with it specifically when it had been tracking "today" continuously (compared against the *previous* `displayToday`, not the new one) — a `selectedDate` the viewer had deliberately navigated away from is left alone, only a still-on-today one gets nudged forward so it doesn't freeze on yesterday.

**ScrollSelect:** `src/components/ScrollSelect.jsx` is a `<select>` replacement for option lists too long for a native popover to handle reasonably (e.g. the task end-time picker, which lists every 15/30-minute mark up to 48 hours ahead) — opens through `Modal.jsx` (see above) rather than a custom absolutely-positioned panel, which broke down inside the task form's cramped multi-column flex-wrap layout.

**Theming:** CSS custom properties in `src/index.css`, switched via a `data-theme` attribute on `<html>` (`src/lib/useTheme.js`, persisted to `localStorage`). The explicit theme choice must also set the CSS `color-scheme` property — otherwise native form controls render using the OS-level theme regardless of the rest of the page.

## Push notifications

Web Push (VAPID), fully custom — no third-party push service. Three pieces shared across everything:
- `public/service-worker.js` — receives push events, shows the notification, handles tap-to-focus/open.
- `src/lib/pushNotifications.js` — client-side subscribe/unsubscribe; writes directly to the `push_subscriptions` table.
- `supabase/functions/_shared/notify.ts` — `fetchAllMembers()` (a plain service-role query returning every real `members` row, replacing the old name-based `resolveMemberIds()` — see Members, permissions, and task access above) and `notifyMember(memberId, payload)` (sends via the `web-push` npm package, prunes dead subscriptions on a 404/410 response). Any other per-subscription failure (a VAPID key mismatch, a malformed subscription, a push-service error) gets `console.error`'d rather than silently discarded — the calling function still returns 200 regardless either way, since this whole call is fire-and-forget, so an un-logged failure had no trace anywhere. Caught this the hard way debugging a report of Ada's nudges never reaching Aaron: the Edge Function's own request log showed a clean 200, which looked like "server side is fine" right up until the real cause (in that case, actually unrelated — the Mac was asleep, so the push was correctly queued into Notification Center but had nothing to pop a banner on) got found by a different path. The logging gap was real regardless of what actually caused that specific report, and is worth having for the next one.

Three Edge Functions, two different trigger mechanisms, all deployed with `--no-verify-jwt`. **The two the database calls (`notify-task-events`, `notify-reminders`) refuse any request without an `x-notify-secret` header matching the `NOTIFY_SECRET` function secret** (`rejectUnlessNotifySecret()` in `_shared/notify.ts`; fails closed if the secret was never set). Their addresses are public, so before this anyone could post a made-up payload and push text of their choosing to every admin (found in the Oct 8 2026 audit). The trigger function `notify_task_event()` sends the header and the `notify-reminders-every-5-min` pg_cron job send it, both set together by `supabase/set-notify-secret.sql` (which keeps a placeholder: the real value is never committed). They once drifted apart when set in separate steps, and every call was refused with 401, so always set them from one value and compare fingerprints with `supabase secrets list`. Rotating the secret means changing it in `supabase secrets set` and in the trigger (re-run that SQL) and the cron job together:
- `notify-task-events` — Database Webhook on `tasks` INSERT/UPDATE (assignment + completion pings). Only ever called server-to-server by Supabase's own webhook system, never a browser — `--no-verify-jwt` because there's no user session in that call at all.
- `notify-reminders` — pg_cron scheduled, three independent checks per run rather than three separate functions/schedules: tasks due within 15 minutes (`tasks.reminder_sent_at` prevents re-notifying on later cron ticks), tasks that have been overdue for 3+ days and haven't been nudged about it yet (`tasks.overdue_nudge_sent_at`, same one-shot-per-task reasoning — this fires once, not as a repeating daily nag), and rental charges landing today (`chargeDatesForBooking()`, reimplemented here since an Edge Function can't import frontend code). The rental check skips a charge already covered by `rental_bookings.paid_charges` (an advance payment — see Rentals below) and dedups on `rent_reminder_sent_for`, a *date* rather than a boolean so the same booking's later monthly cycles still get their own reminder without needing to be reset by hand; notifies both members, since a rental charge isn't tied to one person the way a task is. Same `--no-verify-jwt` reasoning as `notify-task-events`.
- `manual-notify` — the only one invoked **directly from the browser** (`supabase.functions.invoke()`, used by the end-of-day report form, the "nudge" button, the task-clarifications feature, and task completion — see below), and the only one that actually cares who's calling — but it still needs `--no-verify-jwt`. The platform's own JWT check runs on the CORS preflight (`OPTIONS`) request too, and preflights never carry an `Authorization` header, so with verification *on* the platform rejected the preflight before the real request ever went out, surfacing to the client as a generic "failed to send a request" with no useful error. `manual-notify` verifies the caller itself instead — a per-request Supabase client built from the forwarded `Authorization` header, `auth.getUser()`. **No kind broadcasts to "everyone but the caller" by default any more** — `eod_report` targets `report_access` grantees, `clarification_asked`/`clarification_answered` target the client-chosen `notifyIds` (falling back to everyone only if that field is missing entirely, an older-frontend safety net — see Task clarifications below), and `task_completed` (see the completion-notification paragraphs below, under Members, permissions, and task access) targets only an explicit, client-chosen list with no fallback at all. `nudge` (the person-level 👋) and `task_nudge` (the per-task 🔔) each resolve a single explicit or task-derived target the same way they always did. Every member-only kind (`eod_report`/`nudge`/`clarification_asked`/`clarification_answered`/`task_nudge`/`task_completed`) explicitly checks `!caller` first and refuses rather than acting on a non-member's behalf — `task_nudge` was found missing this check during an Oct 2, 2026 cohesion audit (a staff session could have pushed an arbitrary notification to real members and silently suppressed a task's legitimate cron nudge) and fixed; `time_entry_correction_request` is the one kind a staff account is actually meant to call, so it deliberately has no such check. This is also the only function with a CORS concern (`_shared/cors.ts`), since it's the only one a browser ever preflights.

Notification rules (see `notify-task-events/index.ts`), not a general preference system: assignment pings are symmetric — whoever gets assigned a task by the other person is notified immediately, either direction; assigning yourself a task doesn't ping you, since you already know. Completion pings are symmetric too, in both directions. (This was asymmetric earlier — Aaron pinged immediately, Ada only via the reminder, so Aaron queuing up tasks for her wouldn't spam her — but that changed to symmetric in commit `4c2e2b8` "notification for ada"; this doc had drifted out of sync with the code until it was caught and corrected.)

**Task-level nudge**, distinct from the person-level 👋 nudge icon in the header (see UI structure below) — a 🔔 button on an overdue task's own action row (`TaskRow.jsx`, next to Duplicate), gated by `canNudge = overdue && !task.assignee_ids.includes(meId)` — shown whenever the signed-in member isn't one of the task's assignees (nudging yourself makes no sense, same reasoning assignment pings skip the assigner) and it's actually overdue. No picker needed here, unlike the person-level nudge — the task itself already names who's relevant, via its own `assignee_ids`. Sends `manual-notify`'s `task_nudge` kind ("Still on your plate?" + the task title) and marks `overdue_nudge_sent_at`, the same column the automatic 3-day cron check above uses — whichever fires first (a manual tap or the next cron pass) suppresses the other from duplicating it. `overdue_nudge_sent_at` is otherwise backend-only bookkeeping, same as `reminder_sent_at` — it's selected into the frontend's `TASK_COLUMNS` now (see Inbox's **Nudges** section below), but only to power that Inbox list; there's still no "already nudged" indicator shown on the task row itself. The button's own per-click `nudging`/`nudgeSent` local state is just a fire-and-forget confirmation, not a read of that column.

iOS specifics: web push only works from an installed Home Screen PWA (`manifest.json` + `apple-touch-icon`), iOS 16.4+ — a regular Safari tab can't receive push at all, and this is a hard platform limit, not something fixable in code.

## End-of-day / week / month / biweekly reports

`eod_reports`: one row per `(submitted_by, period, report_date)` — **not** one row per submission. `report_date` is always computed client-side in the submitter's own local timezone (`reportDateForPeriod()` in `src/lib/tasks.js`) and passed explicitly; the column has no database-side default, deliberately, since a UTC-based default would silently bucket under the wrong calendar day for a meaningful part of every day for Aaron.

A later submission within the same bucket doesn't insert a new row — it upserts via the `upsert_eod_report()` Postgres function (`security invoker`, `insert ... on conflict ... do update`), called through `supabase.rpc()` rather than the client SDK's `.upsert()`, because the two data columns have different update semantics `.upsert()` can't express:
- `body` **appends** (old body + a `---`-separated new chunk) — a running log across multiple work sessions in the same day.
- `minutes_logged` **overwrites**, never summed — this mirrors an external time tracker's running total, which the submitter corrects to match, not something this app tallies from sessions itself. Leaving it blank on a given submission keeps whatever total was last set.

`EndOfDayReportForm.jsx` fetches the caller's own existing row for the selected bucket on open (`fetchOwnEodReport`) and, if one exists, shows it read-only above a fresh "add to this" textarea, seeding the auto-tally via `getCompletedSince(tasks, me.id, existing.updated_at)` — only completions *since the last submission*, not the whole period again, so a second session's draft doesn't duplicate what an earlier session already reported. The submit button's own label is dynamic (`EndOfDayReportForm.jsx`'s `submitLabel`) — joins the display names of every member with `permissions.reports === false` ("Send to Ada"), or falls back to "Submit report" once that list is empty. The gate for who even sees this quick action is `permissions.reports !== false`, not a hardcoded name check — see Members, permissions, and task access above.

**Editing an already-submitted report:** a plain author-only Edit button in `EodReportsList.jsx` (`isOwn = r.submitted_by === meId`), separate from the form's own "add to this" append flow above — appending is for a later work session adding new content, editing is for fixing what's already there (a typo, a wrong total). `updateEodReport()` (`eodReports.js`) is a direct `.update()` on `body`/`minutes_logged`, not a call through `upsert_eod_report()` — no append semantics needed here, and the table's existing `"members can update own eod reports"` RLS policy (`submitted_by = auth.uid()`, already present since this table shipped) already scopes it correctly with zero schema change. Edits a report's full `body` text in one textarea (including earlier `---`-separated chunks, if any) rather than treating each chunk as its own independently-editable unit — simpler, and matches how the body already reads as one continuous log. The time field is an hours-number-input + quarter-hour-minutes-`<select>` pair (`MINUTE_OPTIONS`, '00'/'15'/'30'/'45'), matching `EndOfDayReportForm.jsx`'s own "Total time worked" field exactly rather than a bare minutes number — the two are visually identical by design, duplicated locally rather than shared (same small-helper-duplication precedent `buildWeeks()`/`csvEscape` already set). No push notification on an edit, same silent-by-design reasoning as resolving a task clarification or editing a Cork Board pin.

**Who can read whose reports — `report_access` (`viewer_id`, `target_id`), a plain presence grant.** Reports used to be unconditionally mutually visible to every member (a flat `is_member()` SELECT policy) — that stopped being appropriate once a team member's reports could be as personal as a private work log rather than something every other member, including an unrelated VA, should default into reading. A row means `viewer_id` may read `target_id`'s reports; absence means Hidden, same "restriction, not preservation, is the default" reasoning `task_access`'s own absent-row convention already established, for the same reason (this exists specifically to *restrict* visibility that used to be automatic). `has_report_access(target_id)` (`security definer stable`, mirrors `has_vault_access()`) backs `eod_reports`' own SELECT policy: `submitted_by = auth.uid() or has_report_access(submitted_by)`. Unlike `task_access`, there's no `grant_admin_access_to_new_member()`-style auto-grant for admins — reports are the more private case here, so even the admin has to explicitly opt in to reading a given member's reports rather than getting it for free the way task oversight does. `set_report_access(viewer_id, target_id, can_view)` (admin-only `security definer` RPC, mirrors `upsert_task_access()`) is the one write path — a plain insert-or-delete, not a level change, since reading someone's reports has no finer-grained action to gate the way task access has create/delete/reassign. Migrated in preserving only Ada and Aaron's existing mutual visibility (the original two-person relationship), explicitly *not* every member-pair that technically had access under the old flat policy — a VA was never meant to read another VA's or Ada's reports, so that part of "today's access" was the actual problem being fixed, not something to carry forward.

Managed from `MemberAccessForm.jsx`'s new "Report visibility" section, right below Task visibility — one checkbox per teammate ("Can read {name}'s reports"), same draft-then-Save shape as everything else in that form. `manual-notify`'s `eod_report` kind no longer broadcasts to "everyone but the caller" — it queries `report_access` for every `viewer_id` granted toward the caller and notifies exactly that set, so a report submission can't push someone who isn't actually allowed to open it. `can_access_task_attachment()`'s own `eod_reports`-attachment carve-out (see Completion submissions below) was updated the same way — it used to assume every report was universally readable; now it re-checks the same `submitted_by = auth.uid() or has_report_access(submitted_by)` condition before granting attachment access, or a report's attachment would stay openable by someone who'd just lost (or never had) access to the report itself.

`biweekly` (the 4th `report_period` enum value, alongside day/week/month) exists specifically to account for everything completed within one payroll cutoff at once, rather than piecing it together from several week reports. Unlike week/month's boundaries (always "the current calendar week/month, whatever that happens to be"), a payroll period is a *fixed* 14-day cycle that doesn't reset with the calendar — so `startOfPeriod()` in `src/lib/tasks.js` anchors it to `BIWEEKLY_ANCHOR` (2026-07-26, a real confirmed cutoff: paid Aug 12 for Jul 26 - Aug 8, paid Aug 26 for Aug 9-22) and counts whole 14-day blocks elapsed since then, so every later cutoff stays aligned to it too, however far past the anchor "now" gets — same "always compute from the one fixed origin point, never the previous cycle" reasoning as `rentals.js`'s `addCalendarMonths`. `'biweekly'` reads fine as a bare adjective everywhere else it's used (the H2 title, the sent-notification text, EodReportsList.jsx's meta label — "Biweekly report", "— biweekly —"), but not in the few spots that slot the period into "this ___" prose ("this week" reads fine, "this biweekly" doesn't) — those go through a small `PERIOD_NOUN` map (`'pay period'`) in `EndOfDayReportForm.jsx` instead.

**Hidden from the UI, not removed:** the "2 Weeks" tab was pulled from both `EndOfDayReportForm.jsx`'s `PERIODS` and `EodReportsList.jsx`'s `PERIOD_TABS` after it turned out to add more tab-row clutter than it pulled its weight day to day. Everything else described in this section — `BIWEEKLY_ANCHOR`/`startOfPeriod()`, the DB enum value, `PERIOD_NOUN` — is untouched, and any already-submitted biweekly report still appears in `EodReportsList.jsx` under "All" (it isn't period-filtered out, just no longer has its own dedicated tab). Deliberately reversible rather than a full removal, so bringing the tab back later is a one-line change, not a rebuild.

**Backdating a missed bucket:** `startOfPeriod()`/`reportDateForPeriod()`/`getCompletedInPeriod()` (`src/lib/tasks.js`) all take an `offset` (whole periods back from the current one — 0 default, -1 one period ago, etc.), and `EndOfDayReportForm.jsx` exposes it as a `‹ [bucket label] ›` stepper (`periodBucketLabel()`) below the Day/Week/Month tabs — added once it turned out there was no way to submit for a bucket that got missed entirely (e.g. it's September and August's month report never got sent; the form could previously only ever reach whichever bucket "now" falls in). Resets to 0 whenever the period tab itself changes, and `›` is capped at 0 — there's nothing to report on for a period that hasn't happened yet. The current bucket (offset 0) stays bounded by "now" like before (the period isn't over); a past bucket is bounded by the start of the *next* one instead, so browsing back to August doesn't also pull in everything completed between September 1 and today. A backdated submission's push notification and the modal's own `<h2>` both name the actual bucket (e.g. "Month report — August 2026") rather than just "Month report", so a report arriving well after the fact doesn't read as if it just happened.

## Priorities

`priorities` table — any member can set their own (no `permissions` key gates it, unlike `eod_reports`' submit-side gate). Append-only: every save is a new row scoped to a `period` ('day'/'week'/'month'); "current" priorities for a period is the most recent row **for that specific person**, not the most recent row team-wide — `fetchLatestPriorities(setBy)` in `src/lib/priorities.js` always filters to one `set_by`.

**Genuinely per-person now, not one shared note.** Priorities originally worked the same way `eod_reports` used to: "current" was literally whoever saved most recently, visible to everyone, with no concept of "whose" priorities a given entry was. That broke the moment per-person privacy became a real need (the same VA-privacy concern that drove `report_access`) — a global "most recent wins" view can't coexist with restricting who sees whose, because a restricted viewer would've had RLS silently skip past the real most-recent entry to an older one they *could* see, surfacing as "current" with nothing indicating it was stale. `priorities_access` (`viewer_id`, `target_id`) is the exact same presence-grant shape `report_access` already established — `has_priorities_access()`/`set_priorities_access()` mirror `has_report_access()`/`set_report_access()` precisely, including the "admin opts in explicitly, no auto-grant" rule and the Ada/Aaron-only migration backfill. Managed from the same `MemberAccessForm.jsx` as Report visibility, right below it.

**Granting access needs somewhere to actually use it** — `eod_reports` already has one (`EodReportsList.jsx`'s whole tab); priorities didn't, since the only place priorities ever surfaced was the compose form's own "what did I last write" reference. `fetchLatestPrioritiesForTeam()` (`priorities.js`) is the other half: one unfiltered query — RLS alone already scopes the result to "my own rows, plus anyone's I have `priorities_access` to," no separate access-roster fetch needed first — grouped client-side into the latest row per `(set_by, period)`. `PrioritiesForm.jsx` renders a second read-only "Teammates' priorities this {period}" section from it, listing only teammates it actually found an entry for (RLS already dropped anyone with no grant, and there's no way or need to tell "no access" apart from "hasn't set any" — both mean nothing to show).

Saving also creates a real task per bullet item (`PrioritiesForm.jsx` → `createTask()`), not just the note — the point is that priorities stop being easy to set and forget. Day-period items get `due_date` set to today (so an unfinished one can go overdue like any other task); week/month items become All Day tasks (`due_date: null`), sticking around until done. The previous save's items are shown read-only (as "You last set this," always your own — `memberName` is no longer threaded into this form at all, now that the reference can never be anyone but the viewer) and are never pre-filled into the editable list you're about to submit — otherwise reopening the form and saving again would recreate a task for every old item, not just anything new.

## Rentals (Awa Rentalz / Azu Rentals)

A side-feature bolted onto the task board: `RentalsView.jsx` (the "Rentals" tab — see UI structure below) tracks occupancy and finances for Ada's furnished-rental businesses. Two companies share this exact same schema/UI — `awa` (Ada's own Awa Rentalz) and `azu` (Ada's mom's separate, unrelated Azu Rentals) — as two independent sets of units/bookings/expenses/financials, switched from the header rather than hardcoded, since `rental_company` (schema.sql) was already a two-value enum with nothing else built on `azu` until this. All the `rental_*` tables use the same `is_member()` RLS as everything else — mutual visibility, no per-row ownership, and no RLS distinction between the two companies either (both members already see both).

**Company picker:** which company the whole tab is scoped to (`company`, one of `'awa'`/`'azu'`) is owned by `TaskBoard.jsx` (`rentalsCompany` state), not `RentalsView.jsx` — the picker that changes it replaces the plain page title in the shared header (`COMPANY_LABEL` map, a `<select>` styled to look like the bold `<h1>` it replaces, with a `ChevronDown` caret matching the Today tab's own `MonthNavLabel` — the "the title itself is the control" pattern already established there, rather than a second picker UI bolted on somewhere else). `RentalsView.jsx` receives `company` as a prop and re-fetches everything scoped to it — `properties`/`expenses`/`goals`/`upcomingBookings` in one effect keyed on `company` (which also resets `properties` to `null` and `selectedUnitId` to `''` first, so the old company's data/selection can't linger mid-switch — the null flips the view back to its own existing "Loading…" state, and clearing the id lets the "default to the first unit" effect re-fire against the new company's list instead of pointing at an id that only ever existed in the old one), and month-scoped `bookings` in its own effect keyed on *both* `monthDate` and `company` (unlike the others, it was already re-fetching on month change, so switching companies without also changing months needed adding to that existing effect rather than the mount/company one). The `rentals-changes` Realtime channel subscription is also re-created on `company` change (added to that effect's own dependency array, previously just `[monthDate]`) — without it, the closures the channel's handlers were subscribed with would still point at whichever company was selected when the subscription was created, so a live update arriving after a company switch would refetch the company you'd just switched away from. Every `rental_*` write already took `company` as a real parameter (`fetchRentalProperties(company)`, `createRentalProperty(company, ...)`, etc. — `src/lib/rentals.js`), so none of that layer needed to change; this was purely a frontend UI gap.

`RentalsView.jsx` also subscribes to its own `rentals-changes` Realtime channel (`rental_properties`/`rental_bookings`/`rental_expenses`/`rental_savings_goal`, each just refetching on any change, same reasoning as `TaskBoard.jsx`'s own channels), same as `CorkBoardView.jsx`'s `cork-notes-changes`. **All four of those tables must be added to the `supabase_realtime` publication by hand** (`alter publication supabase_realtime add table rental_properties, rental_bookings, rental_expenses, rental_savings_goal;` in the Supabase SQL editor) — see the Realtime note under Architecture; this is not run automatically by `schema.sql`.

**Two genuinely different layouts**, picked in `RentalsView.jsx` via `useMediaQuery('(min-width: 900px)')` (`src/lib/useMediaQuery.js` — a small `window.matchMedia` + change-listener hook, the *only* JS-driven responsive branch in the app; everywhere else, including this same 900px breakpoint for `.task-board-nav`, is one markup repositioned via CSS media queries alone). That works when both layouts are the same content differently arranged; Rentals' mobile tabs (Calendar/Financials/Overview, one panel at a time behind `view` state) vs. its desktop dashboard (all three always mounted side by side, no tabs) are structurally different trees, not a CSS rearrangement of the same one, so picking which tree to render at all has to happen in JS.

**Desktop dashboard** (`.rentals-dashboard`, a 2-column grid — went through several worse attempts first, all superseded, including a 3-column version with the unit list as its own sidebar column, then a version with it as its own section below the calendar): the main column holds a combined nav row (`.rentals-combined-nav`: month prev/next (`‹ August 2026 ›`) plus "+ Add booking"/"Edit unit"/"+ Add unit" buttons — an earlier version also had a second `‹ Unit ›` prev/next pair cycling `selectedUnitId` by index, since dropped in favor of the Overview-list-as-unit-switcher below being the only way to change units here), then the calendar. `RentalOverview.jsx` renders *inline with "+ Add booking"*, in the same row, via a `unitTabsReplacement` prop on `RentalCalendar.jsx` — `showUnitTabs={false}` hides that component's own `.rental-unit-tabs` toolbar there, and `unitTabsReplacement` fills that exact slot instead of a plain `<select>`/tabs row (no separate "Units" section needed: each row already carries most of the context you'd want — status, and now price too — and doubles as the way you switch units, so a second below-the-grid section duplicating that was redundant). `.rental-calendar-toolbar .rental-overview-list` overrides the list to lay out as a fixed two-per-row wrapping grid (`flex-direction: row`, each `<li>` locked to `flex: 1 1 calc(50% - 4px)`) instead of Overview's own mobile-tab vertical list, to actually fit that toolbar. Financials stays permanently visible in its own column on the right (`RentalFinancials.jsx`, unchanged, just not gated behind a `view === 'financials'` tab — it was already company-wide aggregate regardless of which unit's calendar is showing) under a subtle `.task-section-heading`-styled "Financials" label (reused, not a new class) — the per-unit `$X/mo` price line that used to sit at the top of this column was removed as redundant once `RentalOverview.jsx`'s rows show each unit's price directly. `selectedUnitId` moved out of `RentalCalendar.jsx` (which used to own it) up into `RentalsView.jsx`, since both the Overview list and the combined nav row need to drive the same selection. No flat `max-width` cap on `.rental-month-grid` in this layout — the main column's own width already bounds it to a comfortable size, unlike the old single-column layout where the grid had nothing else constraining it.

`.rental-overview-list` needs an explicit `list-style: none` — a `<li>` still gets a marker box even inside a flex/grid parent (blockification changes layout mode, not marker generation), which is easy to assume is already handled by `display: flex` alone and isn't.

Tandem's shared member shell is `1360px` on desktop, retaining centered outer margins rather than going edge-to-edge; this applies consistently to Timeline, Rentals, Reports, Board, and Staff instead of widening only the dashboard tab. Rentals' own two-column dashboard keeps the 340px Financials rail near the 900px desktop breakpoint, then grows that rail to 380px at 1200px while the calendar receives the rest. Mobile and tablet behavior is unchanged.

**Mobile** used to be three separate tabs (Calendar/Financials/Overview, one panel at a time behind a `view` state) but is now Overview → "+ Add unit" → month nav → Calendar → Financials stacked into one scrollable column, no tabs — switching between "kinds of info" meant losing sight of everything else, which defeated the point of an at-a-glance status board. Doesn't reuse desktop's `unitTabsReplacement` dedup trick (below) for the same job here: `RentalCalendar.jsx` just renders with `showUnitTabs={false}` and `showUnitHeader={false}` (no tab strip, no `$/mo` header — both redundant once Overview's cards, always visible above it, already show price and double as the unit-switcher via the same `selectedUnitId`/`onSelectUnit` `RentalsView.jsx` already threads through both). Overview and Calendar don't need to be visually nested for that to work — they just need to read the same state, which they already did even before this change. `.rental-calendar-toolbar .rental-overview-list`'s horizontal-row override (below) is desktop-toolbar-specific and deliberately not reused here; forcing Overview's multi-line cards into that row at 375px would squeeze them.

Only `.rental-month-grid` itself used to be width-capped (`max-width: 420px`) at the `min-width: 900px` breakpoint, before the dashboard replaced that whole layout at that breakpoint — this went through two worse attempts first, kept here since the reasoning still explains today's `.rental-unit-tabs` styling (below), which still matters on mobile. Capping `.rental-calendar` (toolbar + grid together) fixed the grid's day cells (`aspect-ratio: 1`) stretching into oversized squares, but also squeezed the unit-tabs row down to the same narrow width, wrapping the four unit tabs onto two rows instead of sitting side by side. Capping the whole `.tab-panel` instead (verified via `getComputedStyle` to genuinely apply) avoided that, but with no centering it sat flush against the left edge of the wide desktop content area, and centering it just shrank everything uniformly, reintroducing the unit-tab wrapping. Capping only the grid let the toolbar above it use the full desktop content width instead. `.rental-unit-tabs` itself (`showUnitTabs`'s `true` default) is no longer what mobile Rentals actually renders — see Mobile above — but the styling stays defined and this history stays accurate for it, since `RentalCalendar.jsx` still supports rendering that way and defaults to it for any future caller that doesn't opt out.

**Calendar** (`RentalCalendar.jsx`): shows one unit at a time — a row of unit tabs (`.rental-unit-tabs`, one click to switch — a `<select>` dropdown originally, replaced because it took a scroll-and-choose on every switch) is the default, but both current callers opt out of it (`showUnitTabs={false}`) and switch some other way instead: on mobile, tapping an Overview card (see Mobile above); on desktop, switched externally (see dashboard above) — rendering a standard 7-column month grid — not a multi-unit Gantt-style timeline, which an earlier version tried and had to be scrapped (it needed a wider modal, which fought the mobile CSS reset and broke the layout on phones). `check_out` on `rental_bookings` is the *last occupied day, inclusive* — not a hotel-style departure day — so a single-day booking has `check_out = check_in`.

One booking may contain multiple tenants for the same unit and date range. `rental_bookings.guest_names` is a `text[]` structured list edited through repeatable Tenant fields in `RentalBookingForm.jsx`; `guest_name` remains a joined display/compatibility value so older clients and pre-migration deployments continue to work. Multiple tenants are deliberately one booking—not overlapping bookings—because they share one reservation, occupancy window, and charge schedule. `bookingGuestNames()`/`bookingGuestLabel()` in `rentals.js` are the single normalization/display path. The month grid uses `repeat(7, minmax(0, 1fr))` and day cells have `min-width: 0`; plain `1fr` lets a long tenant label become the track's intrinsic minimum and inflate the entire calendar into oversized blocks. Existing deployments need the incremental `guest_names` block in `supabase/schema.sql`; frontend reads and writes fall back to legacy `guest_name` until it is run.

`.rental-unit-tabs` is `display: grid; grid-template-columns: repeat(auto-fit, minmax(120px, 1fr))`, not `flex-wrap` — auto-fit packs as many equal-width 120px+ columns as actually fit, settling into a neat 2x2 grid instead of flex-wrap's old behavior of stretching each *wrapped* tab to the full row width, stacking 4 heavy full-width bars. It's also forced to `flex-basis: 100%` within `.rental-calendar-toolbar` so it always gets the full toolbar width to compute columns from, rather than sharing a row with "+ Add booking" and wrapping unevenly depending on how much space that left over; "+ Add booking" drops to its own line below instead. Below `max-width: 899px` (i.e. whenever this toolbar can render at all, since the desktop dashboard suppresses it entirely) it shrinks further still — smaller `minmax()` floor, tighter padding, smaller font/dot — "as small as this can reasonably go," since there's no wide-screen case left to keep it legible for.

A multi-day booking bridges the grid's 4px gap between its own consecutive days via an inline `boxShadow` (`-4px 0 0 0 ${unit.color}` / `4px 0 0 0 ${unit.color}` on the connecting side(s), computed as `connectsLeft`/`connectsRight` by checking whether the row-adjacent day is occupied by the *same* booking id) rather than rendering as a checkerboard of separate same-colored tiles — box-shadow is a pure paint effect, so it can't shift the day number or resize the cell the way a padding/margin trick would. Deliberately scoped to within a row only (same as `isStart`/`isEnd`'s existing `col === 0`/`col === 6` edge cases) — a booking spanning a week boundary still breaks into a separate bar per row, since two grid rows can't visually connect anyway.

The guest's name is printed on the bar itself (`.rental-month-day-guest`, truncated with an ellipsis if it doesn't fit), not just left in the `title`/`aria-label` tooltip — reused `isStart` for exactly where to (re)print it, since it already means "the real check-in day, or the first column of a row this booking is only continuing into," which is precisely where a real calendar app would repeat an event's title too. `.rental-month-day-occupied` switched from centering a single item to a small flex column (day number + optional name stacked) to make room — harmless on every other occupied cell in the bar, which only ever has the one child (the day number) and still centers exactly as before.

Bookings carry a `status` (`pending`/`confirmed`): a pending request (e.g. an inbound Airbnb inquiry) still blocks the unit's dates against a double-booking and renders as a diagonal-striped cell instead of a solid one, but never counts toward revenue until explicitly confirmed.

`.tab-panel`'s section gap bumps from 12px to 16px under `max-width: 480px` — a global change (every tab, not just Rentals), motivated by Rentals specifically: its Calendar tab stacks the most sections of any tab (heading, period-tabs, month nav, unit tabs, price line, then the grid), and 12px read as cramped once all of those piled up tightly on a narrow phone screen.

**Financials** (`RentalFinancials.jsx`): revenue is recognized by upfront charge cycle, not by calendar-day occupancy. `chargeDatesForBooking()` in `src/lib/rentals.js` models rent as paid every month on check-in's own calendar day-of-month (security-deposit/Airbnb-style upfront payment) — a guest who checked in May 30 bills on the 30th of every following month, not "30 days later" repeatedly, which would drift the billing day earlier across shorter months (`addCalendarMonths()`, always computed from the original check-in rather than the previous cycle, so a short-month rollover can't compound). A guest who checked in Aug 15 doesn't generate a second month of "revenue" just for still being there in September. A later cycle only counts if there's an actual day of stay left beyond it — a booking checking out on exactly its next billing day doesn't get billed twice for that trailing day. A charge date also only counts once it's actually arrived (`isBillableCharge()`) — a unit whose next cycle starts later this month doesn't show as billed for it while browsing the current month, before that day has actually happened. That unit's "Occupied, no charge yet" badge names the actual upcoming date and amount instead of leaving it a bare status (`upcomingChargeByProperty`, the soonest charge date across every confirmed booking touching that property this month that hasn't arrived yet) — this covers a current tenant's own next cycle and an already-booked replacement tenant's move-in charge (back-to-back turnover) the same way, showing whichever lands first regardless of which booking it belongs to.

Every unit row in the Units list also gets a second line combining the tenant chain with "Available {date}[ – {until}]" (`nextAvailability()` in `rentals.js`), e.g. "Abdul · Available Sep 26" or, for a back-to-back turnover, "Abdul → Ian · Available Dec 13" — one sub-line, not two, so naming tenants doesn't cost more vertical space than the availability line already added on its own. Three needs converged here: eyeballing a unit's checkout date wasn't enough to answer "can I actually book someone new here" once the household's 30-day minimum stay (`MIN_STAY_DAYS`) is factored in (a checkout doesn't mean bookable if another confirmed stay already starts too soon after); the primary badge text alone didn't say who was actually renting; and once a unit had two back-to-back tenants queued, the date alone jumped from "occupied by Abdul" straight to a date months out with nothing explaining why — reported as looking arbitrary/wrong even though the date itself was already correct. `nextAvailability()` now returns `blocking`, the ordered list of every tenant actually stood in the way (not just the first), alongside walking forward through every future *confirmed* booking (a pending request doesn't block — it isn't guaranteed, and treating it as blocking would understate real availability) looking for the first gap of at least 30 days, skipping past any booking that doesn't leave enough room; only shows an `until` date when that gap is itself capped by a specific future booking, otherwise it's open-ended — `until` is that booking's check-in *minus one day*, the last actually-free day (same "inclusive last day" convention `check_out` already uses elsewhere), not the check-in date itself, which reported as showing an already-occupied day as if it were still available before this was caught. Needs the *unscoped* booking set, not the month-limited `bookings` this component otherwise uses (a blocking booking, or the actual current tenant, can be outside the browsed month) — `RentalsView.jsx` already fetches that separately for `RentalOverview.jsx` (`upcomingBookings`), passed to `RentalFinancials.jsx` as `allBookings` rather than duplicating the query. The primary badge itself dropped "no charge yet" down to just "Occupied" once the tenant chain below already implies occupancy — spelling it out twice was the single longest, most-likely-to-wrap badge in the list for no added information.

`paid_charges` (`rental_bookings`, a plain jsonb array of `'YYYY-MM-DD'` charge dates — same "doesn't need a child table" reasoning as `checklist`) is the one manual override to the otherwise fully date-driven revenue calc: `isBillableCharge()` counts a charge as billed once its date has *either* actually arrived *or* been added to this array, closing the "tenant paid in advance" case the pure schedule can't represent on its own. Two entry points reach the same `setChargePaid()` in `rentals.js`, both scoped to one specific upcoming charge rather than a general per-date payment history/toggle: a "Mark paid" button on a Financials `occupiedNoCharge` row's own availability line (targets whichever booking generates that property's next charge), and a "Mark {date} paid" action in `RentalBookingDetail.jsx`'s own modal (targets that specific booking's own soonest unpaid future charge — `chargeDatesForBooking()` filtered to `> todayDateStr()` and not already in `paid_charges`, hidden entirely on a pending request since it can't be paid in advance for something that might still be declined, and hidden once nothing future is left unpaid). No manual refetch after marking, either way: `rental_bookings` is already on `RentalsView.jsx`'s Realtime channel, so the write alone moves the unit from `occupiedNoCharge` into `billed` on the next tick.

**Overview** (`RentalOverview.jsx`): all units at a glance — one status line per unit, "Occupied through {date} — {guest}" or "Vacant" (with the next upcoming booking's start date *and guest name*, if any — the name was computed by `unitOccupancyStatus()` from the start but silently dropped by the JSX until an audit caught it, since "who" is exactly the detail a glance is for). Deliberately a plain list, not a grid, for the same reason the Calendar tab isn't a multi-unit timeline. Backed by `fetchUpcomingRentalBookings()`/`unitOccupancyStatus()` in `src/lib/rentals.js`, a separate query from the Calendar tab's month-scoped `bookings` (`check_out >= today`, no upper bound) — otherwise a unit occupied past the currently-browsed month's end would show a truncated or missing through-date.

Two contexts share this same component: mobile's Overview tab (its own vertical list, default card-row styling) and the desktop dashboard's `RentalCalendar` toolbar (rendered inline with "+ Add booking" via `unitTabsReplacement` — see Rentals above), which overrides `.rental-overview-list` to a fixed two-per-row wrapping layout via a `.rental-calendar-toolbar` ancestor selector rather than a component prop. Two earlier dashboard versions had a `compact` prop here (no card border, tighter spacing) — first for Overview as its own sidebar column, later for its own section below the calendar — both reasons stopped applying once it moved into the toolbar, so the prop was removed outright rather than left unused. Each row shows the unit's price now (`p.monthly_rent`) alongside its status. `selectedUnitId`/`onSelectUnit`, when passed, make each row a `<button>` (a plain `<div>` otherwise) and highlight the active unit — in the desktop toolbar this is the *only* way to switch units now that the plain unit-tabs are hidden there, a low-cost bonus on mobile too (tapping a unit there primes which one the Calendar tab opens to next).

The unit-card header is a constrained flex row: the colored dot and unit name may shrink (the name truncates with its full value in `title`), while the monthly rate is `flex-none` and pinned to the far right at the same vertical level. Status/tenant text is limited to two lines with an ellipsis and `overflow-wrap: anywhere`, also retaining the full text in `title`; this prevents long names from changing card width or making one card in the desktop pair disproportionately tall. Only the status line reserves right-side room for the vertically-centered negotiation control—the header does not—so the rate can genuinely reach the card's right edge without colliding with that control.

**Negotiating mark**: `rental_properties.in_negotiation` (boolean, default `false`) is a quick per-unit flag for "there's a promising prospective tenant / an active back-and-forth on this unit right now" — not tied to any specific booking row, since a negotiation usually predates a confirmed booking existing at all. Displayed as "In talks" (not the column's own "negotiation" naming, which stays internal-only). One element serves as both the control and the display — `.rental-negotiating-toggle`, a `<button>` living *inside* `.rental-overview-item`, absolutely positioned against it (`top: 50%` + `translateY(-50%)`, pinned to the right edge) rather than sitting in the card's normal top-to-bottom flow: a small 🤝-only circle at rest, growing into a filled-amber "🤝 In talks" pill once on. Positioning it against the card as a whole (not inline in the text flow) means toggling it never adds a line or changes the card's height, regardless of whether the status text below happens to wrap to one line or two; `.rental-overview-item` reserves `padding-right: 84px` (restated in the desktop toolbar's own compact override, which would otherwise silently reset it via its own shorthand `padding`) so the toggle never overlaps the name/price/status text at either width. Amber `#e0a83e` rather than the app's usual accent gold, so it doesn't read as the same thing as `.rental-overview-item-selected`'s own accent border on the same card.

Nesting a real `<button>` inside the card is exactly why `.rental-overview-item` is a `<div role="button" tabIndex={0} onKeyDown={...}>` in `RentalOverview.jsx` rather than a real `<button>` — a `<button>` can't validly contain another interactive control, which is also why the toggle's own `onClick` calls `e.stopPropagation()` first, so a tap on it doesn't also fire the card's own select-unit handler. `onToggleNegotiating`, when passed, shows the toggle in *both* contexts (unlike `onEditUnit`, mobile-only) — the mark is meant to be settable wherever the unit list renders. `setUnitNegotiating()` (`src/lib/rentals.js`) just writes the column and lets `RentalsView.jsx` explicitly `reloadProperties()` afterward for a snappy click rather than waiting on the `rentals-changes` realtime round-trip (same pattern `archiveRentalProperty` already relies on for its own refresh). Since `schema.sql` is applied once to a fresh project (see Commands above) rather than tracked as incremental migrations, adding this column to an *existing* live database needs a manual `alter table rental_properties add column in_negotiation boolean not null default false;` run once in the Supabase SQL editor — editing `schema.sql` alone doesn't retroactively touch a database that already exists.

**Savings goals** (`rental_savings_goal`): `saved_amount` is a plain, manually-edited number — not derived from bookings. Two earlier attempts at auto-computing it from booking revenue (a raw cumulative sum, then a full per-month approve/edit reconciliation flow) both turned out to be more machinery than a two-person household actually wants; editing the total directly, in the goal's own edit form, replaced both.

**Turnover planning task:** a `confirmed` booking automatically gets a real Aaron-assigned task, "Schedule turnover cleaning for {unit}", due seven days before its `check_out` (10:00 AM Central — `((check_out - 7) + time '10:00') at time zone 'America/Chicago'`, so the household has a week's notice to actually line up a cleaner rather than finding out the day of). `tasks.rental_turnover_booking_id` (unique, FK to `rental_bookings` with `on delete cascade`) is the one-task-per-booking link; `sync_rental_turnover_task()` (`after insert or update of property_id, guest_name, check_out, status on rental_bookings`) upserts on that link via `on conflict (rental_turnover_booking_id) do update`, so editing a booking's checkout date or guest moves the existing task rather than creating a duplicate. A booking that stops being `confirmed` (still `pending`, or cancelled by whatever means the app allows) deletes its turnover task outright — there's nothing to plan a cleaning around for a booking that isn't actually happening. The generated task seeds one checklist item, "Add a task for when the cleaner will actually come" — this task is the planning reminder, not the cleaner's own appointment, which still needs to be scheduled as its own separate task once actually booked. `supabase/add-rental-turnover-tasks.sql` (see Recurrence above for this file's own "run once by hand" convention) both installs the trigger and backfills tasks for every already-confirmed, not-yet-checked-out booking at the time it's run.

**Short/Midterm vs. Long Term:** `rental_properties.term` (enum `short_midterm`/`long_term`, default `short_midterm`) is orthogonal to `company` — a unit picks both independently (Findlay is `awa` *and* `long_term`; the household's other Awa units are `awa` *and* `short_midterm`). Requested directly: a long-term unit's rent is fixed for the life of the lease and its income is static, so it doesn't need the same day-to-day vacancy monitoring a short/midterm room does, and mixing the two on one calendar-first dashboard buried that distinction. `RentalsView.jsx` gets a second-level pill toggle (`rentalTerm` state, `PeriodTabs`/`PeriodTab` — the same shared capsule Day/Week/Month and Pins/Inbox already use) defaulting to Short/Midterm, since that's the side that actually needs checking; `rental_bookings` has no `term` of its own, same as it has no `company` of its own — both are inherited through `property_id`, so filtering `properties` to one term before handing it to `RentalCalendar`/`RentalOverview`/`RentalFinancials` is enough to scope everything downstream (each of those already buckets purely off its own `properties` prop). The unit auto-selected on load is scoped to short/midterm units specifically, not just `properties[0]` — Findlay's $2,000/mo sorts first among Awa's units (`fetchRentalProperties` orders by `monthly_rent` desc), so without this a long-term unit could end up "selected" for a calendar/edit-unit button that can never actually show it.

Picking Long Term swaps the whole dashboard for `RentalLongTermView.jsx` — not a filtered copy of the same layout, a genuinely different shape, since a month calendar has nothing useful to say about a fixed-rent year lease. Each unit renders as a lease card: current tenant (a booking whose `check_in` is still in the future doesn't count as "current," same as `unitOccupancyStatus()` elsewhere), a progress bar from `check_in` to `check_out`, and a "N months, N days remaining" caption via `monthsAndDaysBetween()`/`formatMonthsAndDays()` (`rentals.js`) — calendar-accurate (real month/day arithmetic, like an age counter), not a flat days-divided-by-30 approximation. A dashed "+ Add a long-term unit" card closes the list, and `RentalPropertyForm.jsx`'s new Term field defaults from whichever tab was active when "+ Add unit" was tapped (`defaultTerm` prop) — same "scope a new thing to whatever tab you're already on" reasoning the company picker already established for a brand-new unit's `company`.

**Long-term lease reminders** (`notify-reminders`, checks 4 & 5): the one place in Rentals nobody checks day to day, so a lease running out has to surface on its own. Two one-shot columns on `rental_bookings` (`last_month_reminder_sent_at`/`turnover_reminder_sent_at`, timestamps rather than the rent-cycle reminder's *date* — each fires exactly once per booking, not once per recurring cycle) gate two independent pings, both to both members:
- **Last month** fires once `check_out` is within one calendar month of today — compared as pure month integers (`monthIndex()`, `year*12+month`), not a day-preserving offset like `addCalendarMonths()`. That distinction matters: a day-preserving "one month before check_out" calculation hits the exact same day-of-month-doesn't-exist-in-the-shorter-month overflow `addCalendarMonths()` already documents for monthly recurring tasks (verified while building this — a Mar 31 check_out's day-preserving anchor overflowed into March itself, well past the point of being a month's notice). Comparing bare calendar months instead sidesteps it entirely: Jul 1, Jul 20, and Jul 31 check-outs all get the identical "last month" anchor of June, with no day component to overflow.
- **Turnover in one week** fires once `check_out` is 7 days out, and branches on whether a **confirmed** booking already starts on/after this one's own `check_out` for the same property — a pending inquiry doesn't count as "already lined up" (it isn't a sure thing yet), so that case still gets the plain tenant-search nudge. When one is confirmed, the message instead points at the household's existing turnover-cleaning task (see Turnover planning task above) — that task already gets created automatically for every confirmed booking regardless of term, so nothing new has to be built there; the notification just makes sure a rarely-checked long-term unit's turnover doesn't go unnoticed the way the task alone would risk.

## Password vault

**One shared vault, per-entry sharing** — `vaults` (`id`, `name`, `private_entries`) plus `vault_access` (`vault_id`, `member_id`) replaced a single global `vault_meta` row (it used to be enforced by a literal unique index on a constant expression). This was originally built as *two* vaults — a second, healthcare-scoped one with its own separate master password, for a third member (a household VA) who shouldn't see the original vault's contents — but that shipped and was then deliberately reverted the same day: a second master password for Ada to remember turned out to be more cost than the actual goal needed, once it was clear the real requirement (let a new member see only specific credentials, not everything) was already exactly what `vault_entries.shared_with` does *within* one vault, not something that required a second one. The `vaults`/`vault_access` architecture itself stayed — a future vault with a genuine reason to carry its own separate master password is still just a new row away — but today there is exactly one (`'Household'`), with every member's access (including the VA's) granted against that same one. `permissions.vault` (the old blanket on/off flag) is retired entirely — `vault_access` subsumes it (zero `vault_access` rows is exactly as blocked as `permissions.vault: false` used to be). Granting/revoking vault access is SQL-editor-only for now, same precedent `is_admin` promotion already established for a privileged action with no admin UI yet. `has_vault_access(vault_id)`/`vault_has_private_entries(vault_id)` (schema.sql) are `security definer`/plain `stable` helpers respectively, mirroring `is_member()`'s own reasoning — a raw `exists (select from vault_access ...)` inline in `vault_access`'s own SELECT policy would recurse into itself.

`VaultView.jsx` (also off the "+" speed-dial) stores credentials encrypted client-side — AES-GCM, key derived via PBKDF2 from a **shared** master password (known to every member with vault access) — before anything reaches Supabase. RLS on `vault_meta`/`vault_entries` governs who can read/write ciphertext, but it is *not* the security boundary for the passwords themselves; the encryption is, so a leaked service-role key or an RLS mistake only exposes unreadable ciphertext. The derived key lives only in React component state, never persisted to localStorage/sessionStorage, so it has to be re-entered every time the vault is reopened. `VaultView.jsx` still supports a `PeriodTabs` picker at the top of the modal for a member with access to 2+ vaults — unused today with only one vault in play, but left in place rather than ripped out, since it's exactly what a future second vault (one that genuinely needs its own separate master password) would need again with zero frontend changes.

**Per-entry privacy, not per-vault.** Every vault — in practice, the one — has `private_entries = true`: a new entry defaults to visible only to its creator, with an explicit "Share with: [checkboxes]" section in `VaultEntryForm.jsx` (rendered whenever the active vault is private) to grant specific other vault members read access. This is the real, deliberate behavior change from before the healthcare-vault work: Ada and Aaron's own entries used to be automatically mutual with no extra step; now every entry — anyone's — starts private to its creator and needs an explicit share to become visible to someone else, the same rule a third member now gets too. A one-time migration backfilled every entry that existed before this change with `shared_with` set to whoever already had vault access at the time (preserving exactly who could already see what), so nothing already saved silently disappeared — only entries created *after* the migration actually start private. Sharing grants visibility, not co-ownership — matching `cork_notes`' own "the other member can see it, not manage it" rule, edit/delete on a shared entry stays creator-only, both server-side (the RLS policies) and client-side (`VaultEntryDetail.jsx`'s `canManage` hides Edit/Delete/folder-move for anyone else, though the real enforcement is the RLS). `vaults.private_entries` staying a per-vault flag (rather than this being hardcoded true everywhere) is what would let a future vault opt back into the old fully-mutual, zero-extra-step behavior, if one ever needed to.

**Changing who an existing entry is shared with doesn't require re-opening Edit.** `VaultEntryDetail.jsx`'s "Shared" row gets its own small inline "Edit" action (creator-only, same `canManage` gate as Delete/Edit) that swaps the plain name list for an `AssigneePicker` (the same toggle-pill multi-select `TaskForm.jsx`/`TaskClarifications.jsx`'s own "Notify" picker use) plus Save/Cancel — adjusting access to an already-saved password shouldn't mean reviewing and re-saving the label/username/password/notes just to add or remove one person. `updateVaultEntrySharing()` (`lib/vault.js`) is a focused single-column update, deliberately separate from `updateVaultEntry()` — `shared_with` is a plain, unencrypted column (see the "Shared" row's own display), so changing it needs no decrypt/re-encrypt round trip the way every other field does. The parent (`VaultView.jsx`'s `handleShareChanged`) patches `entries`/`selectedEntry` directly in local state after a successful save rather than re-fetching and re-decrypting the whole list through `loadEntries()` — nothing else about the entry changed, so there's nothing else worth re-deriving.

The modal itself (`.vault-modal`, desktop only, `min-width: 641px`) gets a fixed `width`/`height` instead of the shared `.submission-modal` default of sizing to content — same fix, and the same reasoning, as `.how-to-guide-modal` (see UI structure below): the entry list grows with however many entries/folders exist, and folder accordions resize the card's content on top of that, which without this made the whole card visibly grow, shrink, and jump around while just navigating it. A fixed box scrolls its overflow internally (inherited from the shared `.submission-modal` rule's `overflow-y: auto`) instead. Below that breakpoint it's still a content-sized slide-up sheet like every other mobile modal.

There is no password-reset path by design — if the master password is forgotten, the only way out is "Reset vault" (wipes `vault_meta` and all `vault_entries`), gated behind typing a confirmation word rather than a plain `window.confirm`. That's the first typed-confirmation pattern in this codebase; the only other place it's used is the CSV export, since that's the one action that undoes the vault's whole security guarantee (it downloads every password as an unencrypted file).

**One-time codes (TOTP).** An entry can carry `totp: { secret, algorithm, digits, period }` — the base32 setup key a site shows when you turn on an authenticator app (the standard SHA1 / 6 digits / 30s are the defaults). It lives **inside the encrypted entry payload** like every other field, so there is no schema change, per-entry sharing applies unchanged (anyone an entry is shared with can generate its codes — that is the point for shared business accounts, and the form's help text tells people to keep their most sensitive accounts in their own authenticator app), and it is absent (not null) when unset. `lib/totp.js` implements RFC 6238 with Web Crypto (HMAC-SHA1/256/512; checked against all the RFC's published test vectors) and parses either a bare key or an `otpauth://` link, rejecting anything unsupported in plain language. `VaultEntryForm.jsx` validates as you type and shows a live code to compare against the site; `VaultEntryDetail.jsx` renders `TotpCode.jsx` (grouped digits, a countdown bar, Copy gives the plain digits). The CSV export adds an "Authenticator Link" column holding a standard `otpauth://` link, so leaving Tandem never strands a key. **Clock check.** Codes come from the device's clock in UTC seconds, so time *zones* never matter, but a clock that is set by hand or has drifted makes sites reject the code with no other sign. `lib/clockCheck.js` measures the device's offset from real time using the `Date` header of a same-origin `HEAD /manifest.json` (compensated by half the round trip, and `Age`); Supabase's own replies cannot be used because a browser hides the `Date` header on cross-site responses and Supabase does not expose it. `TotpCode.jsx` shows a warning when the device is 10+ seconds off, and says nothing if the measurement fails (offline, no header). It warns only — it does not silently shift the codes. It relies on the service worker having no `fetch` handler (true today); adding one that caches `/manifest.json` would make this report false skew. Precision is one second, so this is for "off by tens of seconds", not fine tuning.

**Any code that rebuilds an entry's payload from a fixed field list must carry `totp` through** — `saveEntryFolder()` in `VaultView.jsx` does, and without that a folder rename or move would silently wipe the key.

An entry's `loginMethod` field (e.g. "Google") is set instead of a password for accounts with no password of their own ("Sign in with Google") — `VaultEntryDetail.jsx` shows "Sign in via {loginMethod}" instead of a blank, confusing password row when it's set.

**Folders**: an optional `folder` field on each entry groups the list in `VaultView.jsx`, collapsible per folder, same shape as `EodReportsList.jsx`'s month groups (own `.vault-folder*` classes, not shared ones — the two features aren't otherwise related). Folders aren't their own stored entity — there's no folder table/row, just this string tag per entry — so the full set in play is always *derived* fresh from whatever's actually on entries right now (`distinctFolders()` in `VaultView.jsx`), seeded with `VAULT_FOLDERS`' two defaults (`lib/vault.js` — currently `'Awa Rentalz'`/`'Azu Rentals'`, for per-unit door-lock codes and the like) so the create form's suggestions aren't empty on a brand-new vault. `folder` lives *inside* the encrypted entry payload, not as its own database column — every entry is already fully decrypted client-side on every load, so grouping by a field inside that payload needed no schema change and doesn't leak which entries belong to which folder to anyone without the master password, unlike a plaintext column would have. An entry with no folder (or an old one predating this feature) falls into a catch-all "General" group, which never gets rename/delete controls of its own since nobody created it. The grouped/collapsible UI only replaces the plain flat list once there are actually 2+ groups present — a vault where nobody's used folders yet still looks exactly as before, no empty-group clutter. Every folder starts collapsed, and `loadEntries()` never resets that — the vault is a modal (`.submission-modal`), which sizes itself to content (same reasoning as the How-to guide's own fixed-size override), so a folder springing open again on every entry save/rename/move made the whole card visibly grow and shrink out from under whatever you were doing. Collapsed by default, left exactly as the user leaves it across reloads.

Creating a folder is just typing a new name — `VaultEntryForm.jsx`'s Folder field is a free-text `<input>` with a `<datalist>` of existing names as suggestions, not a fixed `<select>`, so there's no separate "new folder" action and no way to pre-create an empty one (a folder only exists for as long as at least one entry is tagged with it). Renaming/removing a folder (the ✎/× actions beside each header in `VaultView.jsx`, inline-swapping the header for a text input while renaming, same idea `CorkBoardView.jsx` uses for editing a pin in place) bulk-rewrites every entry currently tagged with the old name, since there's no single folder row to update — `handleRenameFolder`/`handleDeleteFolder` both funnel through one `saveEntryFolder(entry, folder)` primitive that re-encrypts one entry with a new folder value. Renaming to a name that already matches a different existing folder just merges the two — nothing extra to reconcile, since grouping is re-derived fresh afterward either way. "Removing" a folder only clears the tag on its entries (back to General); it never deletes the entries themselves. `VaultEntryDetail.jsx` also gets a quick per-entry "Folder" `<select>` (existing folder names only, not free text — creating a new one is reserved for the full Edit form) so an entry can be moved into a folder without opening the whole edit form, useful for sorting entries that predate this feature one at a time.

## Working status

`members.working_since` — nullable `timestamptz`, doubling as the on/off flag (`is`/`is not` null) and giving "working since 2:15 PM" for free with no separate boolean that could drift out of sync. `members.working_status` (enum `member_working_status`: `available`/`busy`/`in_meeting`, null while offline) and `members.working_status_until` (nullable expiry — null means "until changed") layer availability on top, per `/Users/aaron/.claude/plans/multi-member-permissions.md`'s design. Switching between the three states never touches `working_since`, so a session's actual start time survives a status change.

An earlier version of this feature gave every member an identical on/off toggle, which read fine for exactly two people but left the mobile header with no room to grow once the nudge and settings icons needed the same row (reported broken on a real phone) — `WorkingStatusToggle.jsx` is now permission-gated instead: `members.permissions.workingStatus` (deny-list, same shape as `rentals`/`vault`/`staff`/`reports` — see Members, permissions, and task access above; off for Ada, on by default for everyone else) decides who gets the real toggle at all. A permitted, online member gets the familiar one-tap Online/Offline pill (unchanged interaction) plus a small chevron `IconButton` that opens a status sheet — an anchored popover, the exact same shape `TaskBoard.jsx`'s nudge dropdown already established (`relative` anchor, a full-viewport click-catcher `div` for outside-click dismissal, `absolute right-0 top-full` panel) rather than a new CSS pattern. Inside: `PeriodTabs`/`PeriodTab` for Available/Busy/In a meeting, and — only while not Available — three small buttons (30 min / 1 hour / Until changed) that set `working_status_until` relative to now. A non-permitted member (Ada) instead gets one compact "N working" / muted "Nobody working" pill in the same footprint, opening the same sheet minus the personal section. Either way, the team list inside the sheet (every *other* member's live status, "since"/"until" times) is what "I'm working" scales to as the team grows — not a growing row of individual badges.

**Effective status is always computed, never read raw**: `effectiveStatus(member, now)` in `WorkingStatusToggle.jsx` treats a `busy`/`in_meeting` row as `available` once `working_status_until` has passed, comparing against a `now` state ticked locally every 60s (same "don't trust a value that can silently go stale while the tab sits idle" reasoning `TaskBoard.jsx`'s own `displayToday` tick already established for the day-rollover fix). This runs on every viewer's own client, including the member's own — so an expiry stays correct even if whoever it belongs to has their browser closed or asleep past it, with no cron job or server-side revert needed. The stored value can sit "stale" in the database indefinitely; nothing about correctness depends on it ever being corrected there.

Permission enforcement for `workingStatus` is UI-only, a known and accepted gap (same class as `reports`): the existing `"members can update own working status"` RLS policy is a plain self-row check with no column restriction (it already covers `default_timezone` too), so a real server-side gate would need the same trigger-guard machinery `permissions`/`is_admin` got — more than this cosmetic feature currently justifies. Team-status visibility has no `task_access`-style restriction either — every member can see every other member's status; presence is treated as low-sensitivity, unlike task content.

## Completion submissions

The task's existing composer now switches between **Comment** and **Completion details** after the task is done (`TaskClarifications.jsx`, wired by `TaskRow.jsx`). Done selects completion mode; discussion and completion drafts/attachments remain separate. Save completion details persists `completion_note` and `completion_attachments` in one task update with `throwOnError: true`, retaining drafts on failure and guarding repeat clicks. Saved details render inline with Edit details; the old Submit/Edit submission modal is removed. View submission remains available. Attachment uploads stage private references locally until Save; removing a reference is staged until Save and Cancel edit restores the saved list. No required submission fields, schema migration or new notification behavior.

Optional per-task proof-of-completion: `completion_note` (text) + `completion_attachments` (`jsonb` array of `{url, name}`, same "doesn't need a child table" reasoning as `checklist`). Any file type is accepted, not just images — `isImageAttachment()` in `src/lib/attachments.js` checks the filename extension to decide between an inline `<img>` preview and a plain download link.

**Attachments are private, not a public bucket** — a task hidden from a member via `task_access` used to still be readable through its attachment's direct public URL, since Storage privacy was never tied to task-level access. `uploadCompletionAttachment()` returns a `storage://task-attachments/{path}` reference instead of a public URL (the `{taskId}-{uuid}.{ext}` object name is unchanged in shape, just no longer `Date.now()`-based — `{ upsert: true }` is gone too, since a random-uuid path can't collide the way a same-millisecond timestamp could). `attachmentPath()` resolves either that reference or an old public-URL string (a one-time-format migration shim for already-stored JSON — `completion_attachments`/`clarifications`/`eod_reports.attachments` are jsonb with no FK, so old rows keep their public-URL string until something rewrites them). `downloadAttachment()` fetches the file through the signed-in Storage client, cached/deduped by reference (module-level `Map`) so the same attachment rendered twice at once, or remounted seconds apart — closing "View submission" and opening "Edit submission" — doesn't re-fetch the full body each time. `PrivateAttachment.jsx` is the one component every attachment now renders through (`AttachmentList.jsx`, `TaskRow.jsx`) — it downloads on mount, builds a `blob:` object URL, and revokes it ~30s after the component stops using it (not immediately, to survive a file link opened `target="_blank"` in a new tab that hasn't finished resolving the blob yet).

`can_access_task_attachment(object_name, writing)` (schema.sql) backs all four `storage.objects` policies on the bucket, parsing the task id out of the object name's `{uuid}-` prefix (via a `safe_uuid()` helper, so a malformed/foreign name degrades to "no match" instead of throwing, and the lookup compares as uuid — not `tasks.id::text` — so it can use `tasks_pkey`'s index instead of a sequential scan) and checking `can_view_task`/`can_update_task` on it. Read access has one broader path: an object also passes if it's referenced in an `eod_reports.attachments` entry the caller can actually read (`submitted_by = auth.uid() or has_report_access(submitted_by)` — see End-of-day reports below for `report_access`, which replaced reports' old flat `is_member()` mutual visibility) — without this, a report a member could fully read could still have an unopenable attachment if they lacked a `task_access` grant on the specific task it came from; the `report_access` condition on top of that is what stops the reverse case, an attachment staying openable to someone who can no longer (or never could) read the report it came from. Delete additionally allows removing an attachment whose owning task was hard-deleted (not just `archived`) — without that, a task's attachments become permanently orphaned (unreadable and undeletable by anyone, including whoever uploaded them) the moment the task itself is gone, since the task lookup that every other policy depends on no longer resolves.

Not a fully general design — authorization is inferred from the upload naming convention (`uploadCompletionAttachment` is the only thing enforcing it), not a real ownership row, so a member with write access to a task could still write/delete an object matching `{that task's id}-anything.ext` even if it's not actually linked from that task's own attachment array. Accepted for now (bounded to members who already have task-level access) rather than building a dedicated `task_attachments` ownership table.

## Task clarifications

`tasks.clarifications` — a lightweight comment/question thread per task (`jsonb` array, `{ id, askedBy, question, answer, notifyIds, askedAt, answeredBy, answeredAt, resolved, resolvedBy, resolvedAt }`), same "doesn't need a child table" reasoning as `checklist`/`completion_attachments`. Despite the field names it covers comments and suggestions too, not just literal questions — the UI copy is deliberately generic ("Ask a question or leave a comment…") since a common case (e.g. Ada commenting on a task Aaron self-assigned) isn't a question at all.

Both the "Send" button (asking, `TaskClarifications.jsx`) and "Reply" (answering, `AnswerRow` in the same file) only render once their textarea/attachments actually hold something — not just disabled-while-empty. `.clarification-ask-button` used to always render, disabled, sitting right next to the task's own Edit/Delete/Duplicate row (`extraActions`, to its left in `.clarification-compose-left`) — an easy misclick target when reaching for one of those instead, and the actual cause of a reported "can't mark a task done" bug (a stray tap landed on the always-there Send button, not the checkbox).

Notifications go through `manual-notify` (direct invoke), not the `notify-task-events` webhook — asking/answering is a discrete user action like the nudge button, not a row-diff the webhook would need to detect. **Who gets pinged is an explicit choice, not "everyone but the caller."** That was the original behavior (and still is for `eod_report`, a genuine whole-team broadcast) but stopped fitting once a third member (the healthcare VA) joined — a comment aimed at her would otherwise also push Ada, who has nothing to do with it. `TaskClarifications.jsx` now shows a "Notify" picker (`AssigneePicker`, the same toggle-pill multi-select `TaskForm.jsx` uses for assignees) next to the compose box, visible only once there's actually a message to send — same visibility condition as the Send/Reply button beside it. It defaults to the task's own other assignees (the people it already concerns), falling back to every other member only when there's nobody else assigned to default to, but is fully adjustable before sending. The chosen ids are saved on the entry itself as `notifyIds` and sent to `manual-notify` as `clarification_asked`'s target list; a reply (`AnswerRow`) defaults its own picker to `notifyIds` *plus the asker explicitly*, minus whoever's replying. The explicit asker union matters and isn't optional: `notifyIds` is the asker's own chosen audience, which by construction never includes the asker themselves — a reply computed as a plain `notifyIds.filter(id => id !== meId)` silently drops to empty (the common single-target case, the asker tagged only the one person now replying) or lands on the wrong person entirely (a multi-target case, the reply notifies whoever else was tagged instead of the actual asker). Caught via real use during RC's onboarding — replies in both directions were landing on nobody or the wrong person — not by review. `manual-notify/index.ts`'s `resolveNotifyIds()` re-validates the list server-side (real members, never the caller) — not a trust concern, same reasoning `nudge`'s `targetId` already established — and falls back to the old broadcast-to-everyone only when `notifyIds` is missing entirely (an older cached frontend that predates this field), so a deploy-order gap between the Edge Function and the frontend can't silently drop every recipient. `TaskRow.jsx` shows a 💬 badge on the collapsed row when there's an unanswered, unresolved message directed at the current viewer (via `getInboxItems`'s existing assignee-scoping, untouched by this — see Inbox below), an in-app reminder that doesn't depend on the push notification having been seen.

Not every entry is actually a question — a plain FYI comment has nothing to answer, so `resolved` lets the recipient dismiss it ("No reply needed" in `TaskClarifications.jsx`, or the same action inline from the Inbox tab) without writing an `answer`. `resolved`/`answer` are mutually exclusive in practice (an entry only ever gets one or the other), and once either is set the entry stops counting as pending anywhere (the 💬 badge, `getInboxItems`'s `question` bucket). Resolving is deliberately quiet — no push notification, unlike asking/answering — since dismissing something as not needing a reply isn't news worth pinging over.

## Inbox

A persistent tab (`InboxView.jsx`) aggregating clarification activity across every task, not just whichever ones happen to be visible in the currently-browsed day/week/month — the only way to notice a stray question before this was stumbling onto that specific task's 💬 badge. Originally scoped to clarifications only, not a general activity feed (assignment/completion pings and the person-level 👋 nudge are still push-notification-only, unchanged) — but a **Submissions** section, and later a **Nudges** section (both below), widened that on purpose, once the exact same discoverability gap turned out to apply to completion submissions and task-level 🔔 nudges too.

**Every section is scoped to tasks you're actually assigned to, not just tasks you can view.** This wasn't true from the start — `getCompletedSubmissions()`/`getNudgedTasks()` were originally built "mutually visible to everyone," a reasonable shortcut back when every member saw every task. Once `task_access` made read-only visibility a real, common relationship (a healthcare VA granted View-only into Aaron's or Ada's tasks), that shortcut turned into a real bug: a member with mere View access to someone else's tasks got every question/submission/nudge on those tasks dumped into their own Inbox, not just things actually concerning them — caught for real testing a fresh member account, whose Inbox showed the admin's questions/submissions/nudges despite having no assignment relationship to any of it. `getInboxItems()`/`getCompletedSubmissions(tasks, meId)`/`getNudgedTasks(tasks, meId)` all now filter to `task.assignee_ids.includes(meId)` first — a task merely visible to you still shows its own full activity when you open it directly, this only narrows what surfaces unprompted in your Inbox. `memberNudges` gets the same treatment inline in `InboxView.jsx` (filtered to `sender_id === meId || target_id === meId`), since a person-level 👋 nudge concerns exactly two people and nobody else.

Not self-fetching like `CorkBoardView.jsx`/`EodReportsList.jsx` — `fetchTasks()` already loads every task with no date filter, and `TaskBoard.jsx` keeps that array live via its existing `tasks-changes` Realtime channel, so `InboxView` just receives `tasks` as a prop and derives everything from data already in memory (`getInboxItems()` in `tasks.js`) rather than duplicating a fetch/channel. Four sections, in priority order: **New** (unanswered, unresolved questions directed at you — self-clearing, same condition as the 💬 badge; labeled "Needs your reply" until it was shortened to "New"), **Resolved** (your own questions that got closed out — merges the `answer`/`finished` item kinds from `getInboxItems()` into one UI section, re-sorted by date since they no longer need `INBOX_KIND_ORDER`'s kind-then-date grouping once shown together; splitting "got an actual reply" from "dismissed with No reply needed" into separate tabs was a finer distinction than the tab row needed to make, both already being the lowest-priority, closer-to-an-archive kind of item), **Submissions** (see below), and **Nudges** (see below). Resolved/Submissions/Nudges show full history, not just recent activity — a resolved conversation, a submission, or a nudge shouldn't age out of findability just because it happened a while ago, since neither `clarifications` nor completed/nudged tasks are ever pruned.

An All/New/Resolved/Submissions/Nudges `.period-tabs` row (`view` state, same reused markup `EodReportsList.jsx`'s own period filter and Bulk Add's Add/Edit toggle already use) narrows the list down to one section at a time — added once several sections stacked together read as one long undifferentiated scroll on a normal day. "All" (the default) keeps the original always-everything-visible behavior; the other four hide every section except their own, showing a small "nothing here yet" message instead of just going blank when that section is empty. Doesn't touch `getInboxItems()`/`getCompletedSubmissions()`/`getNudgedTasks()` or any of the read/unread logic below — `view` is purely which already-computed sections get rendered, not a second data fetch.

**Submissions**: tasks with a `completion_note`/`completion_attachments` — the same "only way to notice was stumbling onto the task itself" problem clarifications had, just for proof-of-completion instead of comments. `getCompletedSubmissions(tasks, meId)` in `tasks.js` filters to tasks `meId` is assigned to (see the Inbox intro above) that are also `status === 'done'` and actually carry a submission (not every completed task — a plain checked-off task with nothing attached isn't "waiting to be found," it's just done), sorted newest-first by `completed_at`. Rendered by a separate `SubmissionItem` (not the shared `InboxItem` used by the clarification sections above), since a submission is keyed by task rather than by clarification and has no per-item resolve/read-state concept of its own — clicking one just peeks the task, same as every other Inbox item. Doesn't participate in the unread-badge logic below (`hasUnseenInboxItems`) — completion already has its own push notification, so this section is for *browsing/finding* a submission later, not surfacing an urgent unread count, same reasoning the merged-in **Finished** items above already don't count toward the badge either.

**Nudges**: merges two different kinds into one time-sorted list, not just the task-level one — `member_nudges` (a new table: `sender_id`/`target_id`/`created_at`, RLS is `is_member()` read-only for clients, the **only** insert path is `manual-notify`'s `nudge` branch writing through its service-role client, same as how the task-level kind below is stamped) is the person-level 👋 header nudge's history, which used to be a pure fire-and-forget push with nothing persisted anywhere; and tasks whose `overdue_nudge_sent_at` is set is the task-level 🔔 nudge button (see Push notifications above). `InboxView.jsx` builds `nudgeEvents` by combining `getNudgedTasks(tasks, meId)` with the `memberNudges` prop (`fetchMemberNudges()` in `src/lib/nudges.js` still fetches full history — the same broad fetch-then-narrow shape `fetchTasks()` already uses — filtered inline here to `sender_id === meId || target_id === meId`) into one array sorted by whichever timestamp each event carries, rendering each through the existing `NudgeItem` (task-level) or a new `PersonNudgeItem` (`"{sender} nudged {target}"`, no badge — there's no assignee to badge a person-level event by, and it's not clickable — no task to peek into). Neither kind participates in `hasUnseenInboxItems`, same reasoning as before: both already fired their own push notification, so this section is for browsing history, not an urgent count. `member_nudges` needed its own Realtime channel (`member-nudges-changes` in `TaskBoard.jsx`, same refetch-the-whole-table shape as `tasks-changes`/`members-changes`) and its own one-time `alter publication supabase_realtime add table member_nudges;` — see the Realtime note under Architecture. Task-level nudges are still badged by `task.assignee_ids` (`assigneeBadge`) rather than sender, unchanged — the column carries no separate "who nudged" of its own to badge by.

Read/unread for **Answered** is tracked client-side only — `localStorage` (`inbox-last-viewed-at`), not a database column, since adding a field to the shared `clarifications` jsonb for this would mean touching an already-race-prone read-modify-write column just to track something purely local to one viewer's one device. `TaskBoard.jsx` owns reading/bumping this value (on entering the tab) so the same value can drive both the nav badge (an unseen-answer dot on the Inbox nav item, shared markup so it renders on mobile's bottom bar and desktop's header-folded nav alike) and `InboxView`'s per-item styling, without either needing to poll the other. Needs-your-reply and Finished don't need this tracking — both are inherently self-clearing the moment their state changes (answered/resolved), the same reasoning the 💬 badge already relies on. (Answered and Finished now share a UI section, **Resolved** — this per-`kind` distinction is still what the badge and per-item read styling key off internally, unaffected by that merge.)

Clicking an Inbox item reuses `TaskBoard.jsx`'s existing "peek" mechanism (`peekTaskId` → a `Modal` with `<TaskRow defaultOpen>`) to jump straight to that task's expanded detail regardless of which day it's on — no separate deep-linking was built for this.

## Cork Board

`cork_notes` — quick pins with no due date and no timeline, the opposite of a task, which is deliberately scheduled. This is the **one place in the app where visibility isn't automatically mutual**: every other table uses `is_member()` alone for its select policy (mutual visibility is the whole point of this app — see What this app is), but `cork_notes`' select policy is `is_member() and (auth.uid() = any(shared_with) or author_id = auth.uid())`. A pin defaults to private (`shared_with = '{}'`); sharing it with specific members is an explicit picker in the compose form (`CorkBoardView.jsx`), not the default. `shared_with` (`uuid[]`) replaced an original plain `shared boolean` — a 2-person-app leftover meaning "visible to literally every member," which stopped making sense once `task_access` made targeted, asymmetric visibility a real concept elsewhere in the schema; there's no "shared with everyone" sentinel, sharing with the whole team just means checking every box. Only the author can edit, archive, or delete their own pin, even once shared — a targeted member can see it, not manage it; editing (`startEdit`/`handleSaveEdit` in `CorkBoardView.jsx`) swaps the pin's body into an inline textarea in place, same shape as the compose form. Sharing itself is its own small anchored popover per pin (`sharingId`/`sharingDraft` state in `CorkBoardView.jsx`, same `relative` anchor + full-viewport click-catcher + `absolute` panel shape `TaskBoard.jsx`'s own nudge picker already established) — a checkbox per other member plus an explicit Save, not a one-tap toggle, since picking specific people needs a multi-select instead of a single flip. No push notification fires on posting, sharing, editing, or archiving; it's a scratchpad, not an assignment.

**Archiving:** `cork_notes.archived` (boolean, default `false`) — the everyday way to get a finished pin off the active board, replacing what "Unpin" used to do. Soft-disable, not delete, same reasoning `rental_properties`/`work_sites` already establish elsewhere in this schema — an archived pin (and its comments) still exists, just tucked into its own collapsed "Archived (N)" section at the bottom of the board (`archivedOpen` state, collapsed by default, same "collapsed until you go looking" reasoning `VaultView.jsx`'s own folders use) rather than sitting on the active list. Goes through the plain author-only `update` RLS policy, same as editing or sharing — `handleArchive(note, archived)` in `CorkBoardView.jsx` just flips the column via `updateCorkNote()`, no confirmation needed either direction since it's fully reversible. An archived pin's own list item is deliberately lighter-weight than an active one — no comment thread, no Focus Today, no Edit — just the body, author/date, shared badge, and Unarchive/Delete, since interacting further with it means unarchiving it first. Real deletion (`handleDelete`, still gated behind a native `confirm()`) is kept around specifically for an already-archived pin, not removed outright — archiving is the reversible everyday action, delete is the deliberate, still-available last step once something's fully done with. Since `schema.sql` is applied once to a fresh project rather than tracked as incremental migrations, adding this column to an *existing* live database needs the same manual one-time `alter table cork_notes add column archived boolean not null default false;` every other additive schema change in this app needs.

**Comments**: a flat, append-only `comments` jsonb array per pin (`{ id, authorId, body, createdAt }`) — no reply-to-reply nesting, same "doesn't need a child table" reasoning as `checklist`/task `clarifications`. Unlike the pin's own body/sharing, comments are meant to come from *any* targeted member once a pin is shared (an evolving back-and-forth, not something only the author manages) — but the plain `update` RLS policy is deliberately author-only, so a comment write goes through `add_cork_note_comment()` instead, a `security definer` Postgres function that re-checks visibility inline (`auth.uid() = any(shared_with) or author_id = auth.uid()`) and only ever touches the `comments` column, never `body`/`shared_with` — it can't be used as a backdoor around the author-only edit restriction. Same silent-by-design reasoning as the pin itself: no push notification on a new comment, unlike task clarifications' ask/answer.

Self-contained like `RentalsView.jsx`/`EodReportsList.jsx` (fetches its own data, no props from `TaskBoard.jsx` besides `me`/`memberName`), but unlike those two it also subscribes to a `cork-notes-changes` Realtime channel — the board is meant to update live as either person pins something, same reasoning as the `tasks-changes`/`members-changes` channels in `TaskBoard.jsx`. **`cork_notes` must be added to the `supabase_realtime` publication by hand** (`alter publication supabase_realtime add table cork_notes;` in the Supabase SQL editor) — see the Realtime note under Architecture; this is not run automatically by `schema.sql`.

**Focus today**: any pin (own or shared-from-the-other-person — visibility already gates which pins render at all, so no extra check here) can be promoted into a real task via `handleFocusToday()`, which mirrors `PrioritiesForm.jsx`'s day-period logic exactly (`title` = the pin's body, `due_date` today at 23:59 local so it can go overdue like any other task, not an All Day task). Assigned to whoever does the promoting (`assignee_ids: [me.id]`), not the pin's original author — claiming it is the point, and for a shared pin the promoter is often the other person. Promoting doesn't unpin or otherwise touch the original note; `promoted`/`promotingId` are transient component state only (not persisted), so the button reverts to "Focus today" on reload — re-promoting just creates another task, which is an accepted low-stakes edge case rather than something guarded against.

Any comments already on the pin carry over as checklist items on the new task — a comment on a pin is a thought/follow-up that would otherwise be stranded on the pin once nobody's looking at it any more. Built in the same shape `ChecklistEditor.jsx` constructs by hand (`id`/`text`/`done`/`blocked`/`blockedReason`), so they're editable normally right away, and each item is prefixed with its author's name (via the same `memberName` prop already used to render the pin's own comment list) since a shared pin can carry thoughts from both people and a bare checklist would otherwise lose that attribution.

**Projects (roadmap pins with milestones):** requested directly, for tracking a new multi-step initiative (e.g. a new side business) without either dumping the whole plan into one giant note or splitting it into N separate pins by hand. A roadmap pin is still just a `cork_notes` row — `roadmap_items` (jsonb array of `{ id, text, milestone, taskId }`, see its own migration comment in `schema.sql`) is non-empty, nothing else distinguishes it — but it's routed to its own **Projects** section of Board (see `BoardView.jsx` below) rather than sitting mixed into ordinary quick notes, since browsing "what am I actively building" and "what did I jot down" are different questions. `CorkBoardView.jsx` takes a `mode` prop (`'pins'` default, or `'projects'`) that both screens share one component for: `isRoadmapPin(note)` (`roadmap_items?.length > 0`) filters `notes` so a pin renders in exactly one of the two sections, never both, and the compose form itself branches on `mode` — Projects' form always shows the roadmap-steps textarea (Pins' never does), with its own copy ("Project name or goal…", "Create project").

A `## Heading` line in the compose form's roadmap textarea groups every following step under that milestone until the next `##` line (`parseRoadmapDraft()`) — a step typed before any heading gets `milestone: null` and renders with no header, the plain pre-milestone shape. `groupRoadmapItems()` turns the flat array back into `{ milestone, items }` runs for rendering (consecutive same-milestone items only, matching how the parser actually produces the array — never a full regroup-by-value pass). A milestone with a name gets a header (`"{name}"` + `"{doneCount} of {total} done"`) and a progress bar (same `bg-gradient-to-r from-accent to-accent-h` fill `RentalLongTermView.jsx`'s lease-progress bar already established, reused here for the same "meter" visual language rather than inventing a second one).

A step's "Add to timeline" button opens an inline date input (defaulting to today, but genuinely modifiable — not hardcoded) before creating the real task, closing the original gap where every promoted step landed on today regardless of when it was actually due. Confirming calls `handleAddRoadmapItem(note, item, dateStr)` — `addRoadmapItemTask()` invokes the atomic `add_roadmap_item_task` RPC (migration `supabase/add-roadmap-task-atomic.sql`, applied October 6; function body and execute permissions independently confirmed live). It locks the owner’s active pin, creates a self-assigned task and stores the step link in one transaction; a retry returns the existing task ID. It is security invoker and retains existing RLS. Shared viewers cannot schedule another member’s project steps under the current owner-only update rule; the existing visible button returns a clear permission message instead of creating an orphan task. From that point on, a step's "done" state is read live off its linked task's own `status` (`taskById.get(item.taskId)?.status === 'done'`, `taskById` a `Map` built once per `tasks` prop change) — not a second flag tracked on the item — so ticking the real task off on the timeline is what marks the milestone step done, with nothing here to fall out of sync. `tasks` is threaded into `CorkBoardView.jsx` the same way `InboxView.jsx` already receives it (a prop, not a second fetch/Realtime channel — `TaskBoard.jsx`'s existing `tasks-changes` channel is already the live source of truth). A `taskId` that no longer resolves in `taskById` (the linked task was hard-deleted, not just archived — an archived task still resolves fine) falls back to a bare "Added" label rather than a due date that no longer exists.

A project's steps are editable after creation, not just its title — caught directly (editing only ever wrote `body`, inherited unchanged from before milestones existed, so Edit on a project silently offered no way to touch its steps at all). `startEdit()` seeds a second draft, `editRoadmapDraft`, via `serializeRoadmapItems()` (the inverse of `parseRoadmapDraft()` — reconstructs the same `## Heading` / step-per-line text the compose form teaches, blank line between groups for readability only, the parser doesn't need it) whenever the pin is a roadmap pin; the edit form shows that textarea alongside the title one only then. Saving can't just re-parse the edited draft cold the way the compose form does — every re-parsed line gets a fresh `id` and `taskId: null`, which would silently unlink any step already added to the timeline. `reconcileRoadmapItems(oldItems, newItems)` fixes this: it matches each freshly-parsed line against the stored items by exact trimmed text (not milestone, not position — moving a step to a different milestone or reordering it isn't a replacement) and carries over the matched item's real `id`/`taskId`, consuming each old item at most once so duplicate-text lines pair up one-to-one rather than both claiming the same link. A line whose wording changed, or a genuinely new line, gets treated as a fresh step with no link — same as it would from the compose form.

**Quick "+ Add subtask," a collapsed "Completed · N," and undo-on-remove** close the three gaps left when Projects first shipped as a markdown-paste editor rather than the originally-proposed living checklist (`/Users/aaron/.claude/plans/multi-member-permissions.md`'s "Board projects" section). Requested directly once real use made re-opening the full Edit textarea just to add one more line feel like too much ceremony. The per-step `<li>` (icon-and-status row shared by both an open and a completed step) is its own `RoadmapItemRow` component now, rendered from two different lists instead of one straight `.map()` over `group.items`: `openItems` (not done) render inline as before, `doneItems` collapse behind a "Completed · N" toggle (`openCompletedGroups`, a `Set` of `"noteId:milestone"` keys, collapsed by default — same "collapsed until you go looking" reasoning `VaultView.jsx`'s own folders and the Archived section already use) so a long-running project doesn't grow a wall of struck-through text. "+ Add subtask" is a small link below each project's items (author-only, `isOwn`-gated — the underlying `cork_notes` UPDATE policy is author-only regardless, so this isn't just UX consistency) that opens an inline text input on click rather than sitting always-open; submitting appends the new step to whatever milestone the *last* existing step belongs to ("add another step to what I'm currently working on" is the common case — a step meant for a different or brand-new milestone still needs the full Edit textarea) and leaves the input open afterward rather than closing it, so adding several steps in a row doesn't mean reopening it each time. Removing a step (the small × next to an unscheduled one — a step already linked to a real task can't be removed this way, since doing so would silently orphan the task rather than the two staying in sync; deleting the task itself from Timeline is the real removal path at that point) persists immediately, same as every other edit here, but stays undoable for `REMOVE_UNDO_MS` (8s) via a small inline banner — Undo just re-inserts and re-saves rather than holding anything back client-side, so there's no unsaved state a reload could lose, and letting the window lapse (or navigating away) simply forfeits the undo rather than promising a true transactional rollback.

**Archive a task to the board:** requested directly — closes the exact gap `tasks.archived`'s own migration comment flagged when it shipped (no view/restore UI, undoing an archive meant a direct database edit). `cork_notes.archived_task_id` (nullable, `on delete set null`) links a pin to the task it came from. `TaskRow.jsx`'s "Send to board" action (any task, not just overdue ones — a `Pin` icon in the same `extraActions` row as Edit/Duplicate/Delete) and the Overdue modal's own bulk "Archive" action both now go through `archiveTaskToBoard(task, authorId)` (`corkNotes.js`) instead of a plain `updateTask(id, { archived: true })` — two plain sequential writes (create the pin, then archive the task), not a transaction, same reasoning every other multi-step member action in this app already accepts (e.g. `StaffWorkSitesForm.jsx`'s `updateWorkSite` + `assignRentalPropertiesToWorkSite`). The pin is created private (`shared_with: []`, the same default any new pin gets) with the task's title as its body, and lands on the **active** board, not tucked into the collapsed Archived section — the whole point is staying easy to find, not getting buried the way an ordinary finished pin would be. **The task's content comes along as pin comments** (`taskCommentsForPin()` in `src/lib/taskToPin.js`, a pure function; `createCorkNote` takes an optional `comments` array so the pin is inserted with them in one write, no SQL): one first comment from the sender holding the task's notes, where it came from, checklist (☑ done, ☐ open, ✕ blocked with its reason) and completion details, then every question and every reply from the task's comment thread as its own comment, in order, keeping the original author and time. A file on a comment or on the completion details cannot be copied (pin comments are text only), so the line `Attachment: name (still on the original task)` is written instead. Nothing on the task is touched beyond `archived`, so Restore to Today returns it intact. Comments added on the pin afterward stay on the pin and do not flow back to the task. Pins archived before this change were not back-filled.

A task-linked pin gets **Restore to Today** in place of Focus Today — Focus Today would create a second, detail-stripped duplicate of a task that already exists (just archived), rather than actually bringing the original back. `restoreArchivedTask(pin)` (`corkNotes.js`) un-archives that exact task (checklist/notes/clarifications/everything intact, since the row itself was never touched beyond the `archived` flag) and archives the pin in the same motion, since the pin's one job — holding the restore point — is done once the task is back; every other pin action (Edit/Share/Archive) still applies to it identically. Not author-gated, same as Focus Today already isn't — whoever can see the pin (own, or a member it's shared with) can restore it, so sharing a task-pin genuinely means "any of us can bring this back," not just "you can see that I archived something." A pin whose linked task was later hard-deleted outright (not just archived) has `archived_task_id` go `null` via the column's own `on delete set null`; `CorkBoardView.jsx` only ever shows the Restore button while it's still set, so a pin degrades into an ordinary note rather than offering a restore that can't work.

## Property manager / staff time tracking

A third kind of Tandem account — a house/property manager with GPS-confirmed clock-in/out for payroll — sits *alongside* the `members` model (now N members, not just Ada/Aaron — see Members, permissions, and task access above) rather than inside it. Full design rationale (why this couldn't just be a third `members` row, what was deliberately deferred) is in the original plan, `/Users/aaron/.claude/plans/shimmering-fluttering-dusk.md`; this section covers what actually shipped.

**Not a `members` row.** `members` grants full mutual read/write on everything (tasks, rentals, the vault) — a property manager must never get that. Instead they're a separate `staff` table (`id` → `auth.users`, `display_name`, `hourly_rate`/`emergency_rate` numeric, `active` boolean) with its own `is_staff()` RLS function, mirroring `is_member()`'s shape but additionally checking `active` so deactivating someone revokes access immediately rather than just "stops being invited to shifts." `staff` has two SELECT policies OR'd together: members read the whole roster (for the admin dashboard's name/rate display), and a staff account can always read its own row *regardless of `active`* — deliberately not gated through `is_staff()`, so a deactivated account gets a clear "your access has been paused" screen client-side instead of an ambiguous RLS-denied empty result.

**Routing:** `src/lib/useAccountRole.js` runs two independent existence checks (`members`/`staff`, both keyed to `session.user.id`) once a session exists, resolving to `'loading' | 'member' | 'staff' | 'blocked'`. This is load-bearing, not optional — `TaskBoard.jsx` derives `me` as `members.find(...)` and every downstream use is only `me?.`-guarded, not "member not found"-guarded, so a staff session reaching `TaskBoard` would silently render the full shell with every RLS-gated fetch quietly coming back empty rather than an actual error. `App.jsx` branches on the role after the existing `authError`/`loading`/`!session` checks: `'member'` → `TaskBoard` (unchanged), `'staff'` → `StaffClockView`, `'blocked'` → an inline "this account isn't set up in Tandem yet" screen with just a sign-out button. `'blocked'` covers both "recognized by neither table" and a deactivated staff row with one state, since either way there's a real message to show instead of a half-working screen.

**Work sites and geofencing.** `work_sites` (`name`, `address`, `latitude`/`longitude` as `double precision`, `geofence_radius_m` default 100, nullable `rental_property_id` FK back to `rental_properties` for a site that's also an existing Awa Rentalz unit, `active`) is the first structured-geo table in this schema — `rental_properties.address` elsewhere is free text with no coordinates. `haversine_distance_m(lat1, lng1, lat2, lng2)` is a plain SQL function (not inlined into the trigger below) specifically so it's independently testable via `select haversine_distance_m(...)` in the SQL editor; `src/lib/geo.js`'s `haversineDistanceM()` is a second, client-side implementation of the exact same formula — **deliberately duplicated, not shared**, because the two serve different trust levels: the client copy (via `findNearestSite()`) only ever drives instant "you're 42m from Sunset Ave" UI feedback before a clock-in is submitted, while the server copy recomputes `distance_from_site_m`/`flagged` from the *stored* coordinates as the sole source of truth. Neither one makes the underlying GPS reading itself more trustworthy (an inherent limit of browser geolocation either way), but the server recompute means the flag Ada/Aaron see on the dashboard can never be spoofed independently of the coordinates sitting right next to it.

**`time_entries`** — one row per shift. `rate_amount` is stamped server-side at clock-in from `staff.hourly_rate`/`emergency_rate`, never re-read live off `staff` at query time: if a rate is edited later, past entries must not silently reprice, and a raw client insert can't set its own rate either way. `distance_from_site_m`/`flagged` are stamped the same way, from the stored `clock_in_lat`/`clock_in_lng` vs. the work site's coordinates. All three are enforced server-side by the `stamp_time_entry_meta()` trigger (`before insert`, `security definer`) — it unconditionally overwrites whatever a client insert supplied for those columns, so they're effectively read-only from the client's perspective even though no column-level privilege literally blocks writing them. `time_entries_one_active_per_staff` (a partial unique index, `where clock_out_at is null`) stops a lost/duplicate Start tap — or two tabs — from opening two simultaneous shifts for the same person.

**Clock-out is RPC-only.** There is **no UPDATE RLS policy for staff on `time_entries` at all** — a raw UPDATE grant would let a staff account rewrite `status`/`approved_by`/`rate_type`/`rate_amount` after the fact, so instead the only mutation path is `staff_clock_out(p_entry_id, p_lat, p_lng)`, a `security definer` RPC (mirroring `add_cork_note_comment()`'s shape) that re-checks `staff_id = auth.uid() and clock_out_at is null` inline and only ever touches `clock_out_at`/`clock_out_lat`/`clock_out_lng`, returning the updated row directly so the client doesn't need a follow-up select. `p_lat`/`p_lng` default `null` — a bad GPS fix at the *end* of a shift shouldn't trap someone unable to clock out, unlike clock-in, where coordinates are mandatory. `src/lib/staff.js`'s `clockOut()` just wraps this RPC; `clockIn()` is a plain insert (RLS: `staff_id = auth.uid() and is_staff()`), since the trigger above is what actually locks down the columns that matter.

**Manual one-time step, not code:** `alter publication supabase_realtime add table time_entries;` and, since the on-site capture feature below, `alter publication supabase_realtime add table work_sites;` — both needed for `StaffLogsView.jsx`'s admin dashboard to live-update, same as every other Realtime table in this app (see the note under Architecture). `staff` still doesn't get this — it only ever changes via a member's own edit in this same dashboard, so an explicit reload right after that edit (`StaffLogsView.jsx` re-fetching after `setStaffActive`, same pattern `archiveRentalProperty` already uses) is enough. `work_sites` used to fall under that same reasoning too, until on-site capture gave staff their own independent write path onto it — see below for why that made the missing live-update a real, reported bug rather than a hypothetical one.

**Physical-location migration:** projects that already ran the original staff block must also run the final “Physical staff locations (incremental migration)” block in `supabase/schema.sql` once. It makes `work_sites.latitude`/`longitude` nullable, adds `rental_properties.work_site_id` plus its index, migrates any original singular `work_sites.rental_property_id` links, and strengthens `stamp_time_entry_meta()` to reject inactive/unconfigured locations before distance calculation. `fetchRentalProperties()` has a temporary missing-column fallback so the deployed Rentals/Staff views remain readable before that SQL is applied, but creating and linking a location group correctly requires the migration.

**`StaffClockView.jsx`** is the property manager's entire UI — deliberately one layout, not the `isDesktop` dual-tree split `RentalsView.jsx`/`TaskBoard.jsx` use elsewhere; a phone is the realistic primary device for this role, and there's nowhere near the structural complexity that justified that split for Rentals. Not-clocked-in state: tap Start → `getCurrentPosition()` (wrapped in a promise in `getPosition()`, the first use of the Geolocation API in this codebase, so no existing pattern to lean on) → `findNearestSite()` pre-selects a site with a manual `<select>` always available as an override (a bad fix or a legitimately-not-nearest site shouldn't pick the wrong property) → Standard/Emergency rate toggle → optional notes → Confirm. The site remains manually overridable, but a successful location reading is mandatory before Confirm enables because `time_entries.clock_in_lat`/`clock_in_lng` are deliberately non-null; a failed reading now leaves a clear retry action instead of letting the form submit null coordinates and surface a database constraint error. Start is also disabled with an explanatory message when no active work site exists. Clocked-in state: the selected site and rate, a locally-`setInterval`-ticked elapsed timer (no server round-trip needed to animate it), and a Stop button that attempts geolocation with an 8s timeout but falls through to a coordinate-less clock-out on any failure — the same "don't block stopping a shift over a flaky GPS fix" reasoning `staff_clock_out`'s nullable `p_lat`/`p_lng` already encodes server-side. Today/week pay summaries and a recent-history list (site/date, pay, approval, and any geofence flag) come from `computeEntryPay(entry)` (`src/lib/staff.js`) — hours × the `rate_amount` snapshotted at clock-in, computed on read and never stored, same "derive it, don't store it" reasoning `duration_minutes`-based end times and `chargeDatesForBooking()` already use elsewhere in this app; it returns `null` while still clocked in (no `clock_out_at` yet).

**Clock-in location management:** a `work_sites` row now means one physical place—Rachel, Parkside, or a future acquisition—not one rental unit and not one company. `rental_properties.work_site_id` is the many-units-to-one-location link: every unit belongs to at most one location, while a location may contain units from either company. `StaffLocationsManager.jsx` lists each physical location with its linked Awa/Azu units underneath and separately surfaces unassigned units; `StaffWorkSitesForm.jsx` creates/edits the group and uses a checkbox list to move units into it. Coordinates on `work_sites` are nullable after the incremental schema block: a group can be saved before its map point exists, but it is inserted inactive and therefore remains invisible to staff until configured. Status derives without another enum (`lat/lng null` = Needs setup; coordinates + active = Ready; coordinates + inactive = Inactive). The normal setup path is an explicit “Find clock-in point” address search through `searchUsAddresses()` in `src/lib/geocoding.js`, backed by OpenStreetMap Nominatim: search happens only on a member's click (no autocomplete/background traffic), is US-restricted, returns at most four candidates, and visibly attributes OpenStreetMap. Choosing a result copies its canonical address and coordinates into the form. Latitude/longitude, the current-device fallback, and the 150m radius remain available under collapsed “Advanced clock-in details,” keeping technical geo fields out of the everyday setup flow. The original singular `work_sites.rental_property_id` remains only as legacy compatibility; the migration copies any old link into `rental_properties.work_site_id`, and new code no longer writes it. Archiving a location stays a soft-disable so past `time_entries` remain intact.

**On-site GPS capture with member approval:** the fallback for when address lookup can't place a location accurately. Five nullable columns on `work_sites` (`pending_latitude`/`pending_longitude`/`pending_accuracy_m`/`pending_captured_by`/`pending_captured_at`) — not a child table, since a site has at most one live geofence point regardless of how many capture attempts led to it, so resubmitting before approval just overwrites the previous attempt rather than needing a history to reconcile (same "pending state on the row itself" shape `rental_bookings.status`/`time_entries.status` already use). Staff still has zero direct write RLS on `work_sites` — the only path is `staff_submit_location_capture(p_work_site_id, p_lat, p_lng, p_accuracy_m)`, a `security definer` RPC mirroring `staff_clock_out()`'s shape exactly: it re-checks `is_staff()` and that the site is still genuinely unconfigured (`not active and latitude is null and longitude is null`) inline, and only ever touches the four `pending_*` columns. A third `work_sites` SELECT policy (`is_staff() and not active and latitude is null and longitude is null`) lets staff see — never write — a needs-setup or already-pending site; an archived site that used to be ready (`active = false` *with* real coordinates) still correctly stays invisible to staff, unchanged from before this feature. `workSiteStatus()` (`src/lib/staff.js`) is the single 4-state classifier (`ready`/`pendingApproval`/`needsSetup`/`inactive`) both `StaffLocationsManager.jsx`'s badge and `StaffLogsView.jsx`'s summary counts read, so the two views can't drift apart on what a pending capture means.

`StaffClockView.jsx`'s "Set up a location" card (shown whenever any site is `needsSetup` or `pendingApproval`) is where a staff account taps "Capture location" (or "Recapture," once a capture already exists) — reuses the same `getPosition()` promise-wrapped geolocation call the Start flow already has, then calls `submitWorkSiteLocationCapture()`. Approving or discarding is a plain member-side `work_sites` update, not an RPC (members already hold unrestricted UPDATE RLS there) — `StaffWorkSitesForm.jsx` shows an "On-site capture awaiting approval" banner (captured-by name, timestamp, accuracy) with "Approve as clock-in point"/"Discard" buttons whenever `site.pending_latitude`/`pending_longitude` are set; approving copies the pending point into the real `latitude`/`longitude`, activates the site, and clears all four `pending_*` fields, discarding just clears them, leaving the site at Needs setup exactly as if nothing had been captured. Setting real coordinates any other way (address search, the manual advanced-details fields) also clears a stale pending capture, so an old "captured by X" banner can't resurface if coordinates are ever cleared again later.

Real-world gap found via a live report (a capture that succeeded on the property manager's phone never showed as pending on Ada/Aaron's side): staff's capture is a `work_sites` write that happens entirely outside any member action, so `StaffLogsView.jsx` needs the same live-refresh treatment `time_entries` already has, not just a fetch on mount — see the Realtime publication note above and `StaffLogsView.jsx`'s own `staff-work-sites-changes` channel. The same gap existed in the other direction too: a member's approve/discard is itself a `work_sites` write outside anything the pmanager's own screen does, so `StaffClockView.jsx` mirrors it with its own `staff-clock-work-sites-changes` channel (`reloadSites()`, split out of `loadAll()` so a live capture/approval update doesn't also re-run the unrelated profile/active-entry/history fetches or disturb in-flight Start-flow state).

**`StaffLogsView.jsx`** is the admin dashboard, reached through `TaskBoard.jsx`'s own staff tab exactly like every other tab — no extra visibility gating needed, since `TaskBoard` is now only ever reached by `role === 'member'` sessions and both Ada and Aaron already see every tab equally. Self-contained like `RentalsView.jsx`/`CorkBoardView.jsx` (fetches its own data, just `me` as a prop) rather than wired through `TaskBoard`'s shared tasks channels, and subscribes to three independent Realtime channels — `staff-time-entries-changes`, `staff-work-sites-changes`, and `staff-time-entry-requests-changes` (hence the manual publication step above) — kept separate rather than merged into one, since they refetch different state (`reloadEntries()`/`reloadSites()`/`reloadRequests()`) and the time-entries one re-subscribes on every filter change while the other two deliberately don't (nothing about a capture/approval/correction-request depends on the status/period filters). Its status filter (`All`/`Pending`/`Approved`) reuses `PeriodTabs`/`PeriodTab`. The former raw “No time entries yet” line is now a guided onboarding card whose copy/action changes depending on whether any active clock-in location exists; both the top Locations action and the compact location summary open `StaffLocationsManager`. Rental fetching deliberately runs `fetchRentalProperties('awa')` and `fetchRentalProperties('azu')` in parallel and combines/sorts the results—Staff configuration must never silently omit the second company. The roster list supports editing name/rates through `StaffProfileForm.jsx`, plus Deactivate/Reactivate; changed rates only affect future clock-ins because every existing shift keeps its server-stamped `rate_amount`. Entry and roster cards use min-width-safe grid columns so long site/name/rate text cannot force the dashboard wider than a phone viewport.

**Adding a new property manager:** `staff.id` references `auth.users`, so creating one means creating a new Auth user first — a privileged operation the browser's anon-key client can never perform directly, unlike every other staff write in this app. `create-staff-account` is the second Edge Function invoked directly from the browser (alongside `manual-notify`), deployed the same way with `--no-verify-jwt` for the same preflight-has-no-Authorization-header reason — which means the caller-is-a-member check inside it (`supabaseAdmin.from('members').select('id').eq('id', user.id)`, using the service-role client to bypass RLS for the check itself) isn't optional the way it might look; it also requires the caller's **Staff permission** not to be turned off (`featureAllowed(memberRow, 'staff')` from `_shared/permissions.ts`, the same deny-list rule `has_permission()` uses), because a function holding the service-role key bypasses row-level security, so being a member alone would let someone with Staff access removed (for example the VA) create or reset staff logins by calling it directly (found in the Oct 8 2026 audit; `update-staff-credentials` has the same check); without it, `--no-verify-jwt` would let anyone with a network path to the URL create arbitrary staff accounts with a password of their own choosing. On success it calls `auth.admin.createUser()` (email `{username}@tandem.local`, same placeholder-domain convention every real login already uses) then inserts the `staff` row; if the `staff` insert fails, it deletes the just-created Auth user rather than leaving an orphan `useAccountRole.js` would classify `'blocked'` forever with no roster row to notice or fix it by. `StaffProfileForm.jsx` now covers both create (`staffMember` null — adds username/password fields, the latter with a "Generate" button reusing `generateStrongPassword()` from `vault.js`) and edit (`staffMember` set, unchanged), same `x ? edit : create` shape `StaffWorkSitesForm.jsx`/`StaffTimeEntryForm.jsx` already use. A create has no single updated row to hand back the way an edit's plain update does, so `StaffLogsView.jsx`'s `onSaved` branches on that — `null` means refetch the whole roster instead of splicing one row in.

**Optional emergency rate; job description:** `staff.emergency_rate` is nullable with no default (was `not null default 25`) — not every role actually works emergency shifts, and a nonzero number nobody meant to set was worse than an explicit "this role doesn't have one." `StaffProfileForm.jsx` exposes this as a "This role works emergency shifts" checkbox wrapping the Emergency rate field — unchecked submits `null`, not `0`. Every Standard/Emergency rate picker (`StaffClockView.jsx`'s Start flow, `StaffTimeEntryForm.jsx`'s manual-add flow) now renders the Emergency option only when the relevant staff row's `emergency_rate` is non-null, rather than disabling it — there's no reason to offer a choice that would just error. `stamp_time_entry_meta()` (schema.sql) enforces this server-side too, raising if a client attempts an `'emergency'` clock-in against a staff row with no emergency rate — belt-and-suspenders against a raw insert bypassing the UI's own gating. `staff.job_description`, also new, is unrelated free text bundled into the same migration only because both were requested together: set by a member in `StaffProfileForm.jsx`, shown read-only to the property manager on their own clock-in screen. That description renders through `MarkdownText.jsx` (a small `react-markdown` wrapper with element overrides matching Tandem's theme tokens) rather than plain text — a real job description pasted in as markdown (`##` headings, `*` bullets, `**bold**`) would otherwise show those characters literally. `react-markdown` renders to a real element tree, not `dangerouslySetInnerHTML`, so no separate sanitizer is needed; not that it would matter much here anyway, since `job_description` is only ever member-authored (`StaffProfileForm.jsx`), never staff-authored. Collapsed behind a small "Your role ›" pill (`StaffClockView.jsx`, `roleOpen` state) rather than always-open inline — a full job description is easily the tallest thing on this screen, and it isn't something checked every time the way Start/Stop or the pay summary are; tapping the pill opens it in a `Modal`/`ModalCard`, same as every other on-demand detail view elsewhere in the app.

**Staff login changes:** two independent additions — a property manager changing their own password, and a member changing a property manager's username and/or password on their behalf, the latter specifically to make account turnover to a new employee easy. `changeOwnPassword()` (`src/lib/staff.js`) is a direct `supabase.auth.updateUser({ password })` call, no Edge Function needed — GoTrue trusts the current session for changing its own password, unlike `create-staff-account`'s `auth.admin.createUser()`. `StaffChangePasswordForm.jsx` is a small modal reached from a "Change password" button next to Sign out in `StaffClockView.jsx`'s header — the property manager's only settings surface, since they never reach `SettingsMenu.jsx` (member-only).

A member's side needs `auth.admin.updateUserById()`, the same privileged-operation reasoning `create-staff-account` already establishes, so it's a third Edge Function, `update-staff-credentials` (also `--no-verify-jwt` for the same preflight-has-no-Authorization-header reason, also re-checking caller-is-a-member via the service-role client before doing anything). It takes an optional `newUsername` and an optional `newPassword` — at least one required — and confirms the target id is actually a `staff` row before calling `updateUserById`, without which a member could point it at their own or the other member's own account id and overwrite that login instead. A username change re-derives the same `{username}@tandem.local` placeholder-domain email every real login already uses (`toLoginEmail()` in `Login.jsx`) and passes `email_confirm: true`, same as account creation. Changing only the username (leaving password blank) is the actual turnover mechanism: it reassigns the same `staff` row — its rates, job description, and `time_entries` history — to a new person's login, rather than deactivating the old account and creating a fresh one and losing that continuity. `StaffCredentialsForm.jsx` is reached via a "Login" button on each `StaffLogsView.jsx` roster row, deliberately separate from `StaffProfileForm.jsx`'s own Edit (name/rates/cadence/job description) — changing either credential immediately changes how that person signs in, a different kind of action than editing profile fields, so it gets its own explicit button rather than being bundled into "Save changes." Both fields are write-only (there's no way to read back a staff account's current username — its `auth.users` row isn't queryable through the anon client — so unlike, say, `StaffProfileForm.jsx`'s rate fields, neither one is prefilled from the existing value); leaving a field blank leaves that credential unchanged. Reuses the same "share this with them directly — there's no email to send it to" convention `create-staff-account`'s own password field already established, and its own Generate button (`generateStrongPassword()` from `vault.js`).

**Manual time entries and correction requests:** members previously had no way to fix a shift's clock-in/out times, add one the property manager forgot to clock into at all, or even learn that either problem existed short of a side-channel message outside the app. `time_entries` gained a `"members can insert time entries"` policy (`with check (is_member())`) alongside its existing unrestricted UPDATE — `updateTimeEntryTimes()` (`src/lib/staff.js`) is a plain client update on `clock_in_at`/`clock_out_at`, same as `approveTimeEntry()`/`forceClockOutEntry()`; `clockOutAt: null` reopens a shift, and a conflicting reopen surfaces as a plain Postgres unique-violation from the existing `time_entries_one_active_per_staff` index rather than a special-cased check. `createManualTimeEntry()` covers the "never logged at all" case: `stamp_time_entry_meta()` still runs regardless of who inserts and still requires `clock_in_lat`/`clock_in_lng` not null, so a manual entry reuses the selected work site's own stored coordinates (there's no real GPS reading to attach to a shift nobody was actually present to clock into live) — this keeps `distance_from_site_m`/`flagged` meaningful (0m, not flagged) instead of nonsensical. A member-created entry is inserted already `approved` with `approved_by`/`approved_at` set, since creating it by hand already is the review. `StaffTimeEntryForm.jsx` is one component covering both cases (`entry` set = edit times only; `entry` null = full manual-add form with staff/site/rate pickers), same `site ? edit : create` shape `StaffWorkSitesForm.jsx` already uses. Members also gained an unrestricted DELETE policy on `time_entries` (`deleteTimeEntry()`) — the one verb missing after this, for a duplicate, a bogus manual add, or a mistaken clock-in — granted the same unconditional way as the existing SELECT/INSERT/UPDATE rather than scoped to unapproved-only, and gated by a plain `confirm()` on the client since it's irreversible, same convention `handleForceClockOut` already follows.

`time_entry_requests` is the request/notification trail, not the fix itself — a member still makes the actual correction by hand through the paths above. Its own table, not a jsonb column on `time_entries` like `checklist`/`clarifications` elsewhere in this schema: a request about a shift that was never logged has no natural row to live on, so `time_entry_id` is nullable rather than required. Staff gets a plain INSERT policy (`staff_id = auth.uid() and is_staff()`) rather than an RPC — unlike `staff_clock_out()`/`staff_submit_location_capture()`, there's no existing-row trust boundary to cross for inserting a brand-new row that's entirely the staff member's own; members get full read/update (resolving is a plain `status`/`resolved_by`/`resolved_at` update, deliberately silent — no push notification, same reasoning resolving a task clarification or a cork-note comment already establish). `StaffClockView.jsx` exposes one shared compose panel for both a per-shift "Something wrong with this shift?" link (only shown when that entry has no open request already, to avoid duplicate spam) and a standalone "Report a shift I forgot to clock in for" button not tied to any entry; both funnel into `submitTimeEntryRequest()` then a best-effort `sendTimeEntryCorrectionRequest()` push — best-effort because the request is already durably saved by the time the push fires, so a notification failure shouldn't read as the request itself having failed. `StaffLogsView.jsx` surfaces only *open* requests, in their own section that disappears entirely once none are open (unlike Clock-in locations, which is always shown) — resolved requests still exist in the database, there's just no browsing UI for them yet.

`manual-notify` (the Edge Function) gained a `time_entry_correction_request` kind that's the one call in that function a **staff** account makes, not a member — every other kind assumes the caller is a real member and targets other members from `fetchAllMembers()`, which is meaningless here (the caller isn't in that table at all), so this branch notifies every member unconditionally and resolves the caller's own `display_name` via the service-role client instead (staff can't be looked up through `fetchAllMembers()`, which only ever queries `members`).

**Break/geofence-exit clock-out flow and shift reports:** Stop no longer clocks out immediately — it opens a choice between "Taking a break" and "Clocking out for now." Break is deliberately *not* a new schema concept: by product decision it's just an ordinary clock-out followed by an ordinary clock-in later, auto-tagged with `"(Break — will resume shortly)"` (via `submitShiftReport()`, below) so the resulting gap in the day reads as deliberate rather than unexplained. Choosing "Clocking out" instead moves to a second step — an optional "What did you work on?" textarea; Stop must never be blocked on this, so an empty report still finishes clocking out normally. Both paths share one `runClockOut()` core (unchanged from the original `staff_clock_out()` RPC call) and differ only in what happens around it.

Because a break is really two separate rows with no shared state between them, the on-screen elapsed timer would otherwise reset to zero every time a new shift starts — reported directly as feeling wrong. Fixed as a pure display concern, no schema change: `priorTodayMs` sums every one of today's already-*closed* shifts from `history`, and the ticking `elapsedMs` effect adds that on top of `Date.now() - activeEntry.clock_in_at` — so the number reads as one continuous work session across a break instead of restarting. This required `loadAll()` to fetch `history` unconditionally now (it used to skip that fetch entirely while `activeEntry` was set, since nothing needed it yet); pay itself is untouched either way, since `computeEntryPay()`/`StaffLogsView.jsx`'s period totals already sum every row on its own regardless of day. The Today/This week summary card also gained an hours-worked figure alongside pay (`todayHours`/`weekHours`, same "sum today's/this week's closed shifts" shape, requested directly right after the timer fix).

`staff_submit_shift_report(p_entry_id, p_note)` is the one write path for a report, covering every case that needs one with a single call rather than separate code per moment: right after clocking out, added later from Recent shifts for a shift that already has a report, or answering a member's explicit request. Mirrors `staff_clock_out()`'s shape (`security definer`, re-checks `staff_id = auth.uid()` inline) but **appends** to `notes` rather than overwriting — same "old body + a new `---`-separated chunk" pattern `upsert_eod_report()` already uses — and unconditionally clears `report_requested_at`, so answering a request (however it's answered) closes the loop regardless of which entry point was used. `StaffClockView.jsx`'s Recent shifts list shows any existing `notes` read-only above a fresh compose box, exactly mirroring `EndOfDayReportForm.jsx`'s own "existing body read-only, compose a new chunk below" shape.

`report_requested_at`/`report_requested_by` are the asking side — plain member columns, already covered by the existing unrestricted `time_entries` UPDATE RLS, so `requestShiftReport()` needs no RPC. Delivered as an **in-app prompt, not a push notification** — staff accounts have no push subscription support at all (`push_subscriptions` only links to `members`, and `StaffClockView.jsx` has no subscribe UI, since staff never reaches `SettingsMenu`), so building real push for this would have meant a schema change plus new subscribe-flow testing for a staff login; a flag the property manager sees highlighted at the top of their next Recent-shifts view was the right-sized answer instead. `StaffLogsView.jsx` shows the same `notes`/`report_requested_at` state on the member side (previously not rendered at all) with an "Ask for report" action.

Geofence-exit detection is entirely client-side, in `StaffClockView.jsx`, and **only ever prompts — it never auto-clocks-out**, by explicit product decision (a GPS glitch or a quick supply run shouldn't silently cut someone's pay). A `navigator.geolocation.watchPosition()` runs for the duration of an active shift (`enableHighAccuracy: false`, unlike the one-shot Start/Stop reads — this can run for hours, so battery life matters more than precision here), comparing against the active entry's own site using the same client-side `haversineDistanceM()` (`src/lib/geo.js`) the Start flow's nearest-site suggestion already uses. Being outside the radius has to persist for `GEOFENCE_PROMPT_DELAY_MS` (2 minutes) before it triggers anything — a single reading is never enough on its own, to avoid a false trigger from drift or a brief step outside. The resulting prompt reuses the exact same Break/Clock-out choice as a manual Stop tap, with one addition: an "I'm still working" option that dismisses it and resets the debounce, so a later genuine excursion can still trigger a fresh prompt rather than being permanently suppressed by one dismissal. Uses a functional `setStopFlow((current) => current ?? ...)` update specifically so an automatic trigger can never clobber a stop flow the property manager already opened manually.

**`StaffPayrollExport.jsx`** — CSV export, reached from a small "Export CSV" button on `StaffLogsView.jsx`. Reuses `VaultExportForm.jsx`'s `csvEscape`/`buildCsv`/Blob-download mechanics, duplicated locally rather than shared (this codebase's established preference for small per-file duplication over a shared module for a handful of helper lines — `buildWeeks()` is already independently duplicated between `MonthView.jsx`/`RentalCalendar.jsx` the same way). Deliberately **without** Vault's typed-`EXPORT`-confirmation gate: that exists specifically because a vault export leaks raw passwords, and names/hours/pay don't carry that same risk class, so a plain export button is proportionate. Exports whatever's currently on screen (matching the active status filter), not a separate date-range picker of its own.

**Member-only how-to:** `HowToGuide.jsx`, opened from `SettingsMenu` inside `TaskBoard`, includes a “Staff hours” guide plus FAQs for physical-location grouping, Needs setup visibility, and rate snapshotting. This is inherently Aaron/Ada-only without another role check: staff sessions route directly to `StaffClockView`, which has only theme/sign-out controls and never renders `TaskBoard` or `SettingsMenu` at all.

**Styling note:** every staff-feature component (`StaffClockView.jsx`, `StaffWorkSitesForm.jsx`, `StaffLogsView.jsx`, `StaffPayrollExport.jsx`) is written in Tailwind utility classes rather than this app's older hand-written `App.css`/`index.css` custom-property classes — consistent with the broader CSS-to-Tailwind migration elsewhere in this codebase (utilities-only import, no Preflight — see `src/tailwind.css`), not a one-off choice specific to this feature.

**Deferred, not part of this pass** (see the plan file for the full reasoning): an offline local-first queue buffering clock actions across network failure, and push notifications for a flagged/anomalous entry (natural shape: a Database Webhook on `time_entries` INSERT where `flagged = true`, reusing `fetchAllMembers()` — the property manager never has a push subscription of their own, since `push_subscriptions.member_id` hard-FKs to `members` and staff deliberately never joins it).

## UI structure

Five persistent destinations — **Today** (the task list, default), **Rentals**, **Reports**, **Cork Board**, **Inbox** (see Inbox above) — are tracked in `TaskBoard.jsx`'s `activeTab` state. `RentalsView.jsx`, `EodReportsList.jsx`, and `CorkBoardView.jsx` are plain tab content, not modals — no `onClose`, nothing to dismiss, you just switch tabs; all three are exclusively reached this way (no other call site). A slide-in panel treatment for Cork Board (toggled from the nav rather than a tab, inspired by Structured's "Inbox" panel) was tried and reverted — plain tab content was simpler and preferred.

`BulkAddTasksForm.jsx`'s Add tab teaches one paste format now, not two: `<date> [time] – description` (`src/lib/bulkTasks.js`'s `parseBulkTasks`, item-line shape) — a real time (`splitDateAndTime()`, a tight-hyphen range like "8am-9am" or a single time, peeled off the end of the date phrase before `parseDateHeader` ever sees it) is now optional on the *same* one-line shape, rather than requiring a switch to the original two-line "date header, then bare shift lines under it" format just to get a specific time on a task. Falls back to the dropdown's zone (`due_timezone: null` on the parsed task) when a line doesn't name one; a `NO_DATE_MARKERS` line drops a named zone too, same contradiction reasoning as the dropped time. The preview list's zone badge shows each row's actually-resolved zone (override or dropdown fallback), not just the dropdown's zone repeated on every row. A line indented underneath a task (`isIndented()`, checked on the raw line before any trimming — the only signal, tried before every other line shape) attaches as a checklist item on the most recently pushed task instead of becoming a task of its own, using the same `{ id, text, done, blocked, blockedReason }` shape `ChecklistEditor.jsx` builds by hand, so it's editable the normal way immediately after creation — an indented line with no task above it yet (nothing yet pushed to `tasks`) is a parse error rather than silently dropped. An optional `!high`/`!med`/`!low` marker (`splitPriorityMarker()`, tried anywhere in the prefix rather than pinned to a fixed position like the zone override, since the `!` sigil can't collide with any other syntax here) sets that task's `priority`, closing a real gap — Bulk Add, `PrioritiesForm.jsx`, and Cork Board's Focus-today promotion all used to silently create every task at the DB's `'med'` default with no way to say otherwise. The token table lives once in `lib/recurrence.js` (`parseRepeatToken` / `repeatToToken`) and drives both reading a pasted marker and writing one from a Guided card, so a card's fields and the text they produce cannot disagree (a test round-trips every token). ## Accessibility rules (UI/UX overhaul Phase 4)

Measured on real mounted components in both themes, not eyeballed — keep these true when adding UI:

- **Colour tokens for text.** The gold `--accent` (#d9a066) is only 2.3:1 on the light surfaces, so it is for fills and borders, never text. Use `text-accent-text` (`--accent-text`) for gold text/icons, `text-on-accent` (`--on-accent`, a dark brown, 7.2:1) for a label ON a gold fill (never `text-white` on `bg-accent`), `text-overdue-text` for red text (`bg-overdue` stays the fill), `text-notice-text` for amber warning text. `--control-border` (3:1) is applied globally to inputs/selects/textareas in `index.css` (unlayered, so it beats the decorative `--border`). All have separate dark values.
- **Muted text is `opacity-80`, not 60/65/70** (those measure 3.2-3.9:1; 80% clears 4.5:1 in both themes). Do not put `opacity` on a container that holds controls — it dims the controls too (that was the selected assignee pills and form fields), and nested opacity multiplies (a done block's dim × its already-muted children ≈ 2.4:1). Dim the text node itself.
- **Text on a colour you don't control** (member badge colour, rental unit colour) goes through `readableTextColor(bg)` in `lib/colorContrast.js` (white or dark ink, whichever has higher contrast). Never hard-code white on those.
- **Priority is never colour alone.** `PriorityDot` takes `priority` and draws it as a hollow ring (low), solid (medium) or solid with a halo (high) with `role="img"`/label; `PriorityBadge` adds a visible "↑ High"/"↓ Low" on rows, all-day pills and timeline blocks (Medium, the default, stays unmarked). `priorityDotStyle()` is the one source for the dot look.
- **Touch targets.** Floor is 24px (WCAG AA); aim for 40-44px. The done checkbox (`.task-done-checkbox`) is a custom 22px box in a 40px tappable area (transparent border + negative margin). Small round buttons get a transparent `after:-inset-2` hit area; text buttons and tabs get `pointer-coarse:min-h-10 max-[480px]:min-h-10`, so desktop stays compact. Every icon-only button needs an `aria-label`/`title`.
- **Errors.** Never show `err.message` raw: `setError(friendlyError(err))` (`lib/friendlyError.js`) rewords network/permission/session/duplicate/constraint/Edge-Function errors into a sentence that says what to do, passes through messages this app wrote itself, and falls back to a generic line for anything technical it does not recognise. The four account Edge Functions' own plain-text messages ("Password must be at least 8 characters") are surfaced by `throwFunctionError()` (`lib/functionError.js`) instead of the generic "non-2xx" line.

## Confirming destructive actions

Every "are you sure?" in the app goes through one in-app dialog, `ConfirmProvider.jsx` (mounted once in `main.jsx`) via `useConfirm()` from `src/lib/confirmContext.js` — `const ok = await confirm({ title, message, confirmLabel, cancelLabel, tone })`. It replaced fifteen scattered native `window.confirm()` calls (UI/UX overhaul Phase 3): the native dialog looks like it belongs to another program, its buttons say only "OK"/"Cancel", and browser automation cannot drive it. `useConfirm()` falls back to `window.confirm` only if a component is ever rendered outside the provider, so a destructive action can never skip its confirmation. **Do not add a new `window.confirm()`** — use this.

The rule, so each new delete path picks the same tier instead of inventing its own:
- **Reversible** (archive, Send to board, move, deactivate with a restore path): no dialog. The button names the result and the result says where it went. (Rental-unit removal and clock-in-location deactivation still confirm, with `tone: 'neutral'`, because their restore path is not obvious.)
- **Tiny inline item** (a checklist row, a Projects roadmap step): remove immediately; offer undo where cheap (roadmap steps already do, 8s).
- **Permanently deleting a real record** (task, pin, booking, expense, savings goal, vault entry, time entry, attachment): the dialog, with a question naming the item, one sentence on what is lost, Cancel focused by default, and a red button labelled with the action itself ("Delete task", never "OK").
- **Wiping everything** (the vault reset, the vault CSV export): keeps its existing typed confirmation instead.

`tone: 'neutral'` gives the gold (non-red) confirm button for confirmations that are not data loss (removing a folder tag, discarding an unsaved form, "Mark all as no reply needed"). A recurring task's delete keeps its own scope dialog in `TaskRow.jsx` ("Only this task" / "This and future tasks"), which already follows the same shape.
