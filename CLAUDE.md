# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install       # install deps
npm run dev        # Vite dev server (http://localhost:5173)
npm run build       # production build to dist/
npm run preview      # preview the production build
npm run lint        # oxlint (react + oxc rule sets, config in .oxlintrc.json)
```

There is no test suite in this repo.

Local dev needs `.env` (copy from `.env.example`) with `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, and `VITE_VAPID_PUBLIC_KEY` pointing at a Supabase project that has `supabase/schema.sql` applied — see README.md for the full first-time setup (creating the project, inviting the two accounts, seeding `members`, deploying to Netlify).

Supabase Edge Functions (`supabase/functions/`) are deployed independently of the frontend — `supabase functions deploy <name>` — and are **not** part of the Vite build or a Netlify deploy. All three are deployed with `--no-verify-jwt` (see Push notifications below for why `manual-notify` needs it too, despite being the one function that actually cares who's calling).

## What this app is

A shared task board for exactly two named people — Ada and Aaron — not a generic multi-user product. That two-person assumption is baked into the schema (no signup flow, a hardcoded `members` allowlist) and into the frontend (`src/lib/whoLabels.js` hardcodes the `who` ↔ display-name mapping). Don't generalize this to arbitrary users without deliberately revisiting both layers — several later features (working status, end-of-day reports, the "+" menu's quick actions) are explicitly asymmetric between the two people by design, not an oversight.

## Architecture

**Stack:** React 19 + Vite, no router (despite `react-router-dom` being a listed dependency — it's unused; `App.jsx` just conditionally renders `Login` or `TaskBoard` based on session state). Backend is Supabase (Postgres + Auth + Realtime + Storage + Edge Functions) on the free tier, accessed directly from the client via `src/lib/supabaseClient.js` — there is no separate API server, except for the Edge Functions described below.

**Auth:** Password sign-in (`supabase.auth.signInWithPassword`) is the default in `Login.jsx`, with magic link (`signInWithOtp`) available as a fallback via a toggle — magic link requires bouncing through the device's default browser to click the email link, which can't complete at all inside an iOS "Add to Home Screen" install (isolated storage, no address bar to land the redirect in), so password is the one that reliably works everywhere. Invite-only either way — public signup is disabled at the Supabase project level, not in this code. `src/lib/AuthContext.jsx` wraps the app and exposes `session`/`loading`/`signOut`.

**The two-account model:** `supabase/schema.sql` has a `members` table (id references `auth.users`, plus `display_name`) that acts as the allowlist — RLS on `members`/`tasks`/most other tables checks membership via the `is_member()` SQL function (`security definer`, needed so checking "is caller a member" against `members` doesn't recursively re-trigger RLS on that same table). Both members get full read/write on shared data; there's no per-row ownership check on `tasks`, because mutual visibility is the entire point of the app. A few newer tables (`eod_reports`) *do* restrict writes to your own `submitted_by` — see End-of-day reports below.

The `tasks.who` column is a `yours`/`assistant` enum tied to a fixed correspondence (`yours` = Ada, `assistant` = Aaron) defined once in `src/lib/whoLabels.js` (`WHO_LABEL`, `WHO_COLOR`, `whoKeyForName`) — this mapping is not stored in the database, so if either person's name ever changes, this file is the only place to update. Several server-side Edge Functions independently re-derive this same mapping via `resolveMemberIds()` (see Push notifications) since they can't import frontend code.

**Status is simpler than the schema suggests:** `tasks.status` is still a 3-value enum (`to_do` / `in_progress` / `done`) in Postgres, but the UI only exposes a done/not-done checkbox (`TaskRow.jsx`) — `in_progress` is vestigial and not reachable from the current UI.

**Checklist:** subtasks are a `jsonb` array column (`tasks.checklist`, shape `[{ id, text, done, blocked, blockedReason }]`) rather than a child table. `blocked`/`blockedReason` mark an item as not accomplishable (e.g. a requirement that turned out to be impossible), with an optional reason; blocked and done are mutually exclusive (setting one clears the other) in both `ChecklistEditor.jsx` (create/edit form, purely local state) and `ChecklistView.jsx` (task detail, writes straight to Supabase on every change). The reason `<input>` in `ChecklistView.jsx` keeps local draft state and only persists `onBlur`, not per-keystroke — wiring it directly to the per-change Supabase write made fast typing feel laggy/dropped, since every keystroke was round-tripping over the network before the input reflected it.

**All Day tasks:** `due_date IS NULL`. Created via an explicit "All day" checkbox in `TaskForm.jsx`, not just by leaving the date field blank — the form tracks a separate `allDay` boolean, because a blank date *string* and "deliberately no date" needed to be distinguishable to fix a real bug where editing an existing All Day task and saving without touching the date field would silently give it today's date.

**Task duration:** `duration_minutes` (nullable) + `due_date` = start; the end time is always derived (`due_date + duration_minutes`), never stored separately, so it can't drift out of sync. Shown as a range, e.g. "5:30–6:10 PM (40 min)". `getOverlappingTaskIds()` in `tasks.js` flags two of the *same* person's timed tasks that intersect — cross-person overlaps are never flagged, since Ada and Aaron having tasks at the same time isn't a real conflict.

**Recurrence:** handled entirely in Postgres (`spawn_next_recurrence()` trigger in `schema.sql`), not in the client. Fires on the transition into `status = 'done'` and inserts the next occurrence with the due date rolled forward and the checklist reset to unchecked (including clearing any `blocked` state). The next occurrence only appears once the current one is completed — it is not pre-generated ahead of time.

**Daily-planner grouping:** inline in `TaskBoard.jsx`, using `getOverdueTasks()` and `getTasksForDay()` (both in `src/lib/tasks.js`) plus a simple `!due_date` filter for the All-Day bucket — rendered as, respectively, a plain list (`AllDayRow.jsx`), a Structured-app-style vertical timeline (`TimelineRow.jsx`) for Overdue, and the same timeline again for the selected day. A completed task is bucketed and positioned by `completed_at`, not its original `due_date` — this was deliberate and revisited more than once: Ada (Central) assigning a task at 3pm her time can land on what's already "yesterday" on Aaron's (Philippines, UTC+8) calendar, and if completed tasks stayed pinned to that original due day, finishing something today would make today's list look empty. The visible time *label* still always shows the original due time (`TaskRow.jsx`'s `dueLabel`) plus a small muted "Completed" tag — only which day's *list* it appears in follows completion time.

**View modes:** the Today tab has a Day/Week/Month toggle (`viewMode` state in `TaskBoard.jsx`, `.period-tabs` reused from Rentals/Priorities) — a "Multi-Day" mode was tried and dropped as redundant with Day+Week. Day/Week share one rendering path — `daysToShow` (an array of Date, `getWeekDays(selectedDate)` for Week, `[selectedDate]` for Day, both in `tasks.js`) is mapped into `daySections`, each just `getTasksForDay()` called per day rather than any new bucketing logic; Day mode isn't special-cased in the loop, only its heading is: Day mode keeps the original "only show a heading if Overdue is also present" rule (to not add a redundant lone heading), while Week always labels each section ("Today"/"Tomorrow"/short weekday+date via `daySectionLabel()`) since multiple sections need telling apart. Month is a genuinely different shape (a grid, not a list) and doesn't fit through the same path — see MonthView below. `DateStrip` (a single-day picker) still renders below the tabs for Day/Week, hidden for Month since a day-by-day scroller doesn't make sense next to a full month grid.

On mobile, Day mode's `.task-list` also responds to a horizontal swipe — left advances `selectedDate` to the next day, right goes back to the day before (`shiftDay()`, a one-day version of the header's own `shiftWeek()`; the initial version had this backwards, going by literal finger-motion direction rather than the usual swipe-left-to-advance carousel/calendar convention, and was corrected after the flip read as wrong in practice). Gated to `!isDesktop && viewMode === 'day'` in the touch handlers themselves rather than conditionally attaching different handlers, since the same `.task-list` element is shared with Week mode. Only reads `touchstart`/`touchend` coordinates (no running `touchmove` tracking, no `preventDefault()`) and requires the gesture to be clearly more horizontal than vertical past a minimum distance, so it can't misfire during an ordinary vertical scroll through a long task list — coexists with `PullToRefresh`'s own vertical-only gesture on the same ancestor without either needing to know about the other. `.task-list` also carries a `min-height: 50vh` — without it, an empty/near-empty day's actual rendered height was just its "Nothing here." text line, so the swipe gesture (attached to `.task-list` itself) only worked in that small sliver; the rest of the visible screen belonged to a parent element with no handler of its own.

Month mode gets the same swipe treatment, same threshold/gating, stepping a new `shiftMonth()` instead (resets to day 1 of the target month rather than shifting the day-of-month as-is, so a naive overflow — e.g. Jan 31 + 1 month — can't skip a month entirely; same fix `RentalsView.jsx`'s own `shiftMonth()` already uses). Implemented as its own small copy of the gesture rather than a shared hook with Day mode's — each is only a handful of lines with a different mode gate and step function. Rentals' own month calendar (mobile only; desktop already has ‹ › arrows and no touch to hook) gets the identical gesture wired to its own existing `shiftMonth()`, wrapped around `RentalCalendar` in `RentalsView.jsx`'s mobile render specifically — mobile/desktop are already two fully separate JSX trees there, so there's no single shared element a runtime `isDesktop` check would need to guard, unlike Today's Day/Month modes sharing one nav header.

Clicking the **Week** tab (`handleViewModeClick()` in `TaskBoard.jsx`) resets `selectedDate` to today before switching `viewMode` — otherwise Week would show whatever week `selectedDate` last happened to be in (e.g. left over from browsing Day mode), not necessarily the current one, when the entire point of Week is "how does this week's workload look right now." Day and Month don't get the same reset: Day mode's whole point is picking a specific day (resetting it out from under you would undo your own navigation), and Month wasn't asked to behave that way.

The **Today** nav item (`handleTabClick()`, wraps `setActiveTab` — used by both the mobile bottom bar and the desktop header nav, since they share one `navButtons` array) does the same reset, unconditionally: back to today's date, in Day mode. Day/Week/Month are all view-modes inside this one nav tab rather than separate tabs, so tapping Today is the one "take me home" control needed — you're always already on it whenever you're deep in Week or Month view, so tapping it again just snaps back to today rather than needing a second dedicated button somewhere else.

The who-filter `<select>` (All/Ada/Aaron) sits inline in the same row as the view-mode tabs (`.view-mode-row`, wrapping `.period-tabs` + `.who-select`) rather than its own standalone row below — both answer "what am I viewing" (time range vs. whose tasks), so grouping them reads as one control cluster. It used to live inside `DateStrip`'s own header row (`headerRight` prop, since removed entirely since nothing else used it) — moving it out to sit beside the view-mode tabs.

**Header** (`.task-board-header` in `TaskBoard.jsx`): the time-of-day greeting (`timeOfDayGreeting()`) that used to open every tab is gone — `src/lib/greeting.js` was deleted outright once nothing referenced it anymore, rather than left as dead code. The header's left side is now tab-specific: Today shows a persistent `Month Year` navigator (`.month-nav-row`, shared with Rentals' own month nav — see below, always visible regardless of `viewMode`, Structured-style) — tapping the label itself (`▾`/`▴` caret) opens a date-picker popover for jumping to an arbitrary date — picking one drops `viewMode` into `'day'` on that date, same drill-down as `MonthView`'s own `onSelectDay` (this used to land on Week instead, inconsistent with that and with the point of picking one exact day) — while the adjacent `‹ ›` pair (`.month-nav-arrows`, `shiftWeek()` despite the row's own "month" naming — a leftover from an earlier version of this control) steps a week at a time. `.month-nav-arrows` is desktop-only (`isDesktop &&`, `useMediaQuery('(min-width: 900px)')` — see Nav placement below): mobile's `.task-list` already has a swipe gesture covering the same step-forward/back job (day-by-day in Day mode, month-by-month in Month mode — see below), so the button pair was pure redundancy there, just competing for cramped header width with the label's own tap target right beside it. Desktop has no swipe equivalent, so the buttons stay the only way to step there. Every other tab shows a plain page title instead (`PAGE_LABELS[activeTab]` — "Awa Rentalz" for Rentals, not "Rentals," so it doesn't just repeat the nav item's own label). Those titles used to be an `<h2>` rendered inside each page's own component (`RentalsView.jsx`, `EodReportsList.jsx`, `CorkBoardView.jsx`) — moved up into the shared header instead of being duplicated in both places, so each of those components no longer renders its own top-level heading at all. `.header-actions` (working-status toggle + settings) has `margin-left: auto` as a defensive right-alignment, in case a tab is ever added without a matching `PAGE_LABELS` entry — every current tab already renders *something* on the header's left, so `.task-board-header`'s own `justify-content: space-between` keeps `.header-actions` pinned right regardless. `DateStrip` no longer renders its own per-day header label (`"Monday, August 10"`) — that got removed once the persistent month/year header made it redundant, leaving `DateStrip` as just the scroller strip.

**MonthView** (`MonthView.jsx`): each cell previews actual task chips (priority-colored dot, title, time — same `PRIORITY_COLOR` map `TimelineRow.jsx` uses, for visual consistency with the rest of the app) capped at `MAX_VISIBLE_TASKS` (3) with a "N more" overflow line, not just a plain "there's something here" dot — the whole point of Month is a bird's-eye view of what's actually coming up, not merely which days aren't empty. Chips aren't individually clickable (out of scope for now — clicking anywhere in a cell, chips included, still just selects that day and drops `viewMode` back to `'day'`, the standard calendar drill-down pattern); reading a task's full detail means going to Day mode for it. Grid-building (`buildWeeks()`) duplicates `RentalCalendar.jsx`'s identical helper rather than sharing it — the two calendars have nothing else in common (task chips vs. colored booking bars) so a shared abstraction wouldn't buy much. Backed by `groupTasksByDay()` in `tasks.js`, which buckets a task list into a `Map` of `'YYYY-MM-DD' -> tasks[]` in one pass (same done/not-done rule as `getTasksForDay`) — computed once per month render rather than calling `getTasksForDay()` in a loop once per grid cell; chip order within a day follows whatever order `tasks` already arrived in (ascending `due_date`, per `fetchTasks()`'s own query order), not re-sorted. The grid itself is full width with tall cells (`min-height`, taller again above `min-width: 900px`) rather than the small square/dot-per-day version this replaced — cells use a shared 1px `outline` (not `border`, and not the grid's own `gap`) so adjacent cells' edges overlap into a single hairline instead of doubling up, since plain `<div>`/`<button>` grids have no `border-collapse` equivalent. `.month-view-grid` has no `overflow: hidden` (an early version paired it with `border-radius` to round the grid's outer corners, which risked clipping actual weeks off a taller month instead — every real ancestor here, `.tab-panel` up through `PullToRefresh`'s wrapper, is otherwise height-unconstrained, so that was the only self-inflicted clipping mechanism in this code; square corners, plain `border`, no clipping risk now) — `.month-view-day`/`.month-view-day-empty` also get an explicit `min-width: 0`, since `1fr` grid tracks default to a content-based automatic minimum that could otherwise force a track wider than its fair share.

**Realtime:** `TaskBoard.jsx` subscribes to two Postgres-changes channels — `tasks-changes` and `members-changes` (the latter exists specifically so Ada's "Aaron is working" badge updates live) — each just refetches its whole table on any change, no granular diffing. A table must be explicitly added to the `supabase_realtime` publication (`alter publication supabase_realtime add table <name>`) before Realtime emits anything for it — this is not automatic on table creation and has been missed before.

**Forms:** `TaskForm.jsx` is shared between creating a task (`NewTaskForm.jsx`) and editing one (rendered inline in place of the row inside `TaskRow.jsx`). Due date/time are edited as separate `due_date` + `due_time` fields (plus an end-time/duration pair) and combined into one ISO timestamp on submit (`zonedTimeToUtcIso` in `src/lib/timezone.js`) — the database only ever sees a single `due_date` timestamptz plus `duration_minutes`.

`detectDefaultTimezone()` (`src/lib/timezone.js`) seeds a lazily-created task/priority/cork-note's zone when nobody touches the Time/Timezone fields — it now prefers the signed-in member's own explicit choice (`members.default_timezone`, set via `SettingsMenu.jsx`) over device detection, falling back to the device's own IANA zone (or `DEFAULT_TIMEZONE`) when unset. That preference is cached in a plain module-level variable (`setPreferredTimezone`, kept in sync by `TaskBoard.jsx` whenever `me` changes) rather than threaded through props, since `detectDefaultTimezone()` is called from several places (`TaskForm.jsx`'s `emptyTaskForm`, `CorkBoardView.jsx`, `PrioritiesForm.jsx`) that would otherwise all need `me`/`members` piped in just for this — the same reasoning `useTheme.js` already uses `localStorage` for, except this preference has to be mutually visible (the other person needs to see it too when bulk-adding *your* schedule for you, see `BulkAddTasksForm.jsx`'s `zoneForWho`), so it lives on `members` in Supabase rather than a per-device value.

**Modal:** `Modal.jsx` renders via a React portal straight onto `document.body`, not in place. This matters because a modal opened from *inside* another modal (e.g. the `ScrollSelect` time picker used inside the edit-task form) would otherwise sit nested deep in the outer modal's own DOM subtree — a `transform` on any ancestor (the mobile slide-up animation, for one) creates a new stacking context that traps `position:fixed` descendants regardless of z-index, so the inner modal could render behind sibling content instead of on top. The portal sidesteps this class of bug entirely rather than fighting it with z-index.

**ScrollSelect:** `src/components/ScrollSelect.jsx` is a `<select>` replacement for option lists too long for a native popover to handle reasonably (e.g. the task end-time picker, which lists every 15/30-minute mark up to 48 hours ahead) — opens through `Modal.jsx` (see above) rather than a custom absolutely-positioned panel, which broke down inside the task form's cramped multi-column flex-wrap layout.

**Theming:** CSS custom properties in `src/index.css`, switched via a `data-theme` attribute on `<html>` (`src/lib/useTheme.js`, persisted to `localStorage`). The explicit theme choice must also set the CSS `color-scheme` property — otherwise native form controls render using the OS-level theme regardless of the rest of the page.

## Push notifications

Web Push (VAPID), fully custom — no third-party push service. Three pieces shared across everything:
- `public/service-worker.js` — receives push events, shows the notification, handles tap-to-focus/open.
- `src/lib/pushNotifications.js` — client-side subscribe/unsubscribe; writes directly to the `push_subscriptions` table.
- `supabase/functions/_shared/notify.ts` — `resolveMemberIds()` (maps 'Ada'/'Aaron' `display_name` to member id via a service-role query) and `notifyMember(memberId, payload)` (sends via the `web-push` npm package, prunes dead subscriptions on a 404/410 response). Any other per-subscription failure (a VAPID key mismatch, a malformed subscription, a push-service error) gets `console.error`'d rather than silently discarded — the calling function still returns 200 regardless either way, since this whole call is fire-and-forget, so an un-logged failure had no trace anywhere. Caught this the hard way debugging a report of Ada's nudges never reaching Aaron: the Edge Function's own request log showed a clean 200, which looked like "server side is fine" right up until the real cause (in that case, actually unrelated — the Mac was asleep, so the push was correctly queued into Notification Center but had nothing to pop a banner on) got found by a different path. The logging gap was real regardless of what actually caused that specific report, and is worth having for the next one.

Three Edge Functions, two different trigger mechanisms, all deployed with `--no-verify-jwt`:
- `notify-task-events` — Database Webhook on `tasks` INSERT/UPDATE (assignment + completion pings). Only ever called server-to-server by Supabase's own webhook system, never a browser — `--no-verify-jwt` because there's no user session in that call at all.
- `notify-reminders` — pg_cron scheduled, three independent checks per run rather than three separate functions/schedules: tasks due within 15 minutes (`tasks.reminder_sent_at` prevents re-notifying on later cron ticks), tasks that have been overdue for 3+ days and haven't been nudged about it yet (`tasks.overdue_nudge_sent_at`, same one-shot-per-task reasoning — this fires once, not as a repeating daily nag), and rental charges landing today (`chargeDatesForBooking()`, reimplemented here since an Edge Function can't import frontend code — same reasoning `_shared/notify.ts` already gives for re-deriving the who/display_name mapping). The rental check skips a charge already covered by `rental_bookings.paid_charges` (an advance payment — see Rentals below) and dedups on `rent_reminder_sent_for`, a *date* rather than a boolean so the same booking's later monthly cycles still get their own reminder without needing to be reset by hand; notifies both members, since a rental charge isn't tied to one person the way a task is. Same `--no-verify-jwt` reasoning as `notify-task-events`.
- `manual-notify` — the only one invoked **directly from the browser** (`supabase.functions.invoke()`, used by the end-of-day report form, the "nudge" button, and the task-clarifications feature — see below), and the only one that actually cares who's calling — but it still needs `--no-verify-jwt`. The platform's own JWT check runs on the CORS preflight (`OPTIONS`) request too, and preflights never carry an `Authorization` header, so with verification *on* the platform rejected the preflight before the real request ever went out, surfacing to the client as a generic "failed to send a request" with no useful error. `manual-notify` verifies the caller itself instead — a per-request Supabase client built from the forwarded `Authorization` header, `auth.getUser()` — and derives the notification target as "whoever isn't the caller," never trusting a client-supplied target. This is also the only function with a CORS concern (`_shared/cors.ts`), since it's the only one a browser ever preflights.

Notification rules (see `notify-task-events/index.ts`), not a general preference system: assignment pings are symmetric — whoever gets assigned a task by the other person is notified immediately, either direction; assigning yourself a task doesn't ping you, since you already know. Completion pings are symmetric too, in both directions. (This was asymmetric earlier — Aaron pinged immediately, Ada only via the reminder, so Aaron queuing up tasks for her wouldn't spam her — but that changed to symmetric in commit `4c2e2b8` "notification for ada"; this doc had drifted out of sync with the code until it was caught and corrected.)

**Task-level nudge**, distinct from the person-level 👋 nudge icon in the header (see UI structure below) — a 🔔 button on an overdue task's own action row (`TaskRow.jsx`, next to Duplicate), only shown when that task belongs to the *other* person (nudging yourself makes no sense, same reasoning assignment pings skip the assigner) and it's actually overdue. Sends `manual-notify`'s `task_nudge` kind ("Still on your plate?" + the task title) and marks `overdue_nudge_sent_at`, the same column the automatic 3-day cron check above uses — whichever fires first (a manual tap or the next cron pass) suppresses the other from duplicating it. `overdue_nudge_sent_at` is backend-only bookkeeping, same as `reminder_sent_at` — never selected into the frontend's `TASK_COLUMNS`, so there's no "already nudged" indicator shown on the task itself; the button's own per-click `nudging`/`nudgeSent` local state is just a fire-and-forget confirmation, not a persisted read.

iOS specifics: web push only works from an installed Home Screen PWA (`manifest.json` + `apple-touch-icon`), iOS 16.4+ — a regular Safari tab can't receive push at all, and this is a hard platform limit, not something fixable in code.

## End-of-day / week / month / biweekly reports

`eod_reports`: one row per `(submitted_by, period, report_date)` — **not** one row per submission. `report_date` is always computed client-side in the submitter's own local timezone (`reportDateForPeriod()` in `src/lib/tasks.js`) and passed explicitly; the column has no database-side default, deliberately, since a UTC-based default would silently bucket under the wrong calendar day for a meaningful part of every day for Aaron.

A later submission within the same bucket doesn't insert a new row — it upserts via the `upsert_eod_report()` Postgres function (`security invoker`, `insert ... on conflict ... do update`), called through `supabase.rpc()` rather than the client SDK's `.upsert()`, because the two data columns have different update semantics `.upsert()` can't express:
- `body` **appends** (old body + a `---`-separated new chunk) — a running log across multiple work sessions in the same day.
- `minutes_logged` **overwrites**, never summed — this mirrors an external time tracker's running total, which the submitter corrects to match, not something this app tallies from sessions itself. Leaving it blank on a given submission keeps whatever total was last set.

`EndOfDayReportForm.jsx` fetches the caller's own existing row for the selected bucket on open (`fetchOwnEodReport`) and, if one exists, shows it read-only above a fresh "add to this" textarea, seeding the auto-tally via `getCompletedSince(tasks, whoKey, existing.updated_at)` — only completions *since the last submission*, not the whole period again, so a second session's draft doesn't duplicate what an earlier session already reported. The push notification still fires on every submission, not just the first one for a bucket — the point is Ada seeing progress after each session.

`biweekly` (the 4th `report_period` enum value, alongside day/week/month) exists specifically to account for everything completed within one payroll cutoff at once, rather than piecing it together from several week reports. Unlike week/month's boundaries (always "the current calendar week/month, whatever that happens to be"), a payroll period is a *fixed* 14-day cycle that doesn't reset with the calendar — so `startOfPeriod()` in `src/lib/tasks.js` anchors it to `BIWEEKLY_ANCHOR` (2026-07-26, a real confirmed cutoff: paid Aug 12 for Jul 26 - Aug 8, paid Aug 26 for Aug 9-22) and counts whole 14-day blocks elapsed since then, so every later cutoff stays aligned to it too, however far past the anchor "now" gets — same "always compute from the one fixed origin point, never the previous cycle" reasoning as `rentals.js`'s `addCalendarMonths`. `'biweekly'` reads fine as a bare adjective everywhere else it's used (the H2 title, the sent-notification text, EodReportsList.jsx's meta label — "Biweekly report", "— biweekly —"), but not in the few spots that slot the period into "this ___" prose ("this week" reads fine, "this biweekly" doesn't) — those go through a small `PERIOD_NOUN` map (`'pay period'`) in `EndOfDayReportForm.jsx` instead.

**Hidden from the UI, not removed:** the "2 Weeks" tab was pulled from both `EndOfDayReportForm.jsx`'s `PERIODS` and `EodReportsList.jsx`'s `PERIOD_TABS` after it turned out to add more tab-row clutter than it pulled its weight day to day. Everything else described in this section — `BIWEEKLY_ANCHOR`/`startOfPeriod()`, the DB enum value, `PERIOD_NOUN` — is untouched, and any already-submitted biweekly report still appears in `EodReportsList.jsx` under "All" (it isn't period-filtered out, just no longer has its own dedicated tab). Deliberately reversible rather than a full removal, so bringing the tab back later is a one-line change, not a rebuild.

## Priorities

`priorities` table — a shared planning note, unlike `eod_reports`: both Ada and Aaron can set it, since it's household planning rather than a personal log. Append-only: every save is a new row scoped to a `period` ('day'/'week'/'month'); "current" priorities for a period is just the most recent row for it (`fetchLatestPriorities()` in `src/lib/priorities.js`).

Saving also creates a real task per bullet item (`PrioritiesForm.jsx` → `createTask()`), not just the note — the point is that priorities stop being easy to set and forget. Day-period items get `due_date` set to today (so an unfinished one can go overdue like any other task); week/month items become All Day tasks (`due_date: null`), sticking around until done. The previous save's items are shown read-only and are never pre-filled into the editable list you're about to submit — otherwise reopening the form and saving again would recreate a task for every old item, not just anything new.

## Rentals (Awa Rentalz)

A side-feature bolted onto the task board: `RentalsView.jsx` (the "Rentals" tab — see UI structure below) tracks occupancy and finances for Ada's furnished-rental business. Hardcoded to `company: 'awa'` throughout the frontend even though the `rental_company` enum also has `'azu'` (Ada's mom's separate, unrelated rental business) — `azu` was added to the schema so it wouldn't require a migration later, but no UI exists for it yet; it's deliberately out of scope. All the `rental_*` tables use the same `is_member()` RLS as everything else — mutual visibility, no per-row ownership.

`RentalsView.jsx` also subscribes to its own `rentals-changes` Realtime channel (`rental_properties`/`rental_bookings`/`rental_expenses`/`rental_savings_goal`, each just refetching on any change, same reasoning as `TaskBoard.jsx`'s own channels), same as `CorkBoardView.jsx`'s `cork-notes-changes`. **All four of those tables must be added to the `supabase_realtime` publication by hand** (`alter publication supabase_realtime add table rental_properties, rental_bookings, rental_expenses, rental_savings_goal;` in the Supabase SQL editor) — see the Realtime note under Architecture; this is not run automatically by `schema.sql`.

**Two genuinely different layouts**, picked in `RentalsView.jsx` via `useMediaQuery('(min-width: 900px)')` (`src/lib/useMediaQuery.js` — a small `window.matchMedia` + change-listener hook, the *only* JS-driven responsive branch in the app; everywhere else, including this same 900px breakpoint for `.task-board-nav`, is one markup repositioned via CSS media queries alone). That works when both layouts are the same content differently arranged; Rentals' mobile tabs (Calendar/Financials/Overview, one panel at a time behind `view` state) vs. its desktop dashboard (all three always mounted side by side, no tabs) are structurally different trees, not a CSS rearrangement of the same one, so picking which tree to render at all has to happen in JS.

**Desktop dashboard** (`.rentals-dashboard`, a 2-column grid — went through several worse attempts first, all superseded, including a 3-column version with the unit list as its own sidebar column, then a version with it as its own section below the calendar): the main column holds a combined nav row (`.rentals-combined-nav`: month prev/next (`‹ August 2026 ›`) plus "+ Add booking"/"Edit unit"/"+ Add unit" buttons — an earlier version also had a second `‹ Unit ›` prev/next pair cycling `selectedUnitId` by index, since dropped in favor of the Overview-list-as-unit-switcher below being the only way to change units here), then the calendar. `RentalOverview.jsx` renders *inline with "+ Add booking"*, in the same row, via a `unitTabsReplacement` prop on `RentalCalendar.jsx` — `showUnitTabs={false}` hides that component's own `.rental-unit-tabs` toolbar there, and `unitTabsReplacement` fills that exact slot instead of a plain `<select>`/tabs row (no separate "Units" section needed: each row already carries most of the context you'd want — status, and now price too — and doubles as the way you switch units, so a second below-the-grid section duplicating that was redundant). `.rental-calendar-toolbar .rental-overview-list` overrides the list to lay out as a fixed two-per-row wrapping grid (`flex-direction: row`, each `<li>` locked to `flex: 1 1 calc(50% - 4px)`) instead of Overview's own mobile-tab vertical list, to actually fit that toolbar. Financials stays permanently visible in its own column on the right (`RentalFinancials.jsx`, unchanged, just not gated behind a `view === 'financials'` tab — it was already company-wide aggregate regardless of which unit's calendar is showing) under a subtle `.task-section-heading`-styled "Financials" label (reused, not a new class) — the per-unit `$X/mo` price line that used to sit at the top of this column was removed as redundant once `RentalOverview.jsx`'s rows show each unit's price directly. `selectedUnitId` moved out of `RentalCalendar.jsx` (which used to own it) up into `RentalsView.jsx`, since both the Overview list and the combined nav row need to drive the same selection. No flat `max-width` cap on `.rental-month-grid` in this layout — the main column's own width already bounds it to a comfortable size, unlike the old single-column layout where the grid had nothing else constraining it.

`.rental-overview-list` needs an explicit `list-style: none` — a `<li>` still gets a marker box even inside a flex/grid parent (blockification changes layout mode, not marker generation), which is easy to assume is already handled by `display: flex` alone and isn't.

**Mobile** used to be three separate tabs (Calendar/Financials/Overview, one panel at a time behind a `view` state) but is now Overview → "+ Add unit" → month nav → Calendar → Financials stacked into one scrollable column, no tabs — switching between "kinds of info" meant losing sight of everything else, which defeated the point of an at-a-glance status board. Doesn't reuse desktop's `unitTabsReplacement` dedup trick (below) for the same job here: `RentalCalendar.jsx` just renders with `showUnitTabs={false}` and `showUnitHeader={false}` (no tab strip, no `$/mo` header — both redundant once Overview's cards, always visible above it, already show price and double as the unit-switcher via the same `selectedUnitId`/`onSelectUnit` `RentalsView.jsx` already threads through both). Overview and Calendar don't need to be visually nested for that to work — they just need to read the same state, which they already did even before this change. `.rental-calendar-toolbar .rental-overview-list`'s horizontal-row override (below) is desktop-toolbar-specific and deliberately not reused here; forcing Overview's multi-line cards into that row at 375px would squeeze them.

Only `.rental-month-grid` itself used to be width-capped (`max-width: 420px`) at the `min-width: 900px` breakpoint, before the dashboard replaced that whole layout at that breakpoint — this went through two worse attempts first, kept here since the reasoning still explains today's `.rental-unit-tabs` styling (below), which still matters on mobile. Capping `.rental-calendar` (toolbar + grid together) fixed the grid's day cells (`aspect-ratio: 1`) stretching into oversized squares, but also squeezed the unit-tabs row down to the same narrow width, wrapping the four unit tabs onto two rows instead of sitting side by side. Capping the whole `.tab-panel` instead (verified via `getComputedStyle` to genuinely apply) avoided that, but with no centering it sat flush against the left edge of the wide desktop content area, and centering it just shrank everything uniformly, reintroducing the unit-tab wrapping. Capping only the grid let the toolbar above it use the full desktop content width instead. `.rental-unit-tabs` itself (`showUnitTabs`'s `true` default) is no longer what mobile Rentals actually renders — see Mobile above — but the styling stays defined and this history stays accurate for it, since `RentalCalendar.jsx` still supports rendering that way and defaults to it for any future caller that doesn't opt out.

**Calendar** (`RentalCalendar.jsx`): shows one unit at a time — a row of unit tabs (`.rental-unit-tabs`, one click to switch — a `<select>` dropdown originally, replaced because it took a scroll-and-choose on every switch) is the default, but both current callers opt out of it (`showUnitTabs={false}`) and switch some other way instead: on mobile, tapping an Overview card (see Mobile above); on desktop, switched externally (see dashboard above) — rendering a standard 7-column month grid — not a multi-unit Gantt-style timeline, which an earlier version tried and had to be scrapped (it needed a wider modal, which fought the mobile CSS reset and broke the layout on phones). `check_out` on `rental_bookings` is the *last occupied day, inclusive* — not a hotel-style departure day — so a single-day booking has `check_out = check_in`.

`.rental-unit-tabs` is `display: grid; grid-template-columns: repeat(auto-fit, minmax(120px, 1fr))`, not `flex-wrap` — auto-fit packs as many equal-width 120px+ columns as actually fit, settling into a neat 2x2 grid instead of flex-wrap's old behavior of stretching each *wrapped* tab to the full row width, stacking 4 heavy full-width bars. It's also forced to `flex-basis: 100%` within `.rental-calendar-toolbar` so it always gets the full toolbar width to compute columns from, rather than sharing a row with "+ Add booking" and wrapping unevenly depending on how much space that left over; "+ Add booking" drops to its own line below instead. Below `max-width: 899px` (i.e. whenever this toolbar can render at all, since the desktop dashboard suppresses it entirely) it shrinks further still — smaller `minmax()` floor, tighter padding, smaller font/dot — "as small as this can reasonably go," since there's no wide-screen case left to keep it legible for.

A multi-day booking bridges the grid's 4px gap between its own consecutive days via an inline `boxShadow` (`-4px 0 0 0 ${unit.color}` / `4px 0 0 0 ${unit.color}` on the connecting side(s), computed as `connectsLeft`/`connectsRight` by checking whether the row-adjacent day is occupied by the *same* booking id) rather than rendering as a checkerboard of separate same-colored tiles — box-shadow is a pure paint effect, so it can't shift the day number or resize the cell the way a padding/margin trick would. Deliberately scoped to within a row only (same as `isStart`/`isEnd`'s existing `col === 0`/`col === 6` edge cases) — a booking spanning a week boundary still breaks into a separate bar per row, since two grid rows can't visually connect anyway.

The guest's name is printed on the bar itself (`.rental-month-day-guest`, truncated with an ellipsis if it doesn't fit), not just left in the `title`/`aria-label` tooltip — reused `isStart` for exactly where to (re)print it, since it already means "the real check-in day, or the first column of a row this booking is only continuing into," which is precisely where a real calendar app would repeat an event's title too. `.rental-month-day-occupied` switched from centering a single item to a small flex column (day number + optional name stacked) to make room — harmless on every other occupied cell in the bar, which only ever has the one child (the day number) and still centers exactly as before.

Bookings carry a `status` (`pending`/`confirmed`): a pending request (e.g. an inbound Airbnb inquiry) still blocks the unit's dates against a double-booking and renders as a diagonal-striped cell instead of a solid one, but never counts toward revenue until explicitly confirmed.

`.tab-panel`'s section gap bumps from 12px to 16px under `max-width: 480px` — a global change (every tab, not just Rentals), motivated by Rentals specifically: its Calendar tab stacks the most sections of any tab (heading, period-tabs, month nav, unit tabs, price line, then the grid), and 12px read as cramped once all of those piled up tightly on a narrow phone screen.

**Financials** (`RentalFinancials.jsx`): revenue is recognized by upfront charge cycle, not by calendar-day occupancy. `chargeDatesForBooking()` in `src/lib/rentals.js` models rent as paid every month on check-in's own calendar day-of-month (security-deposit/Airbnb-style upfront payment) — a guest who checked in May 30 bills on the 30th of every following month, not "30 days later" repeatedly, which would drift the billing day earlier across shorter months (`addCalendarMonths()`, always computed from the original check-in rather than the previous cycle, so a short-month rollover can't compound). A guest who checked in Aug 15 doesn't generate a second month of "revenue" just for still being there in September. A later cycle only counts if there's an actual day of stay left beyond it — a booking checking out on exactly its next billing day doesn't get billed twice for that trailing day. A charge date also only counts once it's actually arrived (`isBillableCharge()`) — a unit whose next cycle starts later this month doesn't show as billed for it while browsing the current month, before that day has actually happened. That unit's "Occupied, no charge yet" badge names the actual upcoming date and amount instead of leaving it a bare status (`upcomingChargeByProperty`, the soonest charge date across every confirmed booking touching that property this month that hasn't arrived yet) — this covers a current tenant's own next cycle and an already-booked replacement tenant's move-in charge (back-to-back turnover) the same way, showing whichever lands first regardless of which booking it belongs to.

Every unit row in the Units list also gets a second line combining the tenant chain with "Available {date}[ – {until}]" (`nextAvailability()` in `rentals.js`), e.g. "Abdul · Available Sep 26" or, for a back-to-back turnover, "Abdul → Ian · Available Dec 13" — one sub-line, not two, so naming tenants doesn't cost more vertical space than the availability line already added on its own. Three needs converged here: eyeballing a unit's checkout date wasn't enough to answer "can I actually book someone new here" once the household's 30-day minimum stay (`MIN_STAY_DAYS`) is factored in (a checkout doesn't mean bookable if another confirmed stay already starts too soon after); the primary badge text alone didn't say who was actually renting; and once a unit had two back-to-back tenants queued, the date alone jumped from "occupied by Abdul" straight to a date months out with nothing explaining why — reported as looking arbitrary/wrong even though the date itself was already correct. `nextAvailability()` now returns `blocking`, the ordered list of every tenant actually stood in the way (not just the first), alongside walking forward through every future *confirmed* booking (a pending request doesn't block — it isn't guaranteed, and treating it as blocking would understate real availability) looking for the first gap of at least 30 days, skipping past any booking that doesn't leave enough room; only shows an `until` date when that gap is itself capped by a specific future booking, otherwise it's open-ended — `until` is that booking's check-in *minus one day*, the last actually-free day (same "inclusive last day" convention `check_out` already uses elsewhere), not the check-in date itself, which reported as showing an already-occupied day as if it were still available before this was caught. Needs the *unscoped* booking set, not the month-limited `bookings` this component otherwise uses (a blocking booking, or the actual current tenant, can be outside the browsed month) — `RentalsView.jsx` already fetches that separately for `RentalOverview.jsx` (`upcomingBookings`), passed to `RentalFinancials.jsx` as `allBookings` rather than duplicating the query. The primary badge itself dropped "no charge yet" down to just "Occupied" once the tenant chain below already implies occupancy — spelling it out twice was the single longest, most-likely-to-wrap badge in the list for no added information.

`paid_charges` (`rental_bookings`, a plain jsonb array of `'YYYY-MM-DD'` charge dates — same "doesn't need a child table" reasoning as `checklist`) is the one manual override to the otherwise fully date-driven revenue calc: `isBillableCharge()` counts a charge as billed once its date has *either* actually arrived *or* been added to this array, closing the "tenant paid in advance" case the pure schedule can't represent on its own. Two entry points reach the same `setChargePaid()` in `rentals.js`, both scoped to one specific upcoming charge rather than a general per-date payment history/toggle: a "Mark paid" button on a Financials `occupiedNoCharge` row's own availability line (targets whichever booking generates that property's next charge), and a "Mark {date} paid" action in `RentalBookingDetail.jsx`'s own modal (targets that specific booking's own soonest unpaid future charge — `chargeDatesForBooking()` filtered to `> todayDateStr()` and not already in `paid_charges`, hidden entirely on a pending request since it can't be paid in advance for something that might still be declined, and hidden once nothing future is left unpaid). No manual refetch after marking, either way: `rental_bookings` is already on `RentalsView.jsx`'s Realtime channel, so the write alone moves the unit from `occupiedNoCharge` into `billed` on the next tick.

**Overview** (`RentalOverview.jsx`): all units at a glance — one status line per unit, "Occupied through {date} — {guest}" or "Vacant" (with the next upcoming booking's start date *and guest name*, if any — the name was computed by `unitOccupancyStatus()` from the start but silently dropped by the JSX until an audit caught it, since "who" is exactly the detail a glance is for). Deliberately a plain list, not a grid, for the same reason the Calendar tab isn't a multi-unit timeline. Backed by `fetchUpcomingRentalBookings()`/`unitOccupancyStatus()` in `src/lib/rentals.js`, a separate query from the Calendar tab's month-scoped `bookings` (`check_out >= today`, no upper bound) — otherwise a unit occupied past the currently-browsed month's end would show a truncated or missing through-date.

Two contexts share this same component: mobile's Overview tab (its own vertical list, default card-row styling) and the desktop dashboard's `RentalCalendar` toolbar (rendered inline with "+ Add booking" via `unitTabsReplacement` — see Rentals above), which overrides `.rental-overview-list` to a fixed two-per-row wrapping layout via a `.rental-calendar-toolbar` ancestor selector rather than a component prop. Two earlier dashboard versions had a `compact` prop here (no card border, tighter spacing) — first for Overview as its own sidebar column, later for its own section below the calendar — both reasons stopped applying once it moved into the toolbar, so the prop was removed outright rather than left unused. Each row shows the unit's price now (`p.monthly_rent`) alongside its status. `selectedUnitId`/`onSelectUnit`, when passed, make each row a `<button>` (a plain `<div>` otherwise) and highlight the active unit — in the desktop toolbar this is the *only* way to switch units now that the plain unit-tabs are hidden there, a low-cost bonus on mobile too (tapping a unit there primes which one the Calendar tab opens to next).

**Negotiating mark**: `rental_properties.in_negotiation` (boolean, default `false`) is a quick per-unit flag for "there's a promising prospective tenant / an active back-and-forth on this unit right now" — not tied to any specific booking row, since a negotiation usually predates a confirmed booking existing at all. Displayed as "In talks" (not the column's own "negotiation" naming, which stays internal-only). One element serves as both the control and the display — `.rental-negotiating-toggle`, a `<button>` living *inside* `.rental-overview-item`, absolutely positioned against it (`top: 50%` + `translateY(-50%)`, pinned to the right edge) rather than sitting in the card's normal top-to-bottom flow: a small 🤝-only circle at rest, growing into a filled-amber "🤝 In talks" pill once on. Positioning it against the card as a whole (not inline in the text flow) means toggling it never adds a line or changes the card's height, regardless of whether the status text below happens to wrap to one line or two; `.rental-overview-item` reserves `padding-right: 84px` (restated in the desktop toolbar's own compact override, which would otherwise silently reset it via its own shorthand `padding`) so the toggle never overlaps the name/price/status text at either width. Amber `#e0a83e` rather than the app's usual accent gold, so it doesn't read as the same thing as `.rental-overview-item-selected`'s own accent border on the same card.

Nesting a real `<button>` inside the card is exactly why `.rental-overview-item` is a `<div role="button" tabIndex={0} onKeyDown={...}>` in `RentalOverview.jsx` rather than a real `<button>` — a `<button>` can't validly contain another interactive control, which is also why the toggle's own `onClick` calls `e.stopPropagation()` first, so a tap on it doesn't also fire the card's own select-unit handler. `onToggleNegotiating`, when passed, shows the toggle in *both* contexts (unlike `onEditUnit`, mobile-only) — the mark is meant to be settable wherever the unit list renders. `setUnitNegotiating()` (`src/lib/rentals.js`) just writes the column and lets `RentalsView.jsx` explicitly `reloadProperties()` afterward for a snappy click rather than waiting on the `rentals-changes` realtime round-trip (same pattern `archiveRentalProperty` already relies on for its own refresh). Since `schema.sql` is applied once to a fresh project (see Commands above) rather than tracked as incremental migrations, adding this column to an *existing* live database needs a manual `alter table rental_properties add column in_negotiation boolean not null default false;` run once in the Supabase SQL editor — editing `schema.sql` alone doesn't retroactively touch a database that already exists.

**Savings goals** (`rental_savings_goal`): `saved_amount` is a plain, manually-edited number — not derived from bookings. Two earlier attempts at auto-computing it from booking revenue (a raw cumulative sum, then a full per-month approve/edit reconciliation flow) both turned out to be more machinery than a two-person household actually wants; editing the total directly, in the goal's own edit form, replaced both.

## Password vault

`VaultView.jsx` (also off the "+" speed-dial) stores credentials encrypted client-side — AES-GCM, key derived via PBKDF2 from a **shared** master password (known to both Ada and Aaron, consistent with everything else in this app being mutually visible) — before anything reaches Supabase. RLS on `vault_meta`/`vault_entries` governs who can read/write ciphertext, but it is *not* the security boundary for the passwords themselves; the encryption is, so a leaked service-role key or an RLS mistake only exposes unreadable ciphertext. The derived key lives only in React component state, never persisted to localStorage/sessionStorage, so it has to be re-entered every time the vault is reopened.

There is no password-reset path by design — if the master password is forgotten, the only way out is "Reset vault" (wipes `vault_meta` and all `vault_entries`), gated behind typing a confirmation word rather than a plain `window.confirm`. That's the first typed-confirmation pattern in this codebase; the only other place it's used is the CSV export, since that's the one action that undoes the vault's whole security guarantee (it downloads every password as an unencrypted file).

An entry's `loginMethod` field (e.g. "Google") is set instead of a password for accounts with no password of their own ("Sign in with Google") — `VaultEntryDetail.jsx` shows "Sign in via {loginMethod}" instead of a blank, confusing password row when it's set.

**Folders**: an optional `folder` field on each entry (a plain `<select>` in `VaultEntryForm.jsx`, options from the fixed `VAULT_FOLDERS` list in `lib/vault.js` — currently `'Awa Rentalz'`/`'Azu Rentals'`, for per-unit door-lock codes and the like) groups the list in `VaultView.jsx`, collapsible per folder same shape as `EodReportsList.jsx`'s month groups (own `.vault-folder*` classes, not shared ones — the two features aren't otherwise related). `folder` lives *inside* the encrypted entry payload, not as its own database column — every entry is already fully decrypted client-side on every load, so grouping by a field inside that payload needed no schema change and doesn't leak which entries belong to which folder to anyone without the master password, unlike a plaintext column would have. An entry with no folder (or an old one predating this feature) falls into a catch-all "General" group. The grouped/collapsible UI only replaces the plain flat list once there are actually 2+ groups present — a vault where nobody's used folders yet still looks exactly as before, no empty-group clutter.

## Working status

`members.working_since` — nullable `timestamptz`, doubling as the on/off flag (`is`/`is not` null) and giving "working since 2:15 PM" for free with no separate boolean that could drift out of sync. Aaron gets an actual toggle (`WorkingStatusToggle.jsx`); Ada only ever gets a read-only badge reflecting it, never the reverse — "I'm working" is inherently self-reported. Ada's badge always shows something now — "🟢 Aaron" or "⚪ Aaron" — rather than only rendering when Aaron's online and disappearing otherwise; `.working-badge`'s base style is muted/gray (the offline state), `.working-badge-online` (added on top) is what supplies the green. The badge dropped the "is online"/"is offline" suffix — the dot color alone already says it, and spelling it out too was redundant; the `title` tooltip still states it in words for anyone who can't tell green from gray at a glance. It lives in `.header-actions`, part of the shared header row present on every tab, so "across all pages" was already true structurally — the only change needed was to stop returning `null` for the offline case.

## Completion submissions

Optional per-task proof-of-completion: `completion_note` (text) + `completion_attachments` (`jsonb` array of `{url, name}`, same "doesn't need a child table" reasoning as `checklist`). Any file type is accepted, not just images — `isImageAttachment()` in `src/lib/attachments.js` checks the filename extension to decide between an inline `<img>` preview and a plain download link. Files go to the public `task-attachments` Storage bucket; `storage.objects` RLS needs INSERT + UPDATE + **SELECT** policies for members — the SELECT policy is easy to miss, since `.upload(..., { upsert: true })` needs to check whether the object already exists first, and its absence surfaces as a generic RLS error on upload rather than an obviously-missing-SELECT one.

## Task clarifications

`tasks.clarifications` — a lightweight comment/question thread per task (`jsonb` array, `{ id, askedBy, question, answer, askedAt, answeredBy, answeredAt, resolved, resolvedBy, resolvedAt }`), same "doesn't need a child table" reasoning as `checklist`/`completion_attachments`. Despite the field names it covers comments and suggestions too, not just literal questions — the UI copy is deliberately generic ("Ask a question or leave a comment…") since a common case (e.g. Ada commenting on a task Aaron self-assigned) isn't a question at all.

Both the "Send" button (asking, `TaskClarifications.jsx`) and "Reply" (answering, `AnswerRow` in the same file) only render once their textarea/attachments actually hold something — not just disabled-while-empty. `.clarification-ask-button` used to always render, disabled, sitting right next to the task's own Edit/Delete/Duplicate row (`extraActions`, to its left in `.clarification-compose-left`) — an easy misclick target when reaching for one of those instead, and the actual cause of a reported "can't mark a task done" bug (a stray tap landed on the always-there Send button, not the checkbox).

Notifications go through `manual-notify` (direct invoke), not the `notify-task-events` webhook — asking/answering is a discrete user action like the nudge button, not a row-diff the webhook would need to detect. Target resolution is unchanged ("whoever isn't the caller"), so it works symmetrically regardless of who created or is assigned the task — either person can comment on any task and the other gets pinged, no special-casing for assignee vs. creator. `TaskRow.jsx` shows a 💬 badge on the collapsed row when there's an unanswered, unresolved message directed at the current viewer, an in-app reminder that doesn't depend on the push notification having been seen.

Not every entry is actually a question — a plain FYI comment has nothing to answer, so `resolved` lets the recipient dismiss it ("No reply needed" in `TaskClarifications.jsx`, or the same action inline from the Inbox tab) without writing an `answer`. `resolved`/`answer` are mutually exclusive in practice (an entry only ever gets one or the other), and once either is set the entry stops counting as pending anywhere (the 💬 badge, `getInboxItems`'s `question` bucket). Resolving is deliberately quiet — no push notification, unlike asking/answering — since dismissing something as not needing a reply isn't news worth pinging over.

## Inbox

A persistent tab (`InboxView.jsx`) aggregating clarification activity across every task, not just whichever ones happen to be visible in the currently-browsed day/week/month — the only way to notice a stray question before this was stumbling onto that specific task's 💬 badge. Originally scoped to clarifications only, not a general activity feed (assignment/completion pings and nudges are still push-notification-only, unchanged) — but a **Submissions** section (below) later widened that on purpose, once the exact same discoverability gap turned out to apply to completion submissions too.

Not self-fetching like `CorkBoardView.jsx`/`EodReportsList.jsx` — `fetchTasks()` already loads every task with no date filter, and `TaskBoard.jsx` keeps that array live via its existing `tasks-changes` Realtime channel, so `InboxView` just receives `tasks` as a prop and derives everything from data already in memory (`getInboxItems()` in `tasks.js`) rather than duplicating a fetch/channel. Three sections, in priority order: **Needs your reply** (unanswered, unresolved questions directed at you — self-clearing, same condition as the 💬 badge), **Resolved** (your own questions that got closed out — merges the `answer`/`finished` item kinds from `getInboxItems()` into one UI section, re-sorted by date since they no longer need `INBOX_KIND_ORDER`'s kind-then-date grouping once shown together; splitting "got an actual reply" from "dismissed with No reply needed" into separate tabs was a finer distinction than the tab row needed to make, both already being the lowest-priority, closer-to-an-archive kind of item), and **Submissions** (see below). Resolved/Submissions show full history, not just recent activity — a resolved conversation or a submission shouldn't age out of findability just because it happened a while ago, since neither `clarifications` nor completed tasks are ever pruned.

An All/Needs your reply/Resolved/Submissions `.period-tabs` row (`view` state, same reused markup `EodReportsList.jsx`'s own period filter and Bulk Add's Add/Edit toggle already use) narrows the list down to one section at a time — added once several sections stacked together read as one long undifferentiated scroll on a normal day. "All" (the default) keeps the original always-everything-visible behavior; the other three hide every section except their own, showing a small "nothing here yet" message instead of just going blank when that section is empty. Doesn't touch `getInboxItems()`/`getCompletedSubmissions()` or any of the read/unread logic below — `view` is purely which already-computed sections get rendered, not a second data fetch.

**Submissions**: tasks with a `completion_note`/`completion_attachments` — the same "only way to notice was stumbling onto the task itself" problem clarifications had, just for proof-of-completion instead of comments. `getCompletedSubmissions()` in `tasks.js` filters to `status === 'done'` tasks that actually carry a submission (not every completed task — a plain checked-off task with nothing attached isn't "waiting to be found," it's just done), sorted newest-first by `completed_at`. Unlike `getInboxItems()`, not scoped to `meId` — a submission is mutually visible regardless of who completed the task or who's looking, same as everything else in this app. Rendered by a separate `SubmissionItem` (not the shared `InboxItem` used by the clarification sections above), since a submission is keyed by task rather than by clarification and has no per-item resolve/read-state concept of its own — clicking one just peeks the task, same as every other Inbox item. Doesn't participate in the unread-badge logic below (`hasUnseenInboxItems`) — completion already has its own push notification, so this section is for *browsing/finding* a submission later, not surfacing an urgent unread count, same reasoning the merged-in **Finished** items above already don't count toward the badge either.

Read/unread for **Answered** is tracked client-side only — `localStorage` (`inbox-last-viewed-at`), not a database column, since adding a field to the shared `clarifications` jsonb for this would mean touching an already-race-prone read-modify-write column just to track something purely local to one viewer's one device. `TaskBoard.jsx` owns reading/bumping this value (on entering the tab) so the same value can drive both the nav badge (an unseen-answer dot on the Inbox nav item, shared markup so it renders on mobile's bottom bar and desktop's header-folded nav alike) and `InboxView`'s per-item styling, without either needing to poll the other. Needs-your-reply and Finished don't need this tracking — both are inherently self-clearing the moment their state changes (answered/resolved), the same reasoning the 💬 badge already relies on. (Answered and Finished now share a UI section, **Resolved** — this per-`kind` distinction is still what the badge and per-item read styling key off internally, unaffected by that merge.)

Clicking an Inbox item reuses `TaskBoard.jsx`'s existing "peek" mechanism (`peekTaskId` → a `Modal` with `<TaskRow defaultOpen>`) to jump straight to that task's expanded detail regardless of which day it's on — no separate deep-linking was built for this.

## Cork Board

`cork_notes` — quick pins with no due date and no timeline, the opposite of a task, which is deliberately scheduled. This is the **one place in the app where visibility isn't automatically mutual**: every other table uses `is_member()` alone for its select policy (mutual visibility is the whole point of this app — see What this app is), but `cork_notes`' select policy is `is_member() and (shared or author_id = auth.uid())`. A pin defaults to private (`shared = false`); posting it to the other person's board is an explicit toggle in the compose form (`CorkBoardView.jsx`), not the default. Only the author can edit or delete their own pin, even once shared — the other member can see it, not manage it; editing (`startEdit`/`handleSaveEdit` in `CorkBoardView.jsx`) swaps the pin's body into an inline textarea in place, same shape as the compose form. No push notification fires on posting, sharing, or editing; it's a scratchpad, not an assignment.

**Comments**: a flat, append-only `comments` jsonb array per pin (`{ id, authorId, body, createdAt }`) — no reply-to-reply nesting, same "doesn't need a child table" reasoning as `checklist`/task `clarifications`. Unlike the pin's own body/sharing, comments are meant to come from *either* member once a pin is shared (an evolving back-and-forth, not something only the author manages) — but the plain `update` RLS policy is deliberately author-only, so a comment write goes through `add_cork_note_comment()` instead, a `security definer` Postgres function that re-checks visibility inline (`shared or author_id = auth.uid()`) and only ever touches the `comments` column, never `body`/`shared` — it can't be used as a backdoor around the author-only edit restriction. Same silent-by-design reasoning as the pin itself: no push notification on a new comment, unlike task clarifications' ask/answer.

Self-contained like `RentalsView.jsx`/`EodReportsList.jsx` (fetches its own data, no props from `TaskBoard.jsx` besides `me`/`memberName`), but unlike those two it also subscribes to a `cork-notes-changes` Realtime channel — the board is meant to update live as either person pins something, same reasoning as the `tasks-changes`/`members-changes` channels in `TaskBoard.jsx`. **`cork_notes` must be added to the `supabase_realtime` publication by hand** (`alter publication supabase_realtime add table cork_notes;` in the Supabase SQL editor) — see the Realtime note under Architecture; this is not run automatically by `schema.sql`.

**Focus today**: any pin (own or shared-from-the-other-person — visibility already gates which pins render at all, so no extra check here) can be promoted into a real task via `handleFocusToday()`, which mirrors `PrioritiesForm.jsx`'s day-period logic exactly (`title` = the pin's body, `due_date` today at 23:59 local so it can go overdue like any other task, not an All Day task). Assigned to whoever does the promoting (`whoKeyForName(me.display_name)`), not the pin's original author — claiming it is the point, and for a shared pin the promoter is often the other person. Promoting doesn't unpin or otherwise touch the original note; `promoted`/`promotingId` are transient component state only (not persisted), so the button reverts to "Focus today" on reload — re-promoting just creates another task, which is an accepted low-stakes edge case rather than something guarded against.

## UI structure

Five persistent destinations — **Today** (the task list, default), **Rentals**, **Reports**, **Cork Board**, **Inbox** (see Inbox above) — are tracked in `TaskBoard.jsx`'s `activeTab` state. `RentalsView.jsx`, `EodReportsList.jsx`, and `CorkBoardView.jsx` are plain tab content, not modals — no `onClose`, nothing to dismiss, you just switch tabs; all three are exclusively reached this way (no other call site). A slide-in panel treatment for Cork Board (toggled from the nav rather than a tab, inspired by Structured's "Inbox" panel) was tried and reverted — plain tab content was simpler and preferred.

**Nav placement** is a second JS-driven responsive branch (`isDesktop = useMediaQuery('(min-width: 900px)')` in `TaskBoard.jsx`, same hook the Rentals dashboard already established this pattern with) rather than a CSS-only split, because — same reasoning as Rentals — mobile and desktop aren't the same markup repositioned, they're different arrangements: mobile is a fixed bottom tab bar (`<nav className="task-board-nav">`), separate from `.task-board-header`; desktop folds the nav buttons directly into that header row instead (`<nav className="header-nav">`, rendered only when `isDesktop`), so there's no left sidebar at all anymore — `.task-board`'s desktop rule dropped the `display: flex; gap: 28px` it used to seat a 200px sidebar beside `.task-board-content`, and is just a wider centered single column now. Both `<nav>` renders share the exact same `navButtons` array and `.task-board-nav-item` button markup (built once in `TaskBoard.jsx`, reused by whichever `<nav>` actually mounts) — `.header-nav .task-board-nav-item` overrides that markup's layout via a descendant selector (row instead of the mobile bottom-bar's stacked icon-over-label, smaller icon, tighter padding) rather than a second parallel class, so there's one source of truth for what a nav item's icon/label/active-state markup actually is.

Row order in the header, left to right: the date/page-title element, then a `.header-right-group` wrapping *both* `.header-nav` and `.header-actions` together with `margin-left: auto` on the group itself (not on each piece independently, and not `justify-content: space-between` on `.task-board-header`) — the group's position relative to the header's right edge stays fixed regardless of how long the title/date text on the left happens to be ("August 2026" vs. "Awa Rentalz" vs. "Cork Board"), so switching tabs doesn't visibly shift the nav left/right. Splitting the auto-margin across `.header-nav` and `.header-actions` separately was tried first and rejected — two independent auto margins split the header's leftover space between them instead of keeping nav snug against `.header-actions`, so nav's position would still drift depending on title length.

On the wide layout, the Today tab's section groups (All Day / Overdue / Today) get a hairline `border-top` between them (`.task-list > section:not(:first-child)` inside the `min-width: 900px` block) — plain spacing reads as a break fine on the narrow mobile column, but looked like the sections just trailed off on the wider desktop content area.

Everything else is a one-shot action, not a place you browse an ongoing state of — those stay behind the floating "+" button (`NewTaskForm.jsx`), which doubles as a speed-dial menu whenever an `extraActions` array is passed to it. That array (bulk add/edit tasks, priorities, submit report, vault — ordered by roughly how often you'd reach for each, with the rarest/most sensitive one, Vault, last) is built and scoped per-viewer in `TaskBoard.jsx`'s `quickActions` (e.g. "Submit report" only appears for Aaron) — `NewTaskForm.jsx` itself has no opinion on who sees what. The header stays minimal — working-status indicator, a 👋 nudge icon (Ada-only, next to the badge — see Push notifications below), and a single ⚙️ settings button (`SettingsMenu.jsx`: who's signed in, notifications toggle, theme, default timezone, a How-to-use guide, sign out) — separate from the nav. Nudge used to live in this same `quickActions` speed-dial (alongside report/vault) but moved back out to its own header icon — unlike those, it's reached for often enough, and time-sensitive enough in the moment, that two taps behind the FAB menu was real friction; being one narrow, Ada-only exception doesn't reintroduce the header clutter the speed-dial was originally built to avoid (Aaron's header is untouched either way). "Signed in as {name}" sits above the notifications toggle specifically since both accounts sometimes share a device/browser — a quick check before assuming the wrong person's notification setting is the one being flipped. `HowToGuide.jsx` opens as a modal nested inside `SettingsMenu.jsx`'s own modal (same portal-based nesting `ScrollSelect` already relies on — see Modal above) and is the one place in the app with user-facing documentation of what each tab/feature does, kept in sync by hand whenever a section here changes. It has two tabs (`view`, `'guide'`/`'faq'`, reusing `.period-tabs` — same markup/class BulkAddTasksForm's Add/Edit toggle and the Today tab's Day/Week/Month tabs already use) — a Guide tab (one section per tab/feature) and an FAQ tab (real questions Ada has asked, written from her side since she's the one without a write toggle on working-status/reports). Each tab is its own accordion with independent state (`openSection`/`openFaq`, a single value each, not a Set — only one item open at a time within a tab, opening one closes whichever was open in that same tab) rendered through one shared `AccordionList` component so the two lists can't drift into different markup/behavior. On desktop the modal itself (`.how-to-guide-modal`, `min-width: 641px`) gets a fixed `width`/`height` instead of the `.submission-modal` default of sizing to content, so the card doesn't visibly grow and shrink on every section toggle; below that breakpoint it stays a content-sized slide-up sheet like every other mobile modal.

`BulkAddTasksForm.jsx`'s Add tab teaches one paste format now, not two: `<date> [time] – description` (`src/lib/bulkTasks.js`'s `parseBulkTasks`, item-line shape) — a real time (`splitDateAndTime()`, a tight-hyphen range like "8am-9am" or a single time, peeled off the end of the date phrase before `parseDateHeader` ever sees it) is now optional on the *same* one-line shape, rather than requiring a switch to the original two-line "date header, then bare shift lines under it" format just to get a specific time on a task. That original format (`parseShiftLine`, `currentDate` context-tracking in `parseBulkTasks`) still parses exactly as before — nothing removed, so an existing paste in that shape still works — it's just no longer what the hint text/placeholder teach, since it needs remembering "this date stays in effect until the next date line" where the one-line format needs nothing held in your head between lines. `splitDateAndTime` is tried speculatively on every item-line's date prefix regardless of whether it ends up resolving to a real date; an unresolved prefix (a dependency note, a fuzzy phrase) falls back to the *original untouched line* as the title either way, so a false-positive time match can't corrupt it. A `NO_DATE_MARKERS` prefix ("ASAP", ...) plus a time is a contradiction the parser doesn't try to interpret — the time is just dropped, same as it would be for an unresolved line. A date/time prefix can also end in a zone abbreviation (`ET`/`CT`/`MT`/`PT`/`PHT`, the same short names `zoneAbbreviation()` in `timezone.js` already shows on every zone-aware badge — `splitTrailingZone()`, tried before `splitDateAndTime()` since the zone always comes last, after the time when there is one) to override the form's single Time zone dropdown for just that line — the dropdown alone can't cover a paste that mixes, say, Ada's Central shifts with Aaron's Philippines-time tasks in one go. Falls back to the dropdown's zone (`due_timezone: null` on the parsed task) when a line doesn't name one; a `NO_DATE_MARKERS` line drops a named zone too, same contradiction reasoning as the dropped time. The preview list's zone badge shows each row's actually-resolved zone (override or dropdown fallback), not just the dropdown's zone repeated on every row. A line indented underneath a task (`isIndented()`, checked on the raw line before any trimming — the only signal, tried before every other line shape) attaches as a checklist item on the most recently pushed task instead of becoming a task of its own, using the same `{ id, text, done, blocked, blockedReason }` shape `ChecklistEditor.jsx` builds by hand, so it's editable the normal way immediately after creation — an indented line with no task above it yet (nothing yet pushed to `tasks`) is a parse error rather than silently dropped. An optional `!high`/`!med`/`!low` marker (`splitPriorityMarker()`, tried anywhere in the prefix rather than pinned to a fixed position like the zone override, since the `!` sigil can't collide with any other syntax here) sets that task's `priority`, closing a real gap — Bulk Add, `PrioritiesForm.jsx`, and Cork Board's Focus-today promotion all used to silently create every task at the DB's `'med'` default with no way to say otherwise. Unlike the zone/time overrides, a priority marker survives on a `NO_DATE_MARKERS` line (`ASAP !high`) — gated on `resolved`, not `date`, since urgency and datelessness aren't the contradiction a specific time on a dateless line would be. The preview list shows a `task-priority-dot` (same component TaskRow.jsx uses) only on rows that actually named one, not on every row, since most tasks land at the ordinary default silently and a dot everywhere would just be noise.

`BulkAddTasksForm.jsx`'s Edit tab can reschedule a batch, not just retitle/reassign/re-timezone it: a Date/Time field with two modes (`dateTimeMode`, mirroring Title's own Add before/Add after/Replace with pattern) — "Shift by" adds a signed days/hours/minutes offset to each selected task's *own* due_date (MS_PER_UNIT), leaving due_timezone untouched and silently skipping dateless tasks the same way the Time zone field already does (nothing to shift from); "Set to" instead replaces due_date outright with one exact date/time for every selected task, interpreted in the Time zone field's own selection (`editTimezone`) regardless of whether that field's own checkbox is on, and applies to dateless tasks too — pinning a batch of floating "ASAP" items to a real date is exactly the case Shift can't cover but Set can.

`TaskExportForm.jsx` is read-only, the opposite of Bulk add/edit — a plain text dump of every task's title/date/time/timezone, meant to be copied or downloaded and reviewed *outside* the app (pasted to Ada/Aaron directly, or to an AI, to sanity-check "is everything actually scheduled right") rather than parsed back in the way Bulk add's own paste format is. Reached from a small "Export tasks" link in `BulkAddTasksForm.jsx`'s header row (`.bulk-add-header-row`) — stacked on top via `<Modal>`'s own portal rather than a third Add/Edit/Export tab, since reviewing a batch is a genuinely separate task from adding or editing one and doesn't need to share that form's Cancel/Create/Apply footer. Used to also have its own `quickActions` item on the "+" menu — dropped as a redundant second entry point once Bulk Add's own link already got you there. Grouped by day (the *due_timezone's* calendar day, not the viewer's — same due_timezone-aware formatting as `TaskRow.jsx`'s `dueLabel`, since the whole point is catching a task set in the wrong zone, which a silently-converted export would hide), dateless tasks trailing in their own group at the end. Defaults to All (not the signed-in member's own tasks the way Bulk add's Who picker does) and excludes completed tasks unless toggled on, since double-checking a schedule is normally about everything at once, not one person's slice of upcoming work.
